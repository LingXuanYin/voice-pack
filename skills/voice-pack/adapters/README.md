# Adapters overview

**The adapter** is the one piece for a runtime environment: it maps the required capabilities (`vocab/capabilities.json`) to concrete models or services in that environment. Models connect only through adapters; the layer that holds all adapters (this directory, `adapters/`) is called the **environment adapter layer**.

This file is the **single source of truth** for the adapter contract: the factory signature, the shape of the return value, the error conventions, capabilities that are only declared, where the model name in the verification record comes from, and how to report a model change are written only here. Other files only point to it; when something changes, change this one place.

## What an adapter is

| Kind | Where | How to pass it on the command line |
|---|---|---|
| Official adapter | `adapters/<name>/adapter.mjs` (the name is lowercase letters, digits, hyphens); the only official one is `process` (`process/README.md`: forwards capability calls to your own program) | `--adapter <name>`; if `adapter.json` declares a shorthand, the shorthand also works ("How to pass it on the command line" below) |
| Other adapters (your own, or shipped with another product) | An ES module file, or a directory that contains `adapter.mjs`, placed anywhere | `--adapter <module file or directory>` (a value that is not an official name is treated as a path, relative to the command's current directory; an official name is made only of lowercase letters, digits, hyphens, so a directory called `mytts` in the current directory must be written `./mytts`) |

Both forms are the same: the default export is the same **factory** (or a function exported under the name `createAdapter`). **Adding an official adapter only adds the directory** `adapters/<name>/` and changes no other file. Official adapters are not tied to a platform and do not name a model (where a model name may appear: see `../README.md`「Rules」); the general layers (`protocol/`, `lib/`, `tools/`, `cli/`) do not import any adapter and do not mention anything specific to one adapter in their text; adapters are used only through `cli/adapters.mjs`.

## The factory function

```js
export default async function createAdapter({ cwd, dir, env, options, use, VoicePackError }) {
  return { capabilities, runtimes, fetch, billing, limits, previewCard, models };   // 每一项都可选
}
```

It may be a synchronous or an asynchronous function. The parameters it receives:

| Parameter | What it is |
|---|---|
| `cwd` | The command's current directory |
| `dir` | The adapter's own directory (for your own adapter: the directory of the module file, or the directory you gave). For an official adapter given by name on the command line, it is the command's current directory |
| `env` | The runtime environment the command has at this moment (the command's own, plus the adapters given before this one); read-only. To see whether a capability or `fetch` is present, look here |
| `options` | The parameters given to this adapter on the command line, `{ key: string }`; `{}` if none were given. The adapter itself says which keys it accepts (see "How to pass it on the command line" below) |
| `use(name, options)` | Loads another official adapter and returns its return value (it is **not** merged into the environment; how to use it is up to you). A name that is not an existing official adapter (a malformed one, for example one with a path, counts too) throws `adapter_not_found`; a name that is not a string is a wrong call and throws `TypeError` |
| `VoicePackError` | The library's error class (see "Error conventions"), so your own adapter does not need to import a file of the base part |

### Shape of the return value

Return an object. The seven keys below are all optional, and an **unknown key is an error** (most likely a typo, so it is not silently ignored):

| Key | Value | How the general layer uses it | If not given |
|---|---|---|---|
| `capabilities` | `{ capability name: function }`; the capability name may only come from the capability vocabulary; a capability that is only declared has the value `true` ("Capabilities that are only declared" below) | Merged into the `capabilities` of the command's runtime environment | This adapter provides no capability (that is only "none", not an error; the check gives one warning) |
| `runtimes` | `{ tool name: function }`, the implementation of command-line tools, for example `ffmpeg`; the signature is written in the header of the first module that calls it (`@runtime`) | Merged into `runtimes` | The command's existing ones are used |
| `fetch` | A function, same as the standard `fetch(input, init)` | Becomes the command's network read (all network reads go through it) | The command's existing one is used |
| `billing` | A non-empty string: one sentence saying **where the cost is charged** when this adapter's capabilities are called. Write it as a phrase that can follow "This needs" (the notice reads "This needs <billing>"), for example "a call on an account, and the cost is charged to the user's own account" | Before each step that spends money, the command writes it to standard error, starting with "This needs", followed by how many times each capability will be called; with `--json` it is not said, so the machine-readable output stays clean (`dub`, `convert`, `make-pack`, `fidelity` all do this) | The command says nothing about cost: this adapter does not spend money, or the cost is not its concern |
| `limits` | `{ maxChars?, minChars?, maxPromptTokens?, maxPauseInRequestMs?, maxSpeakers? }`: `maxChars` is **the maximum number of characters in one request** (including the cue that `dub` adds at the start of the request), an integer, not less than 10 (same as `dub`'s `--max-chars`); write the number of characters one request on this platform reliably holds, with its source written in the adapter: how much the model itself can hold is in the model notes, and limits the platform adds in front (for example how long a gateway waits) count too. `minChars` is **the minimum number of characters a synthesis capability needs per call**, an integer, not less than 1 (code points, same as the `minChars` option, see `lib/dub.mjs`), for example 15. `maxPromptTokens` is **the maximum input a single `text-generation` request accepts**, an integer, not less than 1; write the number the model or platform states (the unit follows its source, usually tokens). `maxPauseInRequestMs` is **the maximum length in milliseconds of one pause inside one request**, an integer, not less than 0; write the longest pause the model can produce on this platform (source written in the adapter); 0 means every pause is split out. `maxSpeakers` is **for an environment that declares `scene-in-request`, the maximum number of speakers in a scene**, an integer, not less than 2; write the upper limit of reference segments the platform states | `maxChars`: `dub` splits by it by default, counting the characters that are sent: if the same chapter and the same voice fit, it is one request; if they do not fit, it first cuts at a scene boundary (a line that only holds a pause), then between lines, and only if one line does not fit by itself between its sentences (`lib/dub.mjs` steps 5, 5c); a scene is cut into several scenes between lines (step 5a). `dub` has its own default limit as well: about 1000 characters to be read aloud per request (`DEFAULT_MAX_SPOKEN_CHARS` in `lib/synthesis-limits.mjs`); both must be met, so when the declared number is larger than that, it is mostly that one that cuts first; a `--max-chars` given on the command line overrides both. `minChars`: `dub` merges segments by it; a segment that cannot be merged is recorded as failed and the capability is not called (rules in the header of `lib/dub.mjs`); the trial synthesis of `make-pack` does not merge segments, and a held-out recording shorter than it is not synthesized, is recorded as `skipped` (`too_short`), and does not enter the ratio. `make-pack --card-line`: the audition line is handed to dubbing, using `maxChars`, `minChars`, `maxPauseInRequestMs`; it is planned before any money is spent, and if it is not exactly one request, or is shorter than `minChars`, it reports `make_pack_input_invalid` (`lib/make-pack-card-line.mjs`). `maxPromptTokens`: no base part command uses it now (`dub` no longer has the model judge emotion); declaring it is still accepted and is not an error. The old `maxPauseInTextMs` (the maximum total length of the pauses written as `<break>` in one request): `dub` no longer writes `<break>` and does not use it; declaring it is still accepted and is not an error (earlier adapters still connect as before). `maxPauseInRequestMs`: in step 5c `dub` merges a passage into one request; pauses not longer than it are written in the text, and those longer than it are cut at that spot and left to concatenation (each pause is compared on its own; rules in the header of `lib/dub.mjs` and in `lib/pause-in-request.mjs`). `maxSpeakers`: in step 5a `dub` puts a passage spoken by several people in turn into one request; the speakers in one scene do not exceed it, and when they would, it cuts before that point | No limit: without `maxChars`, `dub` cuts only by its own default of about 1000 characters to be read aloud (if the same chapter and the same voice fit, it is one request); without `minChars`, no segments are merged; without `maxPauseInRequestMs`, the base part default is used (`DEFAULT_MAX_PAUSE_IN_REQUEST_MS` in `lib/pause-in-request.mjs`); without `maxSpeakers`, the number of speakers in a scene is unlimited |
| `previewCard` | `{ productName?, links?: { open?, make? } }`: the **product** behind this adapter, and what to write on the preview card (`index.html`) of the share file. `productName` is the X in "Open in X"; `links.open` is the open entry and `links.make` is the "make one of your own" entry, both complete `http` or `https` addresses in which `{id}` is replaced with the pack ID. The shape is the same as the `--product-name`, `--open-link`, `--make-link` of the core layer's `pack` command | When `make-pack` builds a share file with `--share-file`, it hands this to the card generator (`protocol/lib/preview-card.mjs` writes no product name or address and only accepts the values the caller gives) | The card has no product name and neither of the two entries (this is also the case when only other adapters are used, or no adapter) |
| `models` | `{ capability name: model name }`: which model each capability this adapter provides uses; the model name is a non-empty string and the capability name may only come from the capability vocabulary. It is only a notice in advance and does not govern which model is actually called: the model actually used is still written in the return value of each capability call ("Where the model name in the verification record comes from" below) | The summary line of `dub --dry-run` writes "model: …" from it (no capability is called, and the user knows which model will dub before any money is spent) | The summary line says "the adapter does not say which model" |
| `prices` | `{ capability name: number }`: **roughly how many US dollars each call** of this capability costs (a number not less than 0); the capability name may only come from the capability vocabulary. The base part does not know prices, and estimates the amount only from this | In the cost notice and the dry run before `dub`, `make-pack`, `design`, `convert` spend money, one sentence with the estimated amount is written as "counts of each item x unit price" (`make-pack` also writes the maximum if every transient error is retried); for the same capability, the last adapter that gave it wins | It writes "Amount: the adapter gives no unit price, so it cannot be estimated"; for capabilities that have none, the estimated amount excludes them and names them |

How several adapters given together are merged (which one overrides which for a capability of the same name, how `billing` is joined, whose `limits`, `previewCard`, `models` and `prices` are taken) is written **only in one place, the header of `cli/adapters.mjs`**, and not repeated here.

`billing`, `limits` (`maxChars`, `minChars`, `maxPromptTokens`, `maxPauseInRequestMs`, `maxSpeakers`), `previewCard` and `models` are the adapter's own business (which account bears the cost, how many characters one call can synthesize at most, how much input the model can accept at once, which product is written on the card, which model is used). Putting them in the return value means the general layer does not need to read some adapter's product contract. **Do not write a second copy of the numbers the adapter gives in code**: if it has its own data, take them from there (for example, for an adapter shipped with a product, `maxChars` and `previewCard` are read from that product's own contract file).

The shape of the return value is checked by `checkAdapterShape` in `lib/adapter-check.mjs`; if it does not conform, loading reports `adapter_invalid`, and `details.problems` says what is wrong, one item at a time.

### The capability list

A capability is a function: **one object parameter**, and a **return value (it may be a Promise)**; the fields of the parameter and return value, and the errors, are **written only in `vocab/capability-signatures.md`**, in the signature of each capability, and not copied here. Audio is always bytes plus a MIME type `{ bytes, mimeType }`; URLs, Base64 strings and file paths are not accepted.

Provide only the capabilities the environment has: do not pretend; a feature that uses a missing one throws `capability_missing` and names it.

### Capabilities that are only declared

One kind of capability is not a function but a **declaration**: the environment provides it, which means other capabilities will do what it says. There are four now. `phoneme-in-text`, written as `'phoneme-in-text': true`, means the synthesis capability accepts pinyin phonemes in the text (`<phoneme alphabet="x-pinyin" ph="…">`, written inside `<speak>`), and the adapter translates the alphabet into the form of its own service (the form is written in the same place). `phoneme-markers`, written as `'phoneme-markers': true`, means the synthesis capability accepts phoneme tags in the text (`<|phoneme_start|>phonemes<|phoneme_end|>` replaces the word; for Chinese it is pinyin with numeric tones, one tag per syllable; for English it is CMU Arpabet, one tag per word; for Japanese it is romaji with pitch digits, one tag per entry): dubbing writes the phonemes of the pronunciation lexicon as these tags and the adapter sends them out as they are, without conversion; if both are declared, dubbing uses phoneme tags. The form is in `vocab/capability-signatures.md` under `phoneme-markers`. `scene-in-request`, written as `'scene-in-request': true`, means `text-to-dialogue` accepts every turn (`turns`; the cue of each turn is written in that turn's text), and dubbing may put a continuous passage spoken by several speakers in turn into one request (one audio); it counts only if `text-to-dialogue` is also present; the maximum number of speakers in a scene is stated by `limits.maxSpeakers`; the form and the reasons are in `vocab/capability-signatures.md` under `scene-in-request`. Declaring it switches the approach used for these scenes (one voice per speaker, emotion carried by the cue of each turn), so whether to declare it is decided by the adapter and the options the host turns on; it is not declared just because `text-to-dialogue` exists. `seed-in-request`, written as `'seed-in-request': true`, means `voice-cloning` accepts `seed` (`text-to-dialogue` already does): the same seed plus the same input tries to give the same result; dubbing uses this to give every request the same fixed `seed` (a segment redone with `dub --only`, and an audition line redone with the same request, use the previous one plus 1), and the several pieces of a split long text use the same one; each segment of `dub.json` records it (`units[i].seed`). Declare it only if the model accepts this parameter; if it is not declared, dubbing gives no `seed`. The form is in `vocab/capability-signatures.md` under `seed-in-request`. "How to say it" has no declaration: the cue is written in the text and handed to the model as it is (`vocab/capability-signatures.md`「How to read it aloud」›「Cues in the text」). The list is written only in `DECLARED_CAPABILITIES` in `protocol/lib/env.mjs`, and the check and the skeleton generation both follow it; a value that is not `true` reports `declaration_not_true`.

A declaration states **what this environment can do for the caller**, not which field happens to be in the request format of the model or service. If the model or service has another way to accept this kind of information (a meta field, a separate call, text spliced into the prompt), the adapter translates to it and then declares it. "The model or service cannot do it" and "this adapter did not put it in the request" are two different things: the latter must be fixed in the adapter and cannot be used as a reason not to declare. The criterion is whether the model or service can do it, not whether the current request-building code has that key.

The 2.x declarations `style-instruction`, `style-cues`, `pause-in-text`, `cue-in-text` no longer exist since capability vocabulary 2.0: when a command loads an adapter it checks only the shape, so it still connects (one extra key nobody asks for in the environment); the structure check of `adapter check` reports `capability_unknown` and fails; delete them.

### Where the model name in the verification record comes from

The "which model was used" written into the verification record when making a pack comes from **`model` in the return value of the capability** (a non-empty string): if the adapter is willing to report which model was actually used, it reports it, and the library records it in the verification record and the fidelity report; if it does not, this item cannot be written in the verification record (the check gives one warning `model_missing`). The "environment" in the verification record takes the adapter name from the command line (joined with `+` if there are several), and can be changed with `--environment`.

### When the model changes

When the model that was to be used is unavailable at that moment (for example the service is down), another model may be used instead. Whether to switch is decided by the platform that uses the voice pack, in one of two ways: the platform's adapter switches by itself within one capability call (when to switch and to which is written in the adapter's own notes, and is reported as below); or the platform's own skill decides, switches to another model and calls again (then the adapter calls only the model it was told to, there was no switch this time, and no `modelChange` is given). The general layer and the base part do not switch models, do not substitute another capability, and do not retry for a capability. If the adapter switched, it must report it truthfully: for the same character a different model may give a different voice and acting, and the user must know.

- `model` in the return value is still the model **actually used** (a non-empty string).
- When the model was switched, also give **`modelChange: { from, reason }`**: `from` is the model that was originally to be used, and `reason` is one sentence for people saying why it was switched (for example "the original model was unavailable at the moment (503)"); both are non-empty strings. **If there was no switch, do not give it** (giving `null` also counts as no switch).
- If `modelChange` is given, `model` must be the one switched to. If it is written wrongly (`modelChange` is not an object, `from` or `reason` is not a non-empty string, or there is no `model`), the library reports `capability_result_invalid` (`details.problem` is `model_change_invalid`) and stops, like any other wrong return shape: a switched model is something the user must be told, so a wrong entry is not silently dropped.
- If the service refused this request (wrong parameters, moderation refusal, and other errors not marked `transient`), report the error as it is, following "Error conventions", and do not switch the model to get around it.
- What reads it now is dubbing: the returns of `voice-cloning` and `text-to-dialogue` in `dub` carry it, that line in `dub.json` records `model` and `modelChange`, and the command line output adds a separate notice listing which lines were switched to what and why (header of `cli/commands/dub.mjs`). Making a pack with an audition line (`make-pack --card-line`) reads it too: `cardLine` of the report records it, the hint is `card_line_model_changed`, and the text output states both models (header of `lib/make-pack-card-line.mjs`). Other features (`convert`, `fidelity`, transcription) do not read `modelChange` yet. The trial synthesis of making a pack goes through dubbing: a wrong `modelChange` likewise reports `capability_result_invalid` and the pack making stops; a correct one does not enter the report.
- The program of a process adapter (`process/README.md`) writes these two items in the `result` of its response, and they are passed through as they are.
- The field name is `modelChange`, not snake_case like the other fields of the signature tables (`vocab/capability-signatures.md`「General conventions」): when this name was fixed, platform adapters were already written that way.

## Error conventions

Errors an adapter throws are treated by the general layer as follows:

1. **Which errors to throw and how to fill in the fields of `VoicePackError`: follow the "Errors" section of `protocol/README.md`**; the `VoicePackError` class is in the factory parameters (see the table above), so you do not import it yourself. The `code` an adapter throws is defined by whoever throws it, written in the adapter's own header.
2. **Mark transient service errors**: upstream 5xx, gateway timeout, network error, timeout, and the like, which may succeed if tried again later: throw `VoicePackError` and write **`true` in `details.transient`** (put the HTTP status in `details.status` if there is one). Features that call a capability many times (`fidelity`, `dub`, `make-pack`, transcription of long recordings) use it to record that item as "not heard" or "failed", go on with the rest, and decide afterwards whether to redo it, instead of voiding the whole job. **Do not mark what a retry would not fix**: a missing capability, wrong parameters, rejected credentials, a wrong return shape, a business error the service reported explicitly. An error that is not marked is passed up as it is by the general layer, which does not guess from the HTTP status.
3. **Block later calls when credentials are rejected**: when the service answers that the credentials are wrong (HTTP 401, or equivalent), throw an error without `transient`, and **after that this adapter sends no more requests to the service**: later calls directly throw the same `code`, with `details.halted` as `true`, saying it was rejected before. Reason: some services treat a rejected credential as an invalid login and clear the user's local login state, and trying once more makes things worse. The caller should stop and let the user deal with it, not retry. For the first rejected error, `details.status` is `401` (for a service that is not HTTP, write `details.halted: true` from the first time): the library recognizes only these two (`keepsThrowing` in `lib/capability-calls.mjs`); if it cannot recognize it, it is treated as an ordinary error: making a pack, when picking the default segment, falls back to another way and goes on, an audition line is recorded as an ordinary failure to dub, and there is no prompt to handle the credentials first.
4. **Do not retry billable calls**: the library does not retry capability calls (retrying things like creating a task or completion may charge twice); the only exceptions are the kinds of calls listed in the table "谁用它" ("who uses it") in the header of `lib/call-attempts.mjs` (all may be billed), which are tried again only on a transient error (`details.transient`), and the maximum number of tries is written there too (a blind listening error is not here, it has its own redo). So transient errors must be marked correctly: for an error marked `transient`, the library calls once more for the same recording or the same line; for one not marked, it does not. The number of extra calls is written into the "confirm cost" step by the maximum count, and what the user agrees to is the upper limit; a billing fact measured on an environment (whether a failed call is charged) is written in that environment's adapter. The adapter itself retries only steps that cost no money and can be done again (for example read-only polling), and states which are retried and how many times.
5. **Credential values never appear anywhere**: the `message`, `details`, logs and `cause` of an error must not contain the value of a token or key. The credentials an adapter reads are used only to send requests.
6. **Report a blocked answer as blocked, not as an answer**: if the answer obtained by the capability that listens to audio (`audio-text-to-text`), or the result of transcription (`automatic-speech-recognition`), is the notice the provider returns when its content filter blocks it, throw `provider_blocked`, without `transient` (asking again about the same recording is still blocked). What is recognized is the provider's own wording, so it is written only in the adapter, and the general layer recognizes only this code. How to write it and how the library treats it is written only in `vocab/capability-signatures.md`, in the section on `audio-text-to-text` under "The provider blocked the answer", and in the section on `automatic-speech-recognition` under "The provider blocked the transcription of this segment" (for a service where asking again about the same segment sometimes passes, the transcription may also be reported as a transient error: then write `provider_blocked` in `details.problem`; if you do not, the library treats it only as a transient service error and, once the retries are used up, tells the person to redo it later; how to write it and what the library does is under "A blocked answer may also be reported as a transient error" below it).
7. **Mark a refusal tied only to this text with `details.textRejected`**: if a capability refuses because of the text to be said this time (too few or too many characters, a character it cannot handle, the provider's objection to this line), throw `VoicePackError` and write `true` in `details.textRejected`, without `transient`. The convention and how the library (dubbing) treats it are written only in `vocab/capability-signatures.md`「General conventions」. The adapter marks only what it can recognize: its own checks before touching the service (character count, characters, whitespace; the code uses `capability_input_invalid`, and the library does not count it), or the provider's own wording (written into that adapter's code with its source noted; the code does not use `capability_input_invalid`, and the library counts it); what it cannot recognize it does not mark. Errors that are the same for every line, such as references, credentials, parameters, the description of the voice, are not marked and stop as usual.
8. **Mark an answer that did not end normally or is empty with `details.unusable`**: if the answer of the capability that listens to audio (`audio-text-to-text`) was truncated (`stopReason` is `length`), failed midway (`error`, `aborted`), or has no text, throw an error code the adapter defines itself (`details.problem` is `stop_reason` or `text_missing`) and write **`true` in `details.unusable`**, without `transient` (every question costs money, and asking again may give the same). The library records that item as voided, does not throw it upward, and does not stop the whole run. The convention and how the library treats it are written in `vocab/capability-signatures.md`「General conventions」.
9. **Mark a result finished on the service side but not retrieved with `details.unretrieved`**: if the created task is already done and billed, and only downloading the result (or another retrieval step) failed and the adapter's own retries still did not work, throw `VoicePackError`, write **`true` in `details.unretrieved`**, and write in `details.retrieve` one sentence on how to retrieve it (a lead such as a command or task number; no URL, no credentials), without `transient`: calling the capability again would be billed again. Dubbing lists this line separately as "not retrieved" and does not put it into the redo command. The convention is written only in `vocab/capability-signatures.md`「General conventions」.

Errors when loading an adapter (`cli/adapters.mjs`): `adapter_invalid` (`details.reason`: `load` the module cannot be loaded, `not_function` there is no default-exported function, `factory_failed` the factory threw an error, `shape` the return shape is wrong, `manifest` the `adapter.json` of an official adapter is broken, `skeleton` the skeleton generator `skeleton.mjs` of an official adapter cannot be loaded, does not export `generateSkeleton`, threw an error, or returned a wrong shape (reported on `adapter new`; `details.problem` says what is wrong)) and `adapter_not_found` (a name was given and `adapters/` has no such official adapter; the error message teaches that your own adapter must be given as a path; a wrong name in `use(name)` inside an adapter is this too). A `VoicePackError` thrown by the factory itself goes up as it is, not wrapped.

## How to pass it on the command line

`dub`, `convert`, `make-pack`, `fidelity` all accept the same set of parameters. The only unified entry is `cli/adapters.mjs` (merge rules above, written only in its header):

- `--adapter <name|module file>`: may be given several times.
- **How adapter parameters are passed**: `--adapter-option <key=value>`, placed after the `--adapter` it is for (the value is a string, and may contain `=` and spaces); the factory reads from `options`. A key is letters, digits, underscores, starting with a letter. Which keys each adapter accepts is written in its own header; whether an adapter reports an unknown key is its own decision.
- **An official adapter may declare its command-line form in `adapters/<name>/adapter.json`** (optional):
  ```json
  { "summary": "一句话", "shorthand": true, "flags": { "--zone": "zone" } }
  ```
  `shorthand` is `true`: `--<name>` is shorthand for `--adapter <name>`. `flags`: the parameters specific to this adapter; `--zone <value>` equals `--adapter-option zone=<value>`, and belongs to the nearest earlier adapter of the same name, or, if there is none before it, the first one of that name after it; if there is not one such adapter on the command line, it reports a usage error (exit 2) and is not silently ignored. This section of the command's usage text is also generated from `adapter.json`. **The declared parameter names are taken by the entry before the command sees the parameters**, so the command itself cannot use the same name.
- Right now there is only one official adapter:
  - `process`: `--adapter process --command "python my_tts.py"`; `--command` is `--adapter-option command="python my_tts.py"` (no shorthand; options and the process protocol are in `process/README.md`).

## Making your own adapter

Four steps, one command each (`node cli.mjs adapter …`; for the usage of the commands see `node cli.mjs help adapter`):

1. **Generate the skeleton**: `adapter new <directory> --capabilities <capability,…> [--kind module|process]`. The directory must not exist yet; nothing is overwritten; capability names must be in the capability vocabulary (a typo is reported before any file is written, listing the vocabulary).
   - `module` (default): an ES module `adapter.mjs` with one function per capability, whose body throws `adapter_not_implemented` (not implemented yet; defined as `NOT_IMPLEMENTED` in `lib/adapter-skeleton.mjs`); a capability that is only declared is written as `true`.
   - `process`: for when the model is a program such as Python: `program.py` (the protocol half is already written) plus `adapter.mjs` (hands the capability calls to `program.py` through the process adapter); this needs Python 3 on the machine. The protocol and options are in `process/README.md`.
   - The comment above each capability (description, parameters, return value) is **generated from `vocab/capability-signatures.md`** and not copied into the generator; when the signature table changes, newly generated skeletons change with it. An official adapter that adds a `skeleton.mjs` (exporting `generateSkeleton`) adds one more kind of skeleton; how to write it is in the header of `lib/adapter-skeleton.mjs`.
2. **Fill in**: replace the "not implemented" line in each capability with the real call, and make the return value as the comment says (audio is `{ bytes, mimeType }`; if you are willing to report the model name, write `model` in the return, and if the model was switched this time add `modelChange`, see "When the model changes" above).
3. **Check**: `adapter check <name|module file|directory> [--live] [--capability <capability,…>] [--text <text>]`. The adapter's parameters are written after it as in "How to pass it on the command line" above (for example `adapter check process --command "python my_tts.py"`).
   - By default it looks only at the **structure** and calls no capability: it can be loaded, the return shape is right, the capability names are all in the capability vocabulary, the capabilities are functions, the capabilities that are only declared are `true`, and `billing`, `limits` and `models` are written correctly; a capability named with `--capability` must be present. Failing to load (not found, broken, failing to start the program) is also a failed check, and the error is written in the result. The rules and the code of each problem are in the header of `lib/adapter-check.mjs`.
   - `--live`: additionally **calls once for real** each capability **that has a call form** with a very short input (one sentence `Hello, this is a check.`, or the one given by `--text`; for those that need audio, the human voice clip shipped with the base part `lib/adapter-check-voice.wav`, 5–8 seconds, with its verbatim transcript in the `.json` next to it) and checks the return: the audio `mimeType` matches the bytes, it can be decoded, and the length is greater than 0; the shape of text, similarity and speech intervals is right; whether `model` is present (absent is only a warning). It really calls the model and may cost money and use compute: **before calling**, it says on standard error which items it calls and how many times each, and also writes `billing` if the adapter gave one (with `--json` it does not say this, and the plan is in `live.plan` of the output). If the structure fails, no real call is made. One item failing does not stop the others from being checked. Capabilities that are only declared, or have no real call form, are not called, and the reason is stated (each reason is one word: `declaration` means it is only declared, `no_signature` means the signature table has no call form for it yet, `not_wired` means the signature table has it but the check is not wired up yet, which is only `text-to-dialogue` now; all the reasons are in `SKIP_REASONS` of `lib/adapter-check.mjs`). So for an adapter that declares `scene-in-request`, a passing `--live` does not mean `text-to-dialogue` was checked: to verify it, dub a short scene yourself with `dub` (it costs money). Voice design (`voice-design`) is also among the real calls: the input is a fixed design audition text that is long enough plus one short description (it does not accept a short sentence like `Hello.`), it costs one design request, and the notice before the call includes it. A capability not yet filled in in the skeleton reports "not implemented yet" and is not counted as the adapter being broken.
   - Exit codes: 0 pass; 1 fail; 2 usage error. `--json` outputs one JSON document (its shape is in the header of `cli/commands/adapter.mjs`).
4. **Use**: give `--adapter <directory>` to `dub`, `convert`, `make-pack`, `fidelity` ("How to pass it on the command line" above).

`lib/adapter-check.mjs` (check) and `lib/adapter-skeleton.mjs` (generation) are both pure functions that run in browsers, Node and Bun: an environment assembled by an app itself can call the check directly in tests, without going through the command line.

## Where Node-specific things go

An adapter that reads environment variables, finds programs by PATH, or starts processes does Node-specific things, which are not allowed in the library's programs (`protocol/README.md`「Module conventions」). So:

- **The factory file `adapters/<name>/adapter.mjs` is the exception**: it runs on the adapter owner's side and may use Node-specific things, and may also import the `cli/` of its own directory; only `cli/adapters.mjs` loads it, and apps and browsers never load it. The exception is given only to this one file name; other files in the adapter directory still may not use Node-specific things.
- **Keep the pure part in other files**, which run in both browsers and Node, so apps can use it directly: the part that assembles the capabilities does not touch environment variables and does not start processes, and the client, credentials and network reads are all given by the caller; `adapter.mjs` only connects the Node-side things (environment variables, the local client). A process adapter works this way: `wire.mjs` (request encoding, response parsing) is pure, and `cli/session.mjs`, which starts the process, is Node-specific. The skeleton generator `skeleton.mjs` is pure too.
- An adapter depends only on the core layer (`protocol/lib/`) and its own directory.

## Trust

An adapter runs directly in this process, not isolated, with no confirmation from the user, like the scripts in a pack. Whether to use an adapter and which one is the decision of the person at the command line; do not connect an adapter someone else gave you without reading it.

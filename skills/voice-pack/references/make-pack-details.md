# Making a pack: details the main path does not need

This file holds the detailed rules moved out of `references/make-pack.md`: the sections below are the moved text (one pointer in "Reference set and held-out recording" was changed to a file name), and a one-line pointer was left in the original place. It covers how fidelity is measured and reported, enhancers, loudness, the reference set and held-out recording, the details of releasing a new version, the pronunciation lexicon, the language of the skeleton, the full pack, and the share file. Making a new pack from an existing pack (the clean room and the duplicate check) is in `references/clean-room.md`. The three main paths (a designed voice, a recording the user supplies, dubbing a script with a pack) do not need to read it; read it when you need these details.

## Fidelity

**Fidelity**：Synthesize the text of the held-out recordings once with the pack you made (for each, use the default segment of its language as the reference, the same one used in dubbing when neither the caller nor the setup names a reference; the setup is not used, and the setup's `referenceTag` is not used either), then measure as described in "How to read this report" in the file header of `lib/fidelity.mjs`. Write the numbers in the report as they are; the score is computed by the rules there. An item that cannot be measured is reported as "cannot be measured", naming the missing capability. An item where the service had a temporary error is recorded as "not heard": state the count and "can be redone", and the whole job finishes as usual. If the model's provider blocked the answer (the capability throws `provider_blocked`), that blind listening is recorded as "voided"; the number of blocked ones is counted separately, they are not recorded as "not heard", and a redo does not redo them (asking again about the same recording is blocked again). If a recording has no speech that a voiceprint can be embedded in, that item's speaker similarity is recorded as "not measurable" (say whether it was the generated or the held-out segment); it does not enter the ratio and cannot be redone (reading rule 9). To redo, add `--save-evaluation <new directory>` when making the pack, and afterwards run `node cli.mjs fidelity <new directory>/evaluation.json --redo <new directory>/fidelity-report.json`; how many times to redo is already stated in the make-pack report (computed by `planRedo`), and when the adapter gave a cost notice, the redo `fidelity` command says it again on standard error before it starts. A redo does not change the verification record in the pack; to update it, release a new version. These are also recorded as voided and do not count in the ratio: a listening check that did not pass (`listening_check_failed`: the start of the answer does not match the known text; a different way of writing it does not count, the same as every listen in `make-pack.md`「Cue annotation」), an answer that is not in the fixed format (`blind_answer_invalid`), and an answer that did not end normally or is empty (`blind_answer_unusable`). A redo (the `fidelity` command above) redoes only the "not heard" ones; voided ones are not redone. A voided item has, in the report's `details`, which ask it was, which recording, and the error rate. When the trial synthesis (the first step above) has a temporary error, each held-out recording is tried at most 3 times; each try is one synthesis and may be charged again; `retried` in the report counts the extra tries. The verification record is written into the manifest: environment, model, date, ratio (when speaker similarity cannot be measured there is only blind listening, and no ratio).

## Enhancers

Enhancers are only guaranteed to fit the format. Making an enhancer needs a runtime environment that can fine-tune, which is not done here.

## Loudness

**Loudness**：The references and held-out recordings written into the pack are normalized to −20 LUFS with a sample peak no higher than −1 dBFS (the same number as the reference loudness in the clone flow; the rules and these two constants are in `tools/loudness-normalize.mjs`, and the usage is in the file header of `lib/make-pack-loudness.mjs`). When generating, each line picks a different reference; if the references differ a lot in loudness, the dubbed whole passage comes out with one line loud and the next quiet, so they are unified to one loudness. The quality check measures the original audio; what is adjusted is only the copy of the bytes put into the pack (stored as 16-bit WAV). For a segment where adding the gain would push the peak over the ceiling (the peak is 19 dB or more above the loudness, with one especially loud transient in the speech), by default a limiter first holds down the too-high peak and then the gain is added, by at most 6 dB, and each segment's `loudness.limitedDb` records how much was held down. A segment that still cannot reach the target after 6 dB (short by 0.5 LU or more) gets only the gain that can be added, and the report's `notes` has `loudness_target_not_reached`, stating where it ended up and how much was held down. Segments carried over from the previous version, external resources, and ones that cannot be decoded are left as they are, and the report records `loudness_skipped`. `--no-loudness` turns off the whole loudness adjustment, and the audio goes into the pack as it is; `--no-limiter` turns off only the limiter and goes back to adding gain only (a segment whose peak is too high cannot reach the target).

## Reference set and held-out recording

**Reference set and held-out recording**：There is only one copy of the rules, in the file header of `lib/pack-material.mjs`; a held-out recording is never used as a reference, and the numbers are starting values, not calibrated with real packs. The quality check uses the thresholds in `tools/` and gives only warnings (file header of `tools/audio-quality.mjs`): a segment with warnings still goes into the pack, is ranked after the ok ones when references are picked, and the report names the reason. Identical audio bytes are kept only once (`duplicate_audio`); when releasing a new version, the segments in the previous version were stored loudness-adjusted, and the same recording newly added is still recognized. `--default-segment <segment name>` states the default segment explicitly; it can be given for a new pack and for a new version, and once for each of several languages (one segment per language): the segment name is a segment in this round of materials (or a reference of the previous version), and it is not picked as a held-out recording (there is no limit we set on the number of reference segments, only the 500-item limit stated in the format; the rule and the reason are in that file header). For a language not named, the default segment is decided as in `make-pack.md`「Default segment and audition line」: a model that can listen to audio picks it, and if there is none or it did not pick one, rule 5 of `lib/pack-material.mjs` applies (the rule and the reason are in that file header and in the file header of `lib/make-pack-pick.mjs`; a segment marked synthetic is a candidate just like a real recording). Held-out recording: when fewer than 3 real recordings are usable, none is held out (a clone marked `synthetic` does not count as a real recording); otherwise hold out 20% of the number of real recordings (at least 1 segment, at most 6 segments, not more than the number of real recordings minus 1). Group by "language plus the reference tag given with the material" (tags are compared character by character; a name the model made up, a name made up from the segment name as a fallback, and a held-out recording from the previous version count as "no tag", and within one language they form one group). Take from the groups in turn, taking the segment that has no fewer than 10 words of text, can be handed to dubbing as it is (no script markup, no square-bracket cue, no parenthesized note, no line break), fits in one synthesis, and has the lowest priority; each group keeps at least one segment as a reference. A default segment the author stated explicitly is not held out; a segment cited by a setup's `referenceTag`, and a segment that is the only one in its language, is not held out either. `--no-holdout` holds out no recording: every usable segment goes into the reference set, the report does not give `no_holdout` or `holdouts_few`, and the plan has no trial synthesis. Add it when making a pack from a designed voice (see `make-pack.md`「Making a pack from a designed voice」). When releasing a new version, the held-out recordings already in the previous version are carried over as they were; to remove one, use `--drop`.

## Details of releasing a new version

The references and held-out recordings of the previous version keep their original roles, and newly added ones come after them. `--drop` removes segments you do not want, `--retag` changes the reference tag of a previous-version reference (`make-pack.md`「Change the tags」), and `--default-segment` changes the default segment (it changes for the language named; the other languages continue as before; see "Reference set and held-out recording" above). A segment name must not repeat one from the previous version, even a removed one: if `intro` was removed, the new version cannot use the name `intro` again.

The verification record is not carried over: this version is measured again, and if it could not be measured, there is none. If nothing changed, the command reports `make_pack_nothing_changed` and does not release a version. The pack records the base part version used when making it (`--base-version`, by default the version of this base part itself), and does not record the source pack.

## Pronunciation lexicon

**Pronunciation lexicon**：`--lexicon <file.pls>` takes a pronunciation lexicon in W3C PLS format. It replaces only words in the text to be spoken; script markup, cues, and angle-bracket tags stay as they are. There are two ways to write an entry: `<alias>` replaces the word to be read with another spelling (works for all adapters); `<phoneme>` marks phonemes and is used only when the synthesis model recognizes it (below). There are three phoneme alphabets (PLS requires a non-`ipa` alphabet to use a name starting with `x-`), written in `alphabet` on the root, or on an individual `<phoneme alphabet="…">`:

- `x-pinyin`, Chinese: the entry can only be Chinese characters, and `ph` is pinyin with a numeric tone. One syllable per character, lowercase, tone 1 to 5 (5 is the neutral tone and must be written), syllables separated by spaces, and the number of syllables equals the number of characters in the word (`银行` is written `yin2 hang2`). The ü in pinyin is written as `v` (`lü3` is written `lv3`).
- `x-arpabet`, English: the entry is one English word (it may contain an apostrophe or hyphen), and `ph` is CMU Arpabet: phonemes in uppercase with one space between them, and a stress digit after each vowel (0 unstressed, 1 primary stress, 2 secondary stress), none after consonants (`Zorbek` is written `Z AO1 R B IH0 K`).
- `x-romaji`, Japanese: the entry is one word or a short phrase written in kana or kanji, and `ph` is OpenJTalk-style romaji with pitch digits: a digit follows a letter, one after another, with no spaces (the vendor gave only one example, `橋が` is written `ha0shi1ga0`). Only the shape of the letters and digits is checked; whether the morae and pitch are written correctly is not checked.

Write entries as whole words. For characters that are not segmented into words, such as Chinese characters, the tool looks for them literally in the line, and writing a single character (for example "曾") also changes every word that contains this character; "曾经" and "不曾" will probably also be read as zēng (inference; nobody has listened to the result, `models/scene3.md`「Phoneme tags」). An entry of a single character is still used and is not blocked: when the lexicon has one at pack-making time, the report's notes (`notes`) have a `lexicon_single_character` entry; when it was used in a dub, the plan's notes also have one, and `details.terms` is those characters. English is looked up by whole word, and an entry of one letter replaces only that letter standing alone, and is not reported. Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<lexicon version="1.0" xmlns="http://www.w3.org/2005/01/pronunciation-lexicon" alphabet="x-pinyin" xml:lang="zh-CN">
  <lexeme><grapheme>曾小雨</grapheme><phoneme>zeng1 xiao3 yu3</phoneme></lexeme>
  <lexeme><grapheme>银行</grapheme><phoneme>yin2 hang2</phoneme></lexeme>
  <lexeme><grapheme>Zorbek</grapheme><phoneme alphabet="x-arpabet">Z AO1 R B IH0 K</phoneme></lexeme>
  <lexeme><grapheme>Mira</grapheme><alias>Meera</alias></lexeme>
</lexicon>
```

Whether phonemes are used, and how they are written into the text to be spoken, depends on what the environment declares. Which environments declare it, on which capabilities it works, and the range that was not tested are in the notes of the adapter in use:

- `phoneme-markers` declared (the synthesis model recognizes phoneme tags): all three alphabets are accepted, and `dub` replaces the word with phoneme tags (`<|phoneme_start|>…<|phoneme_end|>`; for pinyin one tag per syllable, for the others one tag per entry). When a scene is one request, every round is replaced too, and you can see it in the plan's `spoken`. A phoneme tag handles readings that the context cannot guess (names, rare words). When the marked reading conflicts with a common word in the context, the model may read it as the common word (transcription, judged by the model, nobody has checked it; see the model notes of that model in `models/`).
- Only `phoneme-in-text` declared: only `x-pinyin` is accepted, and the whole line that uses a phoneme is written as SSML before it is sent (a `<phoneme>` wrapped in `<speak>`).
- Neither declared: phonemes are always reported in `lexicon.unapplied` (`reason` is `phoneme`), the same as when there was no pinyin entry.

If the environment accepts the alphabet but the writing does not fit, `phoneme_format` is reported (`problem` is `term`, `count`, or `form`); an alphabet it does not accept (for example `ipa`, or `x-arpabet` and `x-romaji` when only `phoneme-in-text` is declared) is reported as `phoneme`.

**Phoneme tag characters are billed as well.** The tags are written into the text that is sent, and a service that bills by character count counts the tags too: one pinyin tag, with just its two ends (`<|phoneme_start|>`, `<|phoneme_end|>`), is 32 characters, and pinyin is still one tag per syllable. Measured: for a short sentence of 10 characters, after the name was written as three pinyin tags, 116 characters were sent, and one call cost more than 11 times the one without them (0.01624 dollars against 0.0014 dollars; the readings are in the model notes of that model in `models/`, "Phoneme tags"). So write phonemes only for words that would really be misread and that the context cannot guess; if a word appears often in the script, first look at how long `spoken` is with `dub --dry-run`.

**Entries that changed pronunciation with a homophone `<alias>`** (for example `<lexeme><grapheme>曾小雨</grapheme><alias>增小雨</alias></lexeme>`) can be rewritten as phonemes in an environment that declares `phoneme-markers`: leave the entry alone, replace `<alias>` with `<phoneme>`, and write the pinyin for every character of the entry (`<phoneme>zeng1 xiao3 yu3</phoneme>`; if the `alphabet` on the root is not `x-pinyin`, write `alphabet="x-pinyin"` on this `<phoneme>`), then release a new version with `--previous <previous version> --lexicon <new file.pls>` (changing the file inside an installed pack directly does not take effect, see `make-pack.md`). Think about three things before changing: the characters of the tags are charged too (above); if you change a common word to be read as a different sound, and the transcription shows the tag was not changed over, so the model read it as the common word (judged by the model, nobody has checked it, same as above), keep the alias for such a word and do not replace it with a phoneme; in an environment that does not accept phonemes the phoneme is not used, and the word is read as the original characters again.

## Language of the skeleton

**Language of the skeleton**：The skeleton of `SKILL.md` in the pack that is made (the titles and notes of each section) is Chinese by default; to make an English pack for an English author, add `--text-language en` (only the two values `zh` and `en`; any other is a usage error, exit 2). It governs only the skeleton: the line "## 配音指引" (dubbing guidance) is the same for every language, and the text written in `--name`, `--guidance`, and `--direction` is put into the pack as it is, not translated; for a pack in any language, the guidance read back is the same. A new version uses the language given this time, and does not look at what language the previous version was. The authoritative copy of the rule is `protocol/FORMAT.md`「Language of the skeleton」.

## Full pack

**Full pack**：If `--base <base part directory>` is given, it is put into `voice-pack/`; if not, there is only the role part (carrying the protocol core `protocol/`). Resources are put into the pack by default, and a segment is recorded as an external resource only when it has `externalUrl` written (the manifest then has only the URL, size, and hash). The details of enhancers are in `references/make-pack-details.md`「Enhancers」.

## Share file

**Share file**：Add `--share-file <share file>` when making the pack, and after the pack is written, a `.voicepack.zip` is made as well, carrying a preview card (`index.html`). The two entries on the card, "Open in X" and "Make one of your own", are supplied by the adapter connected in (provided by the product behind the adapter); the command does not make links itself, and if no adapter supplies them, the card has no entries. This step does not verify signatures; run `check` before distributing.

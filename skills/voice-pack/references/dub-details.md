# Dubbing and changing a voice with a pack: details the main path does not need

This file is moved out of `references/dub.md`: the sections below are details the main path does not need, and a one-line pointer was left in the original place. The main paths (dubbing a script, a scene with several characters, producing the finished product) read the matching section only in these cases: there is a pronunciation lexicon, there are enhancers, segments merged into one request, speed change or silence at a speaker change ("Stitching details"), or a failure to redo ("Failure and redo details"). Changing a voice, singing, and your own adapter are not on these paths; read them when you need to look them up.

## Pronunciation lexicon

4. **Pronunciation lexicon**：`lexicon.pls` in the root of the pack (W3C Pronunciation Lexicon, PLS); how to write it is in `make-pack-details.md`「Pronunciation lexicon」. It replaces only words in the text to be spoken; script markup, square-bracket cues, and angle-bracket tags stay as they are (words inside a cue are not replaced and phonemes are not marked into a cue; tag names and the phonemes inside phoneme tags are not replaced, while the text wrapped by a paired tag is still replaced, see `references/markup.md`「Angle-bracket tags」). `<alias>` is applied as written. If several entries match the same position, the longer one wins; the whole passage is replaced in one pass, and the text that comes out of a replacement is not looked up in the lexicon again. Whether `<phoneme>` is used depends on what the environment declares:
   - `phoneme-markers` declared: pinyin (`x-pinyin`), Arpabet (`x-arpabet`), and Japanese romaji (`x-romaji`) entries that are written correctly are replaced by phoneme tags in the same pass as `<alias>` (for pinyin one tag per syllable, for the others one tag per entry), not escaped; the plan's `spoken` shows what is sent. When a scene is one request, each round is replaced according to the pack of its speaker. The ones used are recorded in the report's `lexicon.phonemes` and removed from `unapplied`.
   - Only `phoneme-in-text` declared: only pinyin is used, and it is written as SSML before sending. The ones used in a line are recorded in `lexicon.phonemes` and in that line's `phonemes`, and removed from `unapplied`. A line that uses a pinyin phoneme is converted whole into `<speak>`, and the angle-bracket tags in the line are also escaped and never reach the model: for the exception to this, see `references/markup.md`「Angle-bracket tags」. When a scene is one request, no phonemes are marked.
   - Ones not used, and ones whose alphabet the environment does not accept, are reported in `lexicon.unapplied` (`reason` is `phoneme`); when the environment declares nothing, phonemes are always `reason: phoneme`; when the environment accepts the alphabet but the writing does not fit, it is `reason: phoneme_format` (`problem` is `term`, `count`, or `form`).
   - When an entry of a single character was used this time (a character that is looked up literally, such as a Chinese character, for example "曾"), the plan's notes have a `lexicon_single_character` entry, and `details.terms` is those characters (with several packs, there is one entry per pack, the note names the pack at its start, and `details.pack` is the pack ID): every word containing this character was replaced accordingly, and probably read accordingly too (inference; nobody has listened to the result, `models/scene3.md`「Phoneme tags」). It is replaced anyway and not blocked; if you only want to change one name, write the entry as the whole word.

   `lexicon.pls` is read only if the manifest's `files` lists it: if this file in an installed pack was changed directly and the manifest does not list it, it is treated as no lexicon, and `applied` and `unapplied` in the report are both empty. To change a reading, release a new version; for how, see `make-pack.md`.

## Enhancers

6. **Enhancers**：An enhancer in the pack that serves `voice-cloning` is handed to the capability. If the environment knows the corresponding model it is used (the report's `enhancers.used`); if not, generation goes on as usual, `enhancers.statement` is `enhancers_not_used`, and the pack's verification record is attached, so that people know how much worse the result will be in the current environment.

## Stitching details

- Each line's `pauseBeforeMs` hangs at the start of the line and `pauseAfterMs` at the end; each inserts silence in milliseconds, with no cap, as long as it is (a long pause that did not fit in the request and was cut there is put back this way; the default pause that `dub` records at a cut it made itself, where the script wrote no pause, is the same; see `references/dub.md`「How long text is split」›「Breath pause at the cut.」).
- A `joined` segment (several lines of one passage merged into one request, with the short pauses between them written into the text in the measured form; or several lines shorter than the minimum character count merged together) is one piece of audio: the pauses in it are already in the audio, no silence is inserted, and only `pauseBeforeMs` and `pauseAfterMs` at its head and tail are looked at. Each line's cues go with its own words, in the text of the request. For the part merged in a dry run, `pick.directions` lists each member's stage direction.
- When `speed` is not null (a speed given by the caller or the setup that `dub` did not apply: when synthesizing, the environment had no ffmpeg, and `speedChange.speed` is null), the one who stitches changes the speed: the synthesis capability does not accept a speed. `speed` being null means there is no speed requirement (it is not 1.0), or `dub` has already changed it (`speedChange` gives the lengths before and after), and the one who stitches does not change it again; slowing down or speeding up written in the script is a cue, handed to the model, and is not handled here. The upper and lower limits of the speed change are `SPEED_LIMITS` in `lib/mix.mjs` (the same place as `dub`'s target duration and speed); beyond them it changes to the nearest end. For a segment with `targetDuration`, `dub` has already changed the speed to the target duration, `speed` is null, and the one who stitches does not change it again.
- A segment that is one request for a scene (it has `scene`, and the audio file is `<index>-scene.<extension>`): one request, one audio, the gaps between the rounds inside are decided by the model, and the one who stitches does not touch them; its head is the pack of the first speaker (`pack`), its tail is the pack of the last speaker (`lastSpeakerPack`), and `pauseBeforeMs` and `pauseAfterMs` are those at the head and tail of the scene. There is no separate audio for each line (if you want it, use `--no-scene` when dubbing).
- **Silence at speaker changes** (done by `mix`): when the previous line's `lastSpeakerPack` (its own `pack` if there is none) and the next line's `pack` differ (the speaker changed), the silence at the end of the previous line and at the start of the next line are each trimmed to 50 milliseconds, and then the pause marked at that spot is inserted, or about 100 milliseconds if none is marked. Without trimming, the silences at the head and tail of the synthesized lines add up, the pause at a speaker change would be long, longer than the gap at a speaker change in most conversations (inference: speaker changes have not been measured, and there is no source; the measured silence at the head and tail of a block is 90 to 170 milliseconds on each side, see `references/dub.md`「Breath pause at the cut.」). It does not trim when the same pack goes on speaking; it does not trim a line whose whole length is below -40 dBFS (measured every 10 milliseconds), and the report records a `silent_unit`.

## Failure and redo details

When the platform says a scene does not fit in one request (`details.problem` is `too_long_for_one_request`, also recorded as `failed`, and not marked as a temporary error): it is not split automatically and not resent, and redoing the same scene still does not fit; the `scene_too_long` note in `notes` says which scene, and you either add a chapter marker (`# Title`) in the middle of that scene to cut it into two scenes, or use `--no-scene` for one request per line. Wherever people are told to add a chapter marker (the two cases of not fitting here, the `mix` message, `scene_too_long` and `speech_maybe_unfinished` in `notes`), the same sentence also gives the two things to watch when adding a title (`references/dub.md`「How long text is split」›「A piece cannot hear the previous one.」): if what follows the title is not spoken by the first pack, rewrite `[voice:Name]` at the start of the line after the title, and without it the voice goes back to the first pack; to take a breath, write `[pause 0.5s]` at the start of the line after the title. In the text output it is listed on its own as "does not fit", it is not in the redo command, and no `--only` command is given for it: the indexes change after the split, so after fixing, run again without `--only` (the finished ones are reused). A one-request job that is not a scene can also be reported this way (`voice-cloning` can also be marked `too_long_for_one_request`, the convention is in the `voice-cloning` section of `vocab/capability-signatures.md`; this happens when one person speaking and a scene use the same model): it does not count as "does not fit", `--no-scene` does not help with it, it is listed with the ones whose text was rejected (see below), an `--only` command is given, and the reason is written on a separate line below: shorten this line and redo it with that command; if it must be cut into two requests, the indexes change after the cut, so after fixing, run again without `--only`. The two ways of cutting cost differently: if you start a new line in the middle and write a chapter marker, only that chapter is cut again, the finished ones of the other chapters are reused, and no money is spent twice; if you lower `--max-chars`, the whole script is cut again by the new number, every request longer than the new number is cut, and the finished ones whose cut changed must be dubbed again and charged again. Not fitting, whether for a scene or for a line, concerns only the length of that piece, and it is not counted in the number below where the provider rejects 3 lines in a row (if the first few lines all do not fit, dubbing still goes on and is not described as the reference being blocked). When `mix` produces no finished product, it speaks with the same division: for a scene that does not fit and for ones shorter than the minimum character count it gives no `--only`, and says first how to change the script, and to run again without `--only` after the change; for ones whose text was rejected (including a line that does not fit even alone) it says to change the words first (shorten), then gives `--only`; only for ones that can simply be redone as they are does it give `--only` directly. When several kinds exist at the same time, the output of `dub` and the message of `mix` give only one redo command (exception: `speech_maybe_unfinished` in `notes` still gives a separate `--only` that points at that line; when some text was rejected, do not run it alone, and merge that line's number into the command in the "text rejected" part and redo them together): running either one runs only half, and the rejected lines and the scene that does not fit that `--only` did not point at are recorded as not done this time (`skipped`), the reason is lost from `dub.json`, and `mix` again tells people to redo as they are. So when ones with rejected text and ones that can just be redone as they are exist at the same time, change the words first, then redo both with one `--only` (in the output of `dub` this command is in the "text rejected" part, and the "temporary service error" line does not give another); when there are lines shorter than the minimum character count or a scene that does not fit, give no `--only` at all, run again without `--only` after the fix, and the others that did not succeed are redone together in that run. A line that the service has already finished and only the result was not retrieved (the adapter marked `details.unretrieved` on the error, the convention is in `vocab/capability-signatures.md`「General conventions」) is also recorded as `failed`, but it is not a temporary error: the output lists it on its own as "not retrieved", says how to retrieve it according to the adapter's `details.retrieve` (leads such as what to retrieve with and the task number), and does not put it in the redo command. Running the same command again, or pointing at it with `--only`, dubs it again and charges again; if you do not want to dub it again, retrieve it by hand as `details.retrieve` says; for audio that can be retrieved by hand there is for now no way to hand it back into the output directory for `mix` to use (to produce a finished product you can only dub it again). The `mix` message also does not tell people to redo it with `--only`, and says the same two ways. When you redo other lines with the `--only` command from the output, a not-retrieved line that was not pointed at stays recorded as not retrieved (`failed`, and `error` together with `details.retrieve` as in the last run; it counts only for the same request, recognized as in reuse), and is not recorded as `skipped`, so the retrieval lead stays in `dub.json`, and `mix` will not tell people to dub it again with `--only`; `--dry-run` with the same `--out` marks it the same way. In this case, running that `--only` command again as it is does not dub it again, but it dubs the lines it points at once more and charges once more, so the "not retrieved" part of that run's output says "point at it with `--only`, or remove `--only` and run this command", and what `mix` says is to run again the `dub` command for the whole script. For lines still recorded that way, `seed` and `seedChange` are as in the last run, and `--only` on them goes on adding from there. The redo command printed in the output carries this run's adapter (`--adapter`, `--adapter-option`) and the tags, setup, target duration, `--max-chars`, and `--concurrency`; just run it again as it is. A line whose text was rejected (`details.textRejected`, which concerns only the text of this line, and changing the line fixes it) is also recorded as `failed`, only for this line, the others are done as usual, and it is not retried, because only a different line will give a different result: it is not in the redo command of "temporary service error", the text output lists a separate part "text rejected" with each line's error code and reason, and gives another `--only` command that points at these lines (when there are temporary service errors, they go in the same command: when several kinds exist at once only one redo command is given, see above). First change the words of these lines in the script, then run that command; if you only run it again as it is, it is still rejected. Ones detected before the call (blank text, too long, characters that cannot be handled, error code `capability_input_invalid`) and ones the platform says do not fit in one request (above) are not counted; when the provider rejects 3 lines in a row and not one has succeeded, it stops like any other error (error code `dub_text_rejected`, and `details.rejected` of `stoppedBy` states the rejected lines): in this case it is mostly the reference or some other input that was blocked, every line will be rejected this way, and stopping avoids wasting money. Redoing as it is will still be rejected at that point: first switch to another reference (`--reference-tag` with another reference tag) or change or remove the opening cue (`--emotion`, `--style`, `--energy`; for what the setup wrote, use another `--setup` or `--no-setup`), and if it is still rejected after the change, it is mostly the words of the rejected lines, so change the words; after handling it, run the command that stopped again, with the other options as before. To change the reference, change only `--reference-tag`: if it carried `--only`, it still carries it, and only the lines pointed at are dubbed again (those not pointed at do not compare reference segments and are reused as before). The lines finished in this run before the stop (`ok`, no `carriedOver`: already sent when `dub` stopped and later succeeded) are also pointed at, and will be dubbed again with the new reference and charged again; to keep them, remove them from `--only`. Changing the opening cue is different: `--emotion`, `--style`, `--energy`, and what the setup wrote change the cue at the start of every line, and reuse requires the opening cue to be the same; if you run again still carrying `--only`, the lines not pointed at do not match the last run and are recorded as not done this time (`skipped`), and `mix` still cannot produce a finished product. So there are two ways: to change only the lines that were not done well, use a `.json` script and write the new values on these items' own `labels`, keep `--emotion` and the like, `--setup`, and `--only` in the command as before, only that the lines finished in this run before the stop do not get a new value written, and must be removed from `--only` (if kept, they would be dubbed again with the original cue and reference, and charged again), and the finished ones are reused and cost nothing (see "Changing only the opening cue of a few lines" below); or change the whole script, running again without `--only`, and every line is dubbed again with the new opening cue (with `--only` removed, the `--reference-tag` in that command that was meant only for those lines is also applied to the whole script; if you want only those lines to use it, split the script into several parts, run `dub` once for each, and join them in order with `mix`: within one `dub` run a pack uses only one reference tag). The `mix` message names which lines were finished in this run before the stop. Without `--only`, if the reference or the opening cue was changed, the lines already finished whose reference segment or opening cue changed must also be dubbed again and charged again (reuse recognizes only the same request). For other errors (401, wrong parameters, missing capability, missing runtime, ...) it stops directly and does not start new lines, and the files already finished and a `dub.json` that has `stoppedBy` written in it are kept: running it again as it is will mostly stop the same way, so first handle the reason it stopped, then run the command that stopped again, with `--only` carried if it was carried (if removed, the `--reference-tag` in that command meant only for those lines applies to the whole script, and the finished lines whose request changed must also be dubbed again and charged again. Only the reference is like this: emotion, style, and energy change the cue at the start of every line, and with `--only` the lines not pointed at cannot be reused either). Without `--only`, the finished ones are reused; with `--only`, the ones pointed at are always dubbed again, and the lines finished in this run before the stop (`ok`, no `carriedOver`) are reused only if removed from `--only` before running, and so are interrupted ones (`dub_unfinished`). Lines that did not start after the stop are not in `dub.json`, and `--only` cannot point at them all, so when `mix` meets a stop it also gives no new `--only`; it says in this way what to handle first, points to the explanation of when `dub` stopped (`stoppedBy`), and names the lines finished in this run before the stop; lines that were not done before the stop and will not be done by running again as they are (those whose text was rejected, those shorter than the minimum character count, those that do not fit) are also named, with the advice to change them before running again, and `details.failed` lists them: otherwise, if you run again as told, they are sent once more, rejected once more, and another round is needed. A line where synthesis succeeded (and was charged) and a step after synthesis (checking whether it was read to the end, the script's `audio` hook in the pack, the target duration, the speed) failed and stopped is kept too: the file is the piece as the model produced it, it is `ok` in `dub.json`, and `afterSynthesisFailed: { step }` is also recorded, where `step` is the step that failed: `speech-length`, `audio-hook`, `target-duration`, `speed`. It does not count as done: running the same command again does not reuse it, it is dubbed again and charged again, and those steps are done again with this run's environment. A 401 means the authorization has a problem: first have the user handle it, then go on (sending the same line again is still 401).

**Changing only the opening cue of a few lines**（`--only` redubs a few lines, giving them another emotion, style, energy, or speed, while other lines are reused as before; the message of `mix` stopping at `dub_text_rejected` points here）：`--emotion`, `--style`, `--energy`, and these items written in the setup change the cue at the start of every line; `--speed` and the speed written in the setup change the speed of every line: it is the same with `--only`, and lines not pointed at do not match the last run and are recorded as not done this time (`skipped`). To change only a few lines, use a `.json` script (the part about the script in the file header of `cli/commands/dub.mjs`): write these items on their own `labels` (like `{ "emotion": "…" }`; for speed write `speed`, and for the original speed write `1`); an item's own value overrides the same item from the command line and the setup, and they are not merged; to remove an item that the setup wrote, you can only replace the whole setup. `--emotion` and the like, `--speed`, `--setup`, and `--only` in the command stay as before. To turn a `.txt` script into `.json`: each item is one passage of the original script, written as a string, or `{ "text": "…", "labels": { "emotion": "…" } }` (to change speed, `{ "text": "…", "speed": 0.9 }`), and not one character of the words is changed. A boundary between items counts as a chapter change and they are not merged into one request (an item shorter than `limits.minChars` is the exception, and is merged into the next as before, see `references/dub.md`「One request per passage」›「Ones shorter than the minimum are still merged.」), so split only where `dub.json` already had two lines: the lines whose opening cue is to be changed are each their own item, and other chapters can stay in one item, with chapter titles written as they were. If what follows at the start of an item is not spoken by the first pack, rewrite `[voice:Name]`, and without it the voice goes back to the first pack; where the split is and `dub` had recorded a default pause (`cutPause`), none is added between items, and to take a breath write `[pause 0.5s]` at the start of the later item. If it was split correctly, the words to be read, the pack, the opening cue, and the speed of the other lines are all unchanged, and they are reused as before; before spending money, add `--dry-run` with the same `--out` and look at the plan once: the ones not pointed at should be marked `ok` and `carriedOver`.

## Changing a voice and singing

**Changing a voice and singing**：`node cli.mjs convert <pack directory> <audio file> --out <file>`; `--singing` is singing (the input must be a vocal stem, without accompaniment). Speech uses `voice-conversion` and singing uses `singing-voice-conversion`; if one is missing, only this command reports `capability_missing` and names the missing one, and dubbing goes on as usual. Which reference segment to use is the same as in dubbing (`references/dub.md`「How a line becomes synthesis」step 3), except that a setup cannot be named: if the pack has a setup with `default`, that one is always used (its `referenceTag` and `labels.language`), and there is no `--setup` or `--no-setup` (giving them is a usage error). `--reference-tag <tag>` overrides the setup's default reference; it is given only once, and the whole string is the tag; `--language` is this line's language and overrides the setup's (voice conversion has no lines to recognize it from; how it is decided when not given is in the file header of `lib/convert.mjs`). If the pack does not have the tag, it reports `reference_tag_unknown`, calls no capability, gives no cost notice, and writes no file. Voice conversion has no options for emotion, style, or energy (giving them is a usage error). The returned `pick` is written the same as dubbing's `units[i].pick`; the reference text handed to the model is the same as dubbing: if the reference segment has a cue annotation (`annotatedText`) it is handed over, and if not the verbatim transcript is handed over. If the output file already exists it is refused and not overwritten, and the refusal comes before any money is spent; when the adapter connected in gave a cost notice, after everything that should be checked has been checked (the capability, the runtime the script needs, which reference segment is used) and before the voice is changed, it states on standard error which capability will be called once (not stated with `--json`). A script registered under the `convert` feature name handles the audio after the voice change; enhancers are used as in dubbing.

## Your own adapter

Which capabilities the current runtime environment has is in the notes of the adapter connected in. To use another model, write an adapter yourself and hand it to the command with `--adapter <directory or module file>`: an adapter is a function that returns an object (capabilities, runtimes, network reads, cost notices, and so on; every key is optional; how to write it is in `adapters/README.md`「Shape of the return value」); what is given later overrides what is given earlier, and also overrides an item of the same name the command already has. The convention is written only in `adapters/README.md`, and the call parameters and return value of each capability are in `vocab/capability-signatures.md`. The adapter runs directly in this process, not isolated, the same as the scripts in a pack.

# Dubbing and changing a voice with a pack

This is a reference for the base part; section 6 of `SKILL.md` points here. The flow (when to use which command) is in `SKILL.md`; the command syntax, options, report, redo after a failure, and the rules for scripts and stitching are here.

You are given a voice pack (the role part's directory, with `manifest.json`, `SKILL.md` and `reference/` in it). Install it into the environment first, then dub a script with its voice, or change an audio clip into its voice. These commands (`install`, `dub`, `convert`, and `mix` for stitching) are all in `cli.mjs` at the base part's root (one level above `references/`). None of them names a model; they only need the runtime environment to have the matching required capability (`install` and `mix` call no capability).

**Install into the environment**：`node cli.mjs install <pack directory or share file>`. It first runs the same checks as `check` (the manifest matches the files, mutual verification, and signature verification: the base part and the protocol core must carry the official signature) and writes only if they pass. It writes into the project's `.agents/skills/<pack ID>/` (read by Codex, Gemini CLI, Cursor, OpenCode), then copies it to `.claude/skills/<pack ID>/` (read by Claude Code). If a directory of the same name already exists it refuses and does not overwrite. `--project <directory>` sets the project; the default is the current directory. If a check fails (including a wrong signature), no file is written; the report names what is wrong; tell the user as it is and let the user decide the next step (if signature verification fails, nothing guarantees where the pack came from, and only the user can decide whether to trust it). If the base part or the protocol core has no official signature (a development copy you sealed yourself), add `--allow-unsigned` to install: the parts without a signature are not verified, and the output says they were not verified and that this is not an official version; a signature that is present but wrong is still refused even with the flag.

**Dub a passage**：`node cli.mjs dub <pack directory> <script file> --out <output directory>` (for a scene with several roles, give `--pack <pack directory>` several times, see the table below). The script is text with script markup (`SKILL.md` section 4; for the syntax see `references/markup.md`), or a `.json` array `[{ "text": "…", "labels": { "emotion": "angry" }, "speed": 0.9, "expressiveness": 70, "targetDurationMs": 2700 }]` (an item's own labels, speed and expressiveness override what is given on the command line and also override the setup's, see "Opening cue and speed" below); `-` is standard input. Add `--dry-run` first to see the plan: it only plans, does not synthesize, costs nothing. Old packs of protocol 1.x and 2.x (reference segments in the old format) are not read by this version: `dub` and `convert` stop as soon as they open the pack and report `pack_protocol_old` (`details.protocol` is the protocol version the pack declares), without calling any capability; dub an old pack with the program of its own major version: a full pack with the base part it brings, a pack with only the role part with the base part of that major version (a 2.x pack with the 2.x base part, `protocol/FORMAT.md` section 14「2.x packs」).

| Option | What it does |
|---|---|
| `--pack <pack directory>` | Several roles: can be given several times, in place of the positional pack directory (once `--pack` is given, only the script goes in the positional slot). The first pack is the voice at the start of the script; `[voice:name]` takes a pack name or pack ID and switches to that pack from that line on. Each line's reference segment is picked from its own pack, and short lines are merged only within the same pack. Each unit in `dub.json` records its pack ID, and the top-level `packs` lists all the packs; with one pack it is the same as before |
| `--dry-run` | Plan only: what each line says, which reference segment is picked and why, what the pronunciation lexicon changed, which setup of the pack is used, which runtime is missing. Lines `--only` did not name are marked `skipped`; with `--out` given, lines that can be carried over (see "Failure and redo" below) are marked `ok`, `carriedOver`, and the text output says "沿用上一次的……不再合成" ("carrying over the previous run's …, not synthesizing again"); lines the previous run did not retrieve and this run does not name (only if it is the same request, recognized the same way as carrying over) are still marked `failed` (not retrieved): the lines whose `status` in the plan is `planned` are the ones that will be synthesized this time and cost money. The first line of the text output is a summary: how many characters will be spoken (counted as in "Two ways of counting characters" under "How long text is split"), how many requests (one request per scene counts as one; lines too short to send a request count in neither characters nor requests), how many will be synthesized this time (written only when it differs from the number of requests), which model (`models` in the adapter's return; if it did not say, write "适配器没说用哪个模型" ("the adapter did not say which model")); it does not estimate how long it will take. When long text is split into several requests, tell the user so first (`scenes/narration.md` step 6). The `--json` output has no such line. Nothing in the output directory is touched |
| `--language`, `--emotion`, `--style`, `--energy` | Labels given by the caller, applied to every line and overriding the same item in the setup. The language is used to pick the reference (see step 3 below): the whole script is picked by it, and a whole line in another language also uses a reference of this language, which is cross-language cloning; if the text visibly is not in this language (English lines given `--language zh`), `dub` still stops (step 3 "No accent by default"); emotion, style and energy do not affect which reference segment is used; they are combined into one cue written at the start of each request (see "Opening cue and speed" below). `--energy` takes only `low`, `medium`, `high`; anything else reports `pick_input_invalid` |
| `--instructions` (removed) | `dub` no longer sends instructions to the model: `--instructions`, `instructions` on a `.json` item, and `options.instructions` in the library all report `dub_input_invalid` when given, and `--dry-run` reports it too (see "Opening cue and speed" below). For the manner of speaking you want, write a concrete cue in the script, at the place where it happens |
| `--speed <factor>` | Speed given by the caller (a positive number; 1 is unchanged, 0.85 slower, 1.15 faster), overriding the setup's: the speed is changed after synthesis (see "Opening cue and speed" below) |
| `--expressiveness <0 to 100>` | Expressiveness, a control parameter of the model (larger means more drama, smaller means flatter; for the scale see `vocab/capability-signatures.md`), passed to every synthesis request. Order of precedence: the item's own `expressiveness` in a `.json` script → this option → the `expressiveness` of the setup used for this line → the pack's global value (top-level `expressiveness` in the manifest); `--no-setup` does not use the setup's value, the global value is still used; if none is given it is not passed, and `dub` has no default of its own. If the pack gives a value (the setup's or the global one), by default do not give this option; give it only with a reason, moving about 10 from the pack's value; if the pack gives nothing, give one by default (`models/scene3.md`「How to choose the value」), and without it nothing is passed. For how much to give, see `models/scene3.md`「Expressiveness」 (and "Expressiveness" in "Opening cue and speed" below); it overrides the pack's value on every line; for what to do when some voices are fixed and some are not, or when several voices have different values, see `models/scene3.md`「How to choose the value」 |
| `--setup <name>` | Which setup of the pack to use (`setups` in the manifest: the author writes fixed values such as emotion, style and speed into the pack, plus a note for the script writer that is not sent to the model, and each setup has a name). The values fixed in the setup fill in the items the caller did not give (for how this takes effect see "Opening cue and speed" below); if the script itself writes a cue at the start of a passage, that passage follows the script. If not given, the setup marked `default` is used, and if there is none, no setup is used; a name that matches nothing reports `setup_unknown` and lists which setups the pack has (the output of `--dry-run` and `pack.setups` in the plan list them too). With several packs, each pack looks in its own setups: `--setup <name>` looks for that name in every pack; `--setup <pack>=<name>` (pack name or pack ID, case-insensitive, written the same way as the pack reference in `[voice:]` in the script) picks the setup of one pack, can be given several times, and packs not named use their own default setup; the two forms are not mixed; when a setup's name contains `=`, write it as `<pack>=<name>` (the name is everything after the first `=`). If not given, each pack uses its own default setup. `--dry-run` and `pack.setup` in `dub.json` (`packs[i].setup` with several packs) state which one was used |
| `--no-setup` | Use no setup for any pack this time, not even the one marked `default`: the reference is picked by `--reference-tag` and the default segment of this line's language; language, emotion, style, energy and speed are only what the caller gave (expressiveness does not use the setup's either, but the pack's global value is still used, see the `--expressiveness` row). Use it when you want the voice itself, for example to dub a passage in another language with this pack to make a reference (`references/character-voice.md`「Add a reference segment in this language」). Not given together with `--setup` (usage error). The output of `--dry-run` states that this time it is `--no-setup`, and there is no `pack.setup` in the plan or in `dub.json` (`pack.setups` still lists which setups the pack has). The redo command after a failure writes it back as it was |
| `--reference-tag <tag>` | Which reference tag's reference to use in the pack (the pack's `SKILL.md` lists the tags by language): it overrides the default reference written in the setup (the setup's `referenceTag`), and each line takes from the segments with this tag by language (see step 3 below). Use it when the user wants to change the reference, when you pick one according to the script and the situation, and when the user hears the voice has drifted and wants to change it; if not given, the default reference written in the setup is used, and if there is none, the default segment of this line's language. Tags are compared character for character; a tag the pack does not have reports `reference_tag_unknown` (`details` is `{ referenceTag, pack: { id, name }, tags }`, and `tags` lists by language which tags the pack has), reported at planning time, also by `--dry-run`, and no capability is called. With several packs: `--reference-tag <tag>` without a pack name is given only once and every pack uses it, so every pack must have this tag; `--reference-tag <pack>=<tag>` (pack name or pack ID, case-insensitive) picks one pack, can be given several times, one pack is picked only once, and packs not picked take from the setup and the default segment; the two forms are not mixed. The part left of `=` counts as a pack pick only if it is the name or ID of one of the packs given this time; otherwise the whole string is the tag (a tag can contain `=`). The redo command after a failure writes it back as it was. Within one `dub`, one pack uses only one tag, and `dub` does not accept the same pack twice: to change the tag in the middle of a script, split the script in two at the place of the change, give each of the two `dub` runs its own `--reference-tag`, then use `mix` to join the two output directories in order into one file (see "Stitching" below); `mix` adds no extra pause at the split, and if you want a breath, write `[pause 0.5s]` at the start of the second script |
| `--target-duration-ms <milliseconds>` | For a line that has to fit a picture: how many milliseconds the dubbed audio must take; the speed is changed after synthesis to match it (see "Target duration" below). It is given per item: a `.txt` script is one item for the whole script; in a `.json` script an item writes `"targetDurationMs"` itself, which overrides this option |
| `--min-similarity <number>` | Threshold for speaker similarity: when the environment has `speaker-verification`, lines below it are flagged (see "Comparing timbre" below). If not given, the numbers are only reported and nothing is flagged |
| `--only 2,5` | Redo only these lines (numbering starts at 1): the ones named are always synthesized again, even if nothing changed (use it to get another take of one line; where the environment accepts `seed`, a line that succeeded last time gets a different `seed`, see "Failure and redo" below); the ones not named carry over what was made last time (see "Failure and redo" below) |
| `--max-chars`, `--concurrency` | The most characters one request sends out (including the opening cue; when it does not fit, it is split only at boundaries, see "How long text is split" below). Usually not needed: if not given, a request is about 1000 spoken characters by default, and if the adapter declares `limits.maxChars`, what is sent does not exceed it either; if given, it splits only by the given number, and the adapter's limit is no longer considered. `--max-chars` counts the characters sent out (cues, tags, the cue added at the start, every whitespace all count), which is not the same way of counting as the default of about 1000 spoken characters: for a script with many cues and tags, `--max-chars 1000` splits finer than the default. `--max-chars` is not less than 10. `--concurrency` is the number of concurrent requests, 1 to 8, default 2. Values outside these ranges report `dub_input_invalid` |
| `--no-scene` | Explicitly separate: do not dub one request per scene (see "One request per scene" below); one request and one file per line, and lines of the same voice that continue are not merged either (sentences within one line are still one request). If a line has a long pause that does not fit in a request, or a line by itself does not fit in one request, it is still cut there (below, "One request per passage" and "How long text is split"), and that line becomes several files. Use it when you need one file per line, to redo only one line, or to line up timing by line. Exception: when the adapter declares the minimum number of characters per request (`limits.minChars`), a line shorter than it is still merged into the next line (without merging it cannot be synthesized; it also merges across chapters and across items, for the conditions see "Ones shorter than the minimum are still merged" under "One request per passage" below), and those two lines are one file. Between lines, the pauses are as the script wrote them; `dub` adds no default pause (below, "Breath pause at the cut" under "How long text is split") |
| `--allow-cross-language` | Dub even if the reference segment used is not in the language of this line (cross-language cloning, which often carries the accent of the reference's language). If not given, `dub` stops such a line before spending money and reports `dub_cross_language` (see step 3 "No accent by default" below). Give it when the reference is in another language (write the lines in the target language and write the accent you want to hear in square brackets, `references/character-voice.md`「Language and accent」). The redo command after a failure writes it back as it was |
| `--no-language-marks` | For a cross-language line, do not require the name pair at the start and do not add the language cues on both sides; send the script as written (use it when you want the accent of the reference's language, `models/scene3.md`「Cross-language and accent」). The redo command after a failure writes it back as it was |
| `--adapter <name, directory or module file>`, `--adapter-option <key=value>` | The model is connected through an adapter: for an official one give its name, for others give a path; it can be given several times, and the later overrides the earlier; `--adapter-option` gives a parameter to the previous adapter. When the adapter gives a cost notice, before starting it says on standard error how many generations there will be, charged to the user's own account. See `SKILL.md` section 8 |
| `--json` | Standard output is one JSON document |

In the output directory, each line gets one audio file (`<index>-<reference segment>.<extension>`; a line dubbed in a one-request-per-scene is `<index>-scene.<extension>`, see "One request per scene" below), plus one report `dub.json`. `dub` does not stitch the lines into one file: pauses are recorded as they are in `units[i]` of the report (`pauseBeforeMs`, `pauseAfterMs`), and whoever stitches handles them accordingly; `dub` changes the speed itself after synthesis (see "Opening cue and speed" below), and when it could not, that is recorded in `speed` and also left to whoever stitches; for one finished file, use `mix` (see "Stitching" below). Exit codes: 0 all done; 1 some line failed, or it stopped on an error; 2 usage error. In the plan of `--dry-run`, the reference used for each line is the same as in a real run.

**Which model was used**：The adapter reports the model actually used, and `dub.json` records it in `units[i].model`. If the adapter switched models this time (for example the model that was supposed to be used is unavailable at that moment), that line also has `units[i].modelChange` (`from` is the model that was supposed to be used, `reason` is why it changed), and the output adds a separate notice ("注意", notice) listing which lines, what they were changed to, and why: the voice and delivery of these lines may differ from the other lines, and the user must be told. `dub` does not switch models itself and does not retry (whether to switch is decided by the platform; for the convention see `adapters/README.md`「When the model changes」).

**How a line becomes synthesis**：

1. `[voice:name]` in the script takes a pack name or pack ID (case-insensitive). With only one pack, it must be that pack: one pack has only one voice, and any other name reports `voice_unknown`. With several packs (`--pack`), the first pack is the voice at the start of the script (before the first `[voice:]`); `[voice:name]` switches to that pack from that line on, until the next voice marker or the end of this chapter (which returns to the first pack). Any other name reports `voice_unknown`, and `details` lists which packs were given; a name that matches more than one pack reports `voice_ambiguous`, and you specify it by pack ID.
2. **Cues go to the model as written, by position.** Square-bracket cues in the script (`[sad and surprised]`, `[hushed voice]`, `[laughs]`; for the syntax see `references/markup.md`) stay at the position where they are and go to the model together with the text; `dub` does not interpret or change them, and does not pass an instruction or an emotion name through a parameter either. Angle-bracket tags (`<whisper>…</whisper>`, `<french>…</french>`, `<|phoneme_start|>…<|phoneme_end|>`) also stay in place as written: the pronunciation lexicon does not change tag names or phonemes; when a line that is too long is split, it is not split between the two tags of a pair (a pair longer than one request is split inside, and each piece gets the pair of tags added at both ends); when the language is identified, letters inside tags and text wrapped by a language tag do not count (`references/markup.md`「Angle-bracket tags」, which also has one exception for environments that declare only `phoneme-in-text`). Stage directions (`（耳语）`, `*笑*`) are replaced before sending by an English cue of the same meaning (`[whispering]`, `[laughs]`), kept at the original position, and the words in the brackets are not spoken. Cues are always written in English (`models/scene3.md`「What to write」): when everything in the brackets is a phrase from the vocabulary (`vocab/cues.json`), it is replaced by the vocabulary's English form, emotion first and style after (`（生气地大喊）` becomes `[angry, shouting]`); one that only says fast or slow (`（慢慢地）`) is not written as a cue, because speed is not written as a cue (`models/scene3.md`「Speed and pauses: conclusions from listening」), and for speed use `--speed`; one that is already English (`(angrily)`), one the vocabulary does not recognize, or one with words outside the vocabulary in the brackets, has its words moved into square brackets as they are, and if they are Chinese it is a Chinese cue, which you change yourself before dubbing into two or three English words (the notice below lists these). Only `（…）`, `(…)`, `【…】`, `*…*` of up to 30 characters are stage directions; a longer bracket is a line, and is handed to the model to speak as it is, brackets included. An asterisk must stick to the text: `3 * 4 * 5` and `* 笑 *` are body text and are spoken as they are; `**…**` is emphasis, the asterisks are removed and the text is spoken (`references/markup.md`). What reads as a pause (`（停顿 2 秒）`, `（沉默）`; the syntax and near-synonyms are in `vocab/cues.json`) is still a pause; a momentary sound such as a breath, a cough or clearing the throat is not a pause and, like a laugh, is replaced by a cue (`（深吸一口气）` becomes `[deep breath]`, `*coughs*` becomes `[coughs]`). Whatever is written in a bracket of up to 30 characters is taken away like this when dubbing and not spoken, and so is text that the original wanted spoken inside brackets: `（画外音）` is sent as `[画外音]`, and `（疫情之前）` and `（笑话比赛）` are also replaced by cues. When none of the words in a bracket is in the vocabulary (`（画外音）`, `（疫情之前）`), `recognized` of that item in the report is false (`units[i].pick.directions`; for a scene it is `units[i].scene.turns[k].directions`), and `notes` has an extra `unrecognized_directions` entry listing these places (the text output has one notice line). If a bracket has even one word from the vocabulary it counts as recognized (Chinese characters are searched as substrings: `（笑话比赛）` contains "笑" (laugh), `（当时很开心）` contains "开心" (happy)); it does not go into this notice unless it is not in English (`（笑话比赛）` is moved into the square brackets as Chinese, so it is listed, and `notEnglish` of that item is true; the notice says to rewrite it as an English cue), while one in English that the vocabulary recognizes only in part (`(he smiles at her)`) is not listed. So this notice does not list everything, and you cannot rely on it to find the body text: for text in the original brackets that has to be spoken, rewrite each place yourself before dubbing into a form without brackets (commas, dashes). Moved into square brackets as they are, a long stage direction is a long cue: when one cue (written in square brackets, or turned from a stage direction) is longer than 4 words (two Chinese characters or kana count as one word, `lib/cue-length.mjs`), `notes` has a `long_cues` entry listing them (each item of `details.cues` is `{ line, cue, words }`), and the text output has one notice line. It only warns, does not change the text, and sends it as it is: change it yourself into two or three words that say only how this one place is spoken (for how to write it, see `models/scene3.md`「What to write」). A line that has only a cue and no text has its cue attached to the start of the next line of the same voice. Outside dubbing (for example when an app reads ordinary body text), the contents of a bracket are removed only when the whole bracket is a cue from the vocabulary, and the rest (for example `（笑话比赛）`) is read as body text, because it is not a stage cue. The authoritative version of the rules is `cuesInPlace` in `lib/line-hints.mjs`.
3. **Which reference segment to use** (`lib/reference-pick.mjs`): take in this order, and stop at the first that gives one: the reference tag the caller specified (`--reference-tag`, `options.referenceTag` in the library) → the default reference written in the selected setup (the setup's `referenceTag`) → the default segment of this line's language. `dub` does not pick by tag itself, does not pick the reference by each line's emotion, style or energy, and does not have the model judge the emotion of each line: emotion reaches the model through the cues in the script; picking by tag is your job, and once you have picked, you pass it in with `--reference-tag`, and if you cannot pick a suitable one, do not give it.
   - **Language of this line**: the caller's (`--language`), and if none, the setup's, and if none, identified from the text (the language is identified from the text that will be spoken after the cues are removed; cues in square brackets do not count); if it cannot be seen from the text either, the line has no language. A passage (one line in the script) is picked only once: the blocks of one line separated by pauses and cues are identified by the text of the whole line and use the same reference segment; the whole line looks at the main script (a Katakana name in a Chinese line, or one "ありがとう" in an English line, and the whole line is still Chinese or English). A block of English in a Chinese line follows the segment used for the Chinese. That block is marked cross-language. If the pack has English (the block on its own would use an English segment), this is cross-language by following the line: `pick.followsLine` is `true`, and the output for humans says "跨语言：这一行里有别的语言，跟着这一行的参考段" ("cross-language: this line contains another language, following this line's reference segment"); it is not that the pack lacks this language, and there is no need to change the pack; if you want that block to use the English segment, write it as a line of its own. If the pack has no English, mark as in the next two bullets (mark only, do not stop). Both of these are a mixed-language line, the whole line is still Chinese, and dubbing goes ahead as usual and does not stop (below, "No accent by default"). Compared with the segment's language: an exact match comes first, then a match of the main language (the line is `zh`, the segment is `zh-CN`), and when several segments match, take the one that comes first in the reference set. The pack's main language is the language of the main default segment (`reference.defaultSegment`).
   - **When a tag is set** (the first two layers): look, among the segments with this tag, for the one in this line's language. If this language has none: use the segment with this tag in the pack's main language, and if the main language has none either, use the segment with this tag that comes first in the reference set; these two are cross-language cloning, and the output for humans says "跨语言：这种语言里没有这个标签" ("cross-language: this language does not have this tag"); when the whole line is in this language, it stops by default and does not dub; a block embedded in a line is only marked, not stopped (below, "No accent by default"). With no language: use the segment with this tag in the main language, and if there is none, the one that comes first, and it does not count as cross-language.
   - **When no tag is set**: use the default segment of this line's language. The pack has one default segment for each language (`protocol/FORMAT.md` 4.4「Default segment」: the main language's is `reference.defaultSegment`, the other languages' are in `reference.languageDefaults`; for a language the pack does not write, it is the first segment of that language in the reference set). If the pack has no segment in this language: use the main language's default segment, and this line is cross-language, and the output for humans says "包里没有这种语言" ("the pack has no segment in this language"); when the whole line is in this language, it stops by default and does not dub; a block embedded in a line is only marked, not stopped (below, "No accent by default"); with no language, it also uses the main language's default segment and does not count as cross-language.
   - One line uses only one reference segment and does not blend; a held-out recording is never used as a reference. The reference text handed to the model together with the reference: if the reference segment has a cue annotation (`annotatedText` in the manifest, see `references/make-pack.md`「Cue annotation」), hand that, and if not, hand the verbatim transcript `text` (`refTextOf` in `lib/reference-pick.mjs`); the same for each speaker's reference in a scene. In a same-language request of one line whose line opens with this pack's name (`[沈迟]`, the manifest `name`), the reference text also opens with this name, and `units[i].referenceName` records it; a name that is not the pack's `name` as written gets nothing on the reference text (`models/scene3.md`「Put the character name first」; the rule is in `lib/dub.mjs` step 7c). Which segment was used and why is written in `units[i].pick` (the same in the plan of `--dry-run`): `segmentId` is that segment, `tag` is its reference tag (written for default segments too), `by` is which layer it was taken from (`reference-tag`, `setup`, `default`; a default segment changed by this line's language is also `default`), `crossLanguage` is whether this line is cross-language cloning, `followsLine` (present only when true) says that this line is cross-language only because it follows the segment used for this line (see "Language of this line" above), and `language` is which language this line was picked by and where it came from. A segment marked as synthesized (`synthetic`) is picked the same way as a segment of a real recording and written the same way. The authoritative version of the rules is the file header of `lib/reference-pick.mjs`.
   - **No accent by default.** Speaking one language with a reference in another language often gives an accent of the reference's language (inference: heard by one person, small sample; a Japanese reference speaking English is often English with a Japanese accent, and neither `[native English pronunciation]` nor `<english>`, which were heard, removed it, see `models/scene3.md`「Cross-language and accent」). So when among the lines to be synthesized this time there is a line whose reference segment is not in the line's language (the two cases above marked cross-language), `dub` stops before spending money, reports `dub_cross_language`, calls no capability, and writes nothing; `--dry-run` reports it too. What is compared is the language of the whole line: a few words of another language inside a line (the case in "Language of this line" above) do not count, and a line whose language cannot be seen does not count; when `--language` is given (or the setup writes a language), the comparison uses the given one, but if the text visibly is not in this language (English lines given `--language zh`, or the setup writes `ja`), `dub` does not trust what was given, compares by what it identified from the text, and still stops; when the text does not show it (only digits and punctuation), or for several languages in the same script (English and French are both Latin letters), `dub` cannot tell, and compares by the given one; lines that `--only` did not name, and lines carried over from the last run, are not synthesized this time and do not count either. For a merged scene (below, "One request per scene"), what is compared is the one segment each speaker uses for the whole scene against each of his turns.
     - The report says which lines (line N, the same numbering as `--only`), which pack, which reference segment, and the reference segment's language → the line's language. The line's language: if given (`--language`, the setup's), write it as given, `ja→en`; if identified from the text (including the case above of not trusting the given one), for kana or Hangul, which can only be one language, write that language, and for Latin letters or Chinese characters, which are not guessed to be one language, write the script, `ja→拉丁字母` (literal Chinese script name for Latin letters).
     - `details.units` has one item per line (one item per speaker in a scene): `{ unit, pack: { id, name }, speaker?, segmentId, by, from, to, script?, lines, hasLanguage }`. `unit` is the number of the line (starting at 0, the `--only` number minus 1), `speaker` is present only in a scene, `segmentId` and `by` are as in `pick`, `from` is the language of this reference segment, `to` is the language of the line (`null` when it is not guessed, with an extra `script`, for example `Latin`), `lines` is which lines (the same as `lines[i].index` in `dub.json`, starting at 0), and `hasLanguage` says whether the pack has a reference segment in this language.
     - After it stops, do not ask the user and do not add a reference on your own: write the lines in the target language, write the name pair at the start of each line `[name in the reference language|name in the line's language]` (`references/character-voice.md`「Language and accent」), add `--allow-cross-language` (`allowCrossLanguage: true` in the library) and dub again, as cross-language cloning, with `pick.crossLanguage` still marked. The names and language cues on both sides are written into the request by `dub` (`models/scene3.md`「Cross-language and accent」), and `units[i].languageMarks` records what was written. A line whose start has no name pair makes `dub` stop before spending money and report `dub_cross_language_unnamed`, and `--dry-run` reports it too. For the accent of the reference's language, add `--no-language-marks` (`languageMarks: false` in the library): the name pair is not required, the language cues are not added, and the script is sent as written. If the user wants to add a reference in this language themselves: add a reference segment in this language to the pack, hand it as material to `make-pack`, issue a new version on top of the previous version's pack directory (`references/make-pack.md`「Release a new version」), and dub with the new version. Where the reference comes from: if there is a recording of this role speaking this language, use the recording; if there is none, by default use this pack to dub a passage in this language cross-language (`--language <this language> --allow-cross-language --no-setup`, not applying the pack's setup, and mark the material `synthetic`); or a voice speaking this language that the user picked in the library (it is a different voice, say so clearly first); where the platform can specify a model, list as a separate option reading it out with another model first and then cloning it. For how to do it and what to tell the user, see `references/character-voice.md`「Add a reference segment in this language」; the report at the stop says the same.
     - When the pack actually has a segment in this language (`hasLanguage` is `true`), the report also says how to make use of it: when a language was given but the text is not in this language, do not give `--language` (if it came from the setup, override it with `--language` written as the language of the lines, or change to another setup with `--setup`, or use no setup with `--no-setup`); when a tag is set, this language has no segment with this tag, so change to a tag that this language does have (`--reference-tag`), or do not specify one (if the tag is the setup's default reference `referenceTag`, override it with `--reference-tag`, or change to another setup, or use no setup with `--no-setup`); in a merged scene where one speaker uses only one reference segment for the whole scene, dub separately (`--no-scene`), so that each line uses the reference of its own language. What these change are things the user named or the setup wrote, so first ask him as in `references/character-voice.md`「Language and accent」.
4. **Pronunciation lexicon**: for the use of `lexicon.pls` at the pack's root, the conditions for phonemes, and how the report is written, see `dub-details.md`「Pronunciation lexicon」 (read it only if the manifest's `files` lists it; changing pronunciation needs a new version). If the environment declares `phoneme-markers` (the synthesis model recognizes phoneme tags; for the syntax see that model's notes in `models/`), the lexicon's phonemes are written as phoneme tags, which also applies in a scene, and can be seen in `spoken` of `--dry-run`; an entry that has only one character is used, and the plan's notes have a `lexicon_single_character` entry.
5. **Dubbing guidance**: the last section of the pack's `SKILL.md`, in five sections (`### 这个人是谁` (who this person is), `### 音色` (voice), `### 演法` (delivery), `### 台词` (lines), `### 换语言时怎么说` (how to speak when changing language); see `references/make-pack.md`「The five sections of the dubbing guidance」). Read all of it first and follow it when writing the script: who this person is, the lines and the voice are the basis for writing the script (how he would say it at this moment, his attitude to whom; his self-reference, sentence endings, catchphrases, and what the voice is like); when cross-language, follow "how to speak when changing language" for the name pair, self-reference and catchphrases; the delivery is written as cues, put in the script where the way of speaking changes (a line can have several, each two or three words, not written as sentences, always written in English; a pair of tags for something that covers only a few words; see `models/scene3.md`「Cues」). `dub` does not hand the guidance to the model, and `guidance.sent` in the report is always false.
6. **Enhancers**: how enhancers in the pack that serve `voice-cloning` are handed to the capability, and how the report is written when they are not recognized, see `dub-details.md`「Enhancers」.
7. **Executable scripts**: those registered under the `dub` feature, which change the words to be spoken before synthesis and change the audio after synthesis, see below.

**One request per passage** (`lib/dub.mjs` step 5c): a passage is one line of the script (each non-empty line is a passage), in one voice. The pieces of one line separated by pauses (`[pause …]`, or pauses in stage directions) use the same reference segment and are spoken in one request; a sentence after them that has no cue written stays in the same request and continues the manner of speaking before it; lines that follow each other in the same chapter are also merged into this one request if they fit, with a line break between lines (see "How long text is split" below). In `dub.json` it is one unit, and `joined` lists which pieces were merged. The pauses in the middle:

- **Short ones go into the text of the request.** A pause no longer than the adapter's declared `limits.maxPauseInRequestMs` (the longest a single pause in one request may be; if not declared, the base part's default is used, `DEFAULT_MAX_PAUSE_IN_REQUEST_MS` in `lib/pause-in-request.mjs`) is written in whichever of the measured notations gives the closest silence: where there is no punctuation, write a comma or `[pause]`; where what comes before is a comma or similar, add `[pause]` to make it longer; where what comes before is already a period, question mark or exclamation mark, add nothing (they already pause long enough by themselves, and adding more after them was measured to drop the next sentence). When no pause is written and the line just changes, connect with a line change (in the request's text there is a line break between the two lines); a line that has only a pause follows this rule too, written between the two lines. The notations and readings are in `models/scene3.md`「Pause between lines」; how long a short pause comes out is only approximate, and the measured ones vary by a few hundred milliseconds either way.
- **Long ones are split there.** A pause longer than it is split into two requests at that place, and the pause is recorded in the report (`pauseAfterMs` of the earlier line, `pauseBeforeMs` of the later one), and `mix` inserts silence of the same length.
- **The request after a split repeats only the first square bracket at the start of this line.** The script requires each line to start with the role's name, so what is repeated is the name (for a cross-language line, the name pair); `dub` writes it, and you do not. This request counts as having a cue written at its start, and the setup's opening cue is not added again. Other cues exist only where the script writes them: if you want it said that way after a long pause, write it again after the pause (`[甘雨][angry]你好。[pause 3s][angry]我走了。`; the Chinese lines "你好。" "我走了。" mean "Hello." "I'm leaving.").
- Places that are always split: chapters; between items of a `.json` script (each item counts as a chapter of its own: it is not merged with others into one request, `[voice:]` does not cross items, and each item starts from the first pack); a change of voice (the name written in `[voice:]` changed); a change of language between lines (the pack has a default segment in that language, and the reference segment differs; in `dub.json` the later block's `cutBefore` is `language`, and `notes` has a `language_cut` entry listing where it was cut); a different setup speed; a different opening cue; this line needs the setup's cue added while the request it would be merged into already has a cue the script wrote itself (see "Opening cue and speed" below); and the pack having a `dub` script. Of these, chapters, between items, the pack having a `dub` script, and having to add the setup's cue, these four places do not stop a line or item shorter than `limits.minChars` from being merged across, see the next bullet. A short stretch of mixed-language speech should stay in one request: write it in the same line (a line picks only one reference segment, and the other language embedded follows this line, without stopping); or give `--language` (the whole script picks its reference by that one language), or give a `--reference-tag` that exists in only one language: in these two ways, a whole line in the other language uses this segment, which is cross-language cloning, often with an accent, and you must add `--allow-cross-language`, or else `dub` stops (step 3 "No accent by default"). What does not fit in one request is cut at boundaries as in "How long text is split" below. At these cut points (except chapters, between items of a `.json`, and a change of voice), where the script wrote no pause, `dub` records a default pause, see "Breath pause at the cut" under "How long text is split" below.
- **Ones shorter than the minimum are still merged.** When the adapter declares the minimum number of characters per request (`limits.minChars`), a line or item shorter than it is still merged into the next line (without merging it cannot be synthesized; the count is of spoken characters, and square-bracket cues and tag names do not count): the same pack, the same reference, speed, expressiveness and opening cue, no pause written in between, and the merged result fits in one request, then merge; this is the same across chapters, across items, and with `--no-scene`. The pack having a `dub` script and the case of a line needing the setup's cue while a script-written cue is already before it, from the previous bullet, do not stop it either (for how the opening cue is added after the merge, see "Opening cue and speed" below). An item that was given a target duration is merged only with others in the same item (below, "Target duration"). In `dub.json` the merged result is one unit, `joined` lists which lines were merged, and `notes` has a `short_lines_joined` entry. If it is still short after merging, judge after merging into the same request as above, and if it still does not reach the minimum, it is recorded as not synthesized (below, "Failure and redo").

**How long text is split** (`lib/dub.mjs` steps 5 and 5c; the rules for the cut points are in `requestsOf` in `lib/pause-in-request.mjs`): if it fits, do not split; if it does not fit, split only at boundaries.

- **Upper limit per request.** By default a request does not exceed about 1000 spoken characters (about 170 words in English; `DEFAULT_MAX_SPOKEN_CHARS` in `lib/synthesis-limits.mjs`), the same for narration and for a scene. This is `dub`'s own default way of splitting, not an upper limit at which the platform reports an error: beyond it, it splits at boundaries, and within each request lines are still merged. If the adapter declares `limits.maxChars` (the most characters one request can send out, including the cue added at the start of the request), it is not exceeded either: both must be satisfied. If `--max-chars` is given, it splits only by the given number (the characters sent out), and neither the default 1000 nor the adapter's limit is considered. Why the default is 1000 and how much one request of a model can hold: see the model notes (for example `models/scene3.md`「Limits of one request」); limits the platform adds on top (for example how long a gateway waits) are in the adapter's notes.
- **Two ways of counting characters.** The default 1000 counts spoken characters: by character count, one Chinese character, one letter and one punctuation mark each count as one, and English is also counted by letters, not by words; square-bracket cues do not count, the names of angle-bracket tags do not count, the text wrapped by paired tags counts (text in another language wrapped by a language tag counts too), and one phoneme tag counts as one character; consecutive whitespace (a space between words, a line break between lines in one request) counts as one, and whitespace at the two ends does not count. "要念的 N 个字" ("N characters to be spoken") in the `--dry-run` summary is counted this way too (`spokenLength` in `lib/synthesis-limits.mjs`) and is the sum of the characters of the requests. The adapter's `limits.maxChars` and `--max-chars` count the characters sent out: every character counts, and cues, tags, every whitespace, and the cue added at the start of the request are all in it.
- **Boundary rule.** A non-empty line of the script is a paragraph, and the boundaries between lines are paragraph boundaries; a line that has only a pause (`[pause 1.5s]`, or a stage direction that reads as a pause, for example `（停顿 2 秒）`, `（沉默）`) is a scene boundary; a pause written at the end or the start of a line (`他出了门。[pause 1s]`, `（沉默）中午……`) counts as a paragraph boundary; a chapter heading (`# title`) is always a cut (except a line or item shorter than `limits.minChars`, see "Ones shorter than the minimum are still merged" under "One request per passage" above). When it fits, the line that has only a pause is still in the request: a pause that is no longer than what fits in a request is written in the text (above, "One request per passage"), and a longer one is cut as in that section.
- **Order when it does not fit.** First cut at scene boundaries, and scenes that fit into one request are still merged together; for a scene that still does not fit, cut between lines inside it; only when a line by itself does not fit, cut between the sentences of this line (a sentence that still does not fit is cut at a comma or similar; only if it still exceeds the limit of characters sent out, that is the adapter's `limits.maxChars` or `--max-chars`, is it hard-cut between characters). The default of about 1000 spoken characters cuts only as far as commas and does not hard-cut: a sentence with no comma that is longer than it becomes one request as a whole sentence and is not cut in the middle of a word. A hard cut leaves a remainder of only punctuation, which is merged into the previous piece. A block that comes out of a cut and still does not fit is cut only one level further down inside it, and is not merged with the blocks before and after.
- **Cut notes in the report.** For a block cut because it does not fit, `units[i].cutBefore` in `dub.json` records what kind of boundary it was cut at from the previous block: `scene` (scene), `paragraph` (paragraph), `sentence` (inside a line). `notes` has a `cut_to_fit` entry: `details.maxSpokenChars` and `details.maxChars` are the two limits of this run (spoken characters, characters sent out; the one that does not apply is `null`), and `details.cuts` lists each place (`unit` is the number of the piece after the cut, starting at 0; `at` is the boundary); for one cut inside a line, the description has an extra sentence. The text output writes under that block "放不下一个请求，在……和前一段切开" ("does not fit in one request, cut from the previous piece at …"). Those cut by a long pause, a chapter or a change of voice are not of this kind and have no `cutBefore`; for one cut by a change of language, `cutBefore` is `language` (above, "One request per passage").
- **Breath pause at the cut.** Where `dub` cuts by itself and the script wrote no pause at the cut, `dub` records a default pause before the block after the cut, and `mix` inserts it as silence: 540 milliseconds, the same number between lines and between the sentences within a line (`CUT_PAUSE_MS` in `lib/dub.mjs`). `units[i].pauseBeforeMs` is this number, and `units[i].cutPause` is `paragraph` (between lines) or `sentence` (inside a line), meaning this is the cut's default pause, not one the script wrote; the text output states it under that block. It is added whatever the reason for the cut: it did not fit (`cutBefore`), the language changed between lines (`cutBefore` is `language`), the opening cue differs (including the case above "this line needs the setup's cue added"), the setup speed differs, the pack has a `dub` script. When a scene is too long and `dub` cuts it into several scenes between lines (below, "One request per scene"), it is also added if the same person keeps speaking on both sides of the cut (the last speaker of the earlier block is the first speaker of the later one), and `cutPause` is `paragraph`; a cut at a change of speaker gets none, and relies on `mix`'s rule at speaker changes (below, "Stitching", silence on both sides trimmed to about 0.1 second). Not added: where the script wrote a pause at the cut, the script is followed; where one sentence does not fit by itself and is cut in its middle (at a comma or similar, or hard-cut), there is no pause in the middle of a sentence (`cutBefore` is still `sentence`); chapters, between items of a `.json` script, a change of voice, and before and after a scene are the script's own boundaries (if you want a breath, write `[pause 0.5s]` at the start of the later block); between lines with `--no-scene` (explicit separation), one request per line is what you asked for, and the script's pauses are followed, as before. Source: a long Chinese text was dubbed in two versions and measured; in the version with one request for the whole passage, the model left 650 to 740 milliseconds of silence at the paragraph junctions (median 660); in the cut version, the blocks on the two sides of the cut originally had only 90 to 170 milliseconds of head and tail (median 120), and what is inserted is the difference between the two (details and how it was measured are in the note on `CUT_PAUSE_MS`). The 610 to 830 milliseconds measured at periods inside a line overlap with those at paragraph junctions and the two cannot be told apart, so there is only one number. Measured on only one model and one Chinese passage: with another model, the silence the block heads and tails originally leave differs, and the actual silence at the cut differs accordingly; for another length, write `[pause …]` at the cut.
- **Where the split pieces join up.** The same reference segment is used (the reference is picked by language, and splitting does not change it; for the several scenes a scene was cut into, each person uses the segment he got most often over the whole scene before the cut, the same across the scenes, see "One request per scene" below; a line dubbed alone is picked by its own line); the opening cue is added once per block (rules in "Opening cue and speed" below). If the runtime environment declares `seed-in-request` (its synthesis accepts `seed`, see `vocab/capability-signatures.md`), `dub` gives every request the same fixed `seed` (`DUB_SEED` in `lib/dub.mjs`), written in `units[i].seed`, and `capabilities` has `seed-in-request`; in an environment that does not declare it, requests have no `seed`. Whether the same seed makes the blocks closer to each other is in the model notes. A line that `--only` names for redo gets a different `seed` ("Failure and redo").
- **A piece cannot hear the previous one.** The pieces are connected only by the same reference segment, the same seed and the same opening cue, so the fewer the cut points the better. If the platform times out earlier (for example a gateway that waits only a few minutes), add a chapter heading at a scene or paragraph boundary in the middle of that block to cut it, then run the same command again: unchanged blocks are carried over as they are and not paid for again ("Failure and redo"). Two things to watch when adding a heading: a voice marker does not cross chapters, so if what follows the heading is not the first pack, rewrite `[voice:name]` at the start of the line below the heading, and without it it goes back to the first pack; at a chapter `dub` does not record the cut's default pause, so to pause for a breath as when `dub` cuts by itself, write `[pause 0.5s]` at the start of the line below the heading.

**Opening cue and speed** (the setup and several items given by the caller: the author fixes emotion, style, energy and speed into a setup, and one is chosen when dubbing; the caller may also give these items, and on the same item the caller's overrides the setup's):

- **Combine into one cue, written at the start of every request.** For each of emotion, style and energy, take the caller's first (`--emotion`, `--style`, `--energy`, and the item's own `labels` in a `.json` script), and if there is none, the setup's, and combine them into one square-bracket cue, for example `[angry, low energy]`: emotion and style are written as the canonical names of the tag vocabulary (`vocab/cues.json`) (the setup writes "生气", in the cue it is `angry`), and energy is written like `low energy`. If none of the three is given, nothing is added. The authoritative version of the rules is step 7a of `lib/dub.mjs` and the file header of `lib/opening-cue.mjs`.
- **The `instructions` text is not sent to the model.** A summarizing label such as "带一点四川口音" ("with a slight Sichuan accent") does not tell the model how to actually speak. So `--instructions`, `instructions` on a `.json` item, and `options.instructions` are all removed: giving one reports `dub_input_invalid` (`--dry-run` reports it too, and no capability is called), `details.field` is `instructions` or `script[<index>].instructions`, and the message says that `dub` no longer sends instructions to the model, and that for the manner of speaking you want, you write a concrete cue in the script, at the place where it happens. The `instructions` of a setup in the pack (`references/make-pack.md`「Several setups (writing fixed values into the voice)」) are for the script writer to read: when a setup with instructions is used, `notes` has a `setup_instructions` entry, and `details` is `{ setup, instructions, lines, pack? }` (the original instructions, and which lines used this setup; with several packs, one entry per pack that has instructions, and `pack` is the pack ID), telling the script writer to write concrete things in the script following the instructions: wording and modal particles written straight into the lines, commonly used characters with a different pronunciation written as the character that reads with that pronunciation, and changes of tone, final sounds and rhythm marked with a short cue in front of the characters where they happen (for how to write it see `models/scene3.md`「What to write」「Cross-language and accent」). With `--no-setup`, with no setup used, or with a setup that has no instructions, there is no such entry.
- **Keep it short.** The model accepts only text, and the opening cue is written into every request. The way of counting and the limits are in `lib/cue-length.mjs`: after synthesis the whole cue is no more than 10 words (`MAX_OPENING_CUE_WORDS`); two Chinese characters or kana count as one word, alphabetic scripts are counted by spaces, and digits and punctuation do not count. `cueWords` and the two limits (`MAX_CUE_WORDS`, `MAX_OPENING_CUE_WORDS`) are a stable interface for callers: a caller can import them directly and check on its own before handing anything to `make-pack` or `dub`. Within the length limit, the request's text is character for character what it was before.
  - Emotion and style that are momentary sounds (a sigh, a laugh, a cough and the like, `oneShot` in `vocab/cues.json`; an emotion value must be, as a whole, one word for a momentary sound, for example `笑`, `laugh`, while `微笑` and `惊叹` are ordinary emotions and are combined as usual): neither the setup's nor the caller's is added to the opening cue, because the opening cue governs how the whole line is said. `notes` has a `one_shot_style_skipped` entry, and `details` is `{ item, style, from, setup?, lines }` (`item` is `emotion` or `style`, and `style` is the canonical name of that sound; lines whose start already has a script-written cue do not count). If you want that one sound, write it in the script where it happens, for example `[sighs]`.
  - Fallback: when the cue to be added is longer than 10 words in total after synthesis (emotion and style were written as a long string outside the vocabulary), planning reports `dub_input_invalid`, `details.field` is `openingCue`, and the message states what to do: override that item of the setup with a shorter `--emotion` or `--style`, or use `--no-setup`, or change the setup in the pack. It is not reported for a line whose start has a script-written cue (the cue is not sent). It also reports `dub_input_invalid`, with `details.field` of `maxChars`, when the opening cue plus a space leaves `--max-chars` with fewer than 10 characters and the line does not fit in one request and has to be cut: it does not cut into pieces of a few characters each; a line that fits whole in one request is sent as it is. When making a pack, an opening cue synthesized from a setup that exceeds the limit is also reported before money is spent (`references/make-pack.md`「Several setups (writing fixed values into the voice)」).
- **Which request it goes on**: the first item of each request (a passage that is a request by itself, or several lines or passages merged into one request, are each one request; the merged ones count by their first line, and the lines in the middle get none again). For several lines merged into one request, the opening cue is only before the first line: whether it still governs across lines, the vendor did not write, and nobody tested it (`models/scene3.md`「Where a cue is written and how far it reaches」). When the line at the start of this request has a script-written cue (in square brackets, or a stage direction at the start of a line, for example `（小声）`), this request gets none: the script is followed; the later pieces of a line that was cut count by this line's start too. What the script is followed on is only the line that wrote the cue: a line that follows in the same chapter and wrote no cue itself is not merged into the previous request if that request already has a script-written cue (at the start, or written at the start or in the middle of some line), but starts another request and gets the setup's cue (`（小声）快过来。` and the next line `听我说。` are two requests, and the latter starts with the setup's cue; `快过来。（小声）真的。` and the next line `听我说。` are also two); if the previous request is all setup cue from beginning to end, they are still merged (`（小声）快过来。[pause 2s]真的。` and the next line `听我说。`: the long pause cut the line's start sentence into a request of its own, `真的。` and `听我说。` are merged into one, and its start is the setup's cue; the Chinese lines mean "(softly) Come here. … Really." and "Listen to me."). "The previous request" counts as the run before it is cut by the upper limit: when a script-written cue of a line is cut into the previous request because of the limit (for example `（小声）<one long sentence>。[pause 0.3s]真的。` cut exactly before `真的。`), the request of `真的。` is all setup cue from beginning to end, and the next line is not merged into it either, so there is occasionally one more cut point; the setup's cue is not lost. The sentences after a pause in the same line continue to use the cue at the start of the line. Exception: when the adapter declares the minimum number of characters per request (`limits.minChars`), a line or item shorter than it is still merged into the next line (without merging it cannot be synthesized; for the conditions see "Ones shorter than the minimum are still merged" under "One request per passage" above), and this rule does not stop it, also across chapters and across items: the opening cue of the merged request counts by the short line, and if its start has a script-written cue, the whole request gets none; the next line gets no extra setup cue either (a short `（小声）快。` followed by the line `听我说，我们没时间了。` is one request, and the start has no setup cue; the Chinese lines mean "(softly) Quick." and "Listen to me, we have no time."). A cue written in the middle of a sentence stays in place and takes effect from where it is written, and the opening cue is still added. With one request per scene, each turn is one opening for that speaker: each turn gets the cue synthesized from the setup of his own pack (not added if the start of that line has a script-written cue), the same as what each line gets with one request per line. Two lines with different opening cues are not merged into one request. The opening cue counts in the characters sent out (the adapter's `limits.maxChars`, `--max-chars`: leave room for it when cutting and merging passages), and does not count in the spoken characters or the minimum character count (a cue is not spoken).
- **Speed is changed after synthesis.** For speed, take the caller's first (`--speed`, the item's own `speed`), and if there is none, the setup's; the synthesis capability does not accept speed (the model notes say whether it accepts a speed parameter and whether writing "slower" in the text has any effect), so after synthesis `dub` changes the speed of this passage's audio (keeping pitch), with the same rules as the speed change in "Target duration": the upper and lower limits are in `SPEED_LIMITS` in `lib/mix.mjs`, a value outside is changed to the nearest end, and ffmpeg is required. For a passage whose speed was changed, `speed` in `dub.json` is null (`mix` does not change it again), and `speedChange` records the factor wanted (`wanted`), the one actually used (`speed`), and the length before and after (`originalMs`, `actualMs`), with an extra `limit` when it was outside the limits. If the environment has no ffmpeg: the audio is handed over at its original length, with no error, `speed` keeps the wanted speed, `speedChange.speed` is null, and the output has a notice `speed_not_applied`; afterwards stitch with a `mix` that has ffmpeg, and it changes the speed according to `speed`. For an item that was given a target duration, the speed is set by the target duration, and neither the caller's nor the setup's speed is used.
- **Expressiveness is left to the synthesis capability; the audio is not altered.** The expressiveness obtained (for the order of precedence see the `--expressiveness` row of the options table above) is passed unchanged to every synthesis request for these lines (both the request of one person speaking and the request of a scene are passed), recorded in `units[i].expressiveness` of `dub.json` and of the plan, and when a value is obtained, which layer gave it is also recorded, `units[i].expressivenessFrom`: `item` (the `.json` item's own), `option` (`--expressiveness`), `setup` (the setup's), `global` (the pack's global value); for several lines merged into one request whose values are the same but come from different layers, it is `mixed`; what the pack itself would give is `{ value, from }` in `pack.expressiveness` of the plan and `dub.json` (`packs[i].expressiveness` with several packs), where `from` is `setup` or `global` and refers to the value this pack gives when nothing is given on the command line, which `--dry-run` shows (costs nothing; in the text output, the global value is on a separate line starting "Expressiveness from the pack:", and the setup's value is on the "Setup:" line), and if the pack gives nothing, there is no such item; if the selected setup writes an expressiveness, the place in the plan and `dub.json` that tells which setup was used (`pack.setup`, `packs[i].setup` with several packs) also carries its `expressiveness`, whether or not this line finally used it (also when `--expressiveness` or a `.json` item gave a value that overrode the setup's), so that the script writer can see which voice has a fixed value; on the "设定" line of the text output it is written as "起伏 <value>" ("expressiveness <value>"). A value that is not an integer from 0 to 100 (a decimal, the 0-to-1 notation, out of range, not a number) reports `dub_input_invalid`, with `details.field` being `expressiveness` or `script[<index>].expressiveness`, which `--dry-run` also reports, and no capability is called.
  - If none is given, nothing is passed: the request, `dub.json` and the case without this item are character for character the same (also for a pack where neither the setup nor the global value wrote this value); `dub` does not fill in a default by scene (dialogue, narration) itself, and not giving it means the environment's own default. Who gives it and how much is suitable: see the model notes, `models/scene3.md`「Expressiveness」.
  - One request carries only one value: lines with different values are not merged into one request (items of a `.json` are different requests anyway; merging of short passages does not cross values; two people from several packs, each using its own setup with different values, are not merged into one scene, see "Where to split" under "One request per scene" below).
  - What to do if the environment's model does not have this knob: see `expressiveness` of `voice-cloning` in `vocab/capability-signatures.md`.
- **Report**: `units[i].openingCue` in `dub.json` (for a scene it is `units[i].scene.turns[k].openingCue`): `cue` is the synthesized cue, `added` is whether it was added (false means the start of that line has a script-written cue), `parts` is each item used, `{ value, from }`, and `from` is `caller` (given by the caller) or `setup` (the setup's). In the text output, under each line, the opening cue added and where each item came from are written.
- When running again and carrying over the previous run's files, the opening cue, speed and expressiveness (including the setup's and the global expressiveness) must also be unchanged (see "Failure and redo" below).

**Changing speakers within a scene** (several packs dubbing a scene, `--pack` given several times): at a change of speaker, the join is tight by default (`mix` trims it to about 100 milliseconds, details in "Stitching"). If this line is a refusal, a rebuttal, an unwilling response, or is choked or hesitant, mark `[pause 0.5s]` before this line (0.4 to 0.8 second, how long depends on the scene); it is the same when written after a stage direction: `（生气）[pause 0.5s]不行，我不去。` is sent as `[angry]不行，我不去。` with the pause before it (the Chinese line means "(angry) No, I'm not going."); the marked pause is inserted in addition to the trimmed silence (in a scene merged into one, a pause not exceeding the limit stays in the request and is not inserted separately, see "Where to split" under "One request per scene" below). Source: in conversation research, speaker-change gaps of 700 milliseconds or more mostly appear together with unwilling responses (Levinson & Torreira 2015). A script given by the user is often written as "name：line" ("名字：台词"): replace the prefix with `[voice:name]` (the name is a pack name or pack ID); if it is not replaced, the name will be spoken. `--dry-run` warns about those not replaced: if the text to be spoken in a line starts with the name or pack ID of one of the given packs followed by "：" or ":", the plan's `notes` has a `speaker_name_in_line` entry listing which lines (`details.lines`) and what it suggests replacing with; it only warns, does not change the text, and does not change the voice either.

**One request per scene** (the environment declares `text-to-dialogue` and `scene-in-request`, and several packs are given): a continuous passage that several people speak in turn goes into **one** request and yields **one** audio file (`<index>-scene.<extension>`), no longer one request per line. `--dry-run` shows which lines became a scene. Key points:

- **No separate audio for each line.** One request has only one audio, and the platform gives no boundary or timestamp for each turn; in `dub.json` the scene is one unit (`joined` lists the member lines, and `scene.speakers` writes the reference segment each speaker uses for the whole scene and the reason (`scene.speakers[i].pick`: `segmentId`, `tag`, `by` write that of the segment used for the whole scene, as in step 3 above; `crossLanguage` says whether some turn of this speaker is in a language that does not match this segment, for example a role who speaks English and Chinese in one scene can use only one segment for the whole scene, and the language that does not match is cross-language, and the output for humans marks this speaker "有几轮跨语言" ("some turns are cross-language"); with such a turn, if `--allow-cross-language` was not given it stops, see step 3 "No accent by default" above), and `scene.turns` writes each turn's speaker and words (cues in place), the reference obtained for this turn (`picked`) and the stage directions read (`directions`); `pack` is the first speaker's pack, and `lastSpeakerPack` is the last one; the unit of this scene has no `pick` of its own). To get one file per line, or to redo only one line (`--only` goes by unit number, and a scene is one number), use `--no-scene` (`options.scene: false` in the library; the exception is the same as in the `--no-scene` row of the table above: when the adapter declares `limits.minChars`, a line shorter than it is still merged into the next line, and those two lines are one file, see "Ones shorter than the minimum are still merged" under "One request per passage" above).
- **One reference segment per speaker for the whole scene**: for each of his turns, first take one segment in the order of step 3 above (if `--reference-tag` named his pack, or his setup wrote `referenceTag`, it is the segment of that tag), and use for the whole scene the segment obtained most often, and for a tie take the one that appeared first. When a scene is too long and is cut into several scenes, count over the whole scene before the cut, and he uses the same segment in all the scenes and does not change voice at the place where `dub` cuts by itself (in that case the language he speaks in one of the scenes may not match that segment, and `crossLanguage` is written as it is). The cue of each turn is written in the text of this turn (written in the script, and turned from stage directions), and handed to the model as it is; so for a scene with big emotional swings, rely on the cues of each turn, not on changing the reference segment.
- **Where to split**: a chapter change, a pause longer than `limits.maxPauseInRequestMs` (the same limit as in "One request per passage", each place compared on its own), a speed change, an expressiveness change, a pack that has a `dub` script, and speakers exceeding the adapter's declared limit (`limits.maxSpeakers`) are all cut points, and long pauses are left for `mix` to insert. A pause not exceeding the limit (`[pause …]`, a line that has only a pause, a stage direction that reads as a pause) stays in this scene's request and is not cut, written as in "One request per passage": pieces of the same line separated by a pause are still one turn, and the notation is attached after the previous piece; between turns (a change of speaker, or the next line of the same person continuing) it is written at the end of the previous turn; where the notation is to add nothing (for example after a period), add nothing. What stays in the request is not inserted by `mix` again: the `pauseBeforeMs` and `pauseAfterMs` of this scene are only those at the head and tail of the scene, `scene.turns[i].text` is the text as sent (the notation is in it; the setup's opening cue is not in it, it is recorded in `openingCue` and is added at the very front of this turn when sent), and `pauses_in_request` in `notes` counts them too. How a scene written this way sounds, nobody has listened to. A pause written as a square-bracket cue (`[沉默片刻]`, `[停了一下]`) is not treated by `dub` as a pause, nor as a cut point: it is handed to the model as it is, and whether it pauses and for how long is up to the model; written this way at a speaker change, the pause is unstable, by inference (nobody has listened to it, only the model judged that it mostly does not pause long enough; a lead, `models/scene3.md`「Pause between lines」); to have `dub` recognize it as a pause, write `[pause …]` (or a stage direction in round brackets that reads as a pause, for example `（沉默片刻）`): if it is longer than the limit, the scene is cut there, and `mix` inserts exactly as long as it says; if it does not exceed the limit, it is written into the request, and the silence is whichever measured notation is the closest. A scene that does not fit in one request (the limit is the same as in "How long text is split", the spoken characters are those of all the turns added up, and the pauses written in count too) is cut into several scenes between lines: at a change of speaker, or at the next line of the same person continuing, and not in the middle of a line; within each scene it is still one request for several people. For the later scene after the cut, `cutBefore` in `dub.json` is `paragraph`, `cut_to_fit` in `notes` also lists it, and the text output states it under that scene; where both sides of the cut are the same person, a pause of about half a second is recorded in front (above, "Breath pause at the cut"). A line that does not fit by itself is dubbed alone (only one person speaking, cut between sentences as in "How long text is split"). A scene has at least two speakers: a passage with only one person speaking (a monologue, or one left with only one person after the cut) still uses `voice-cloning`, and if it fits in one request as in "How long text is split" it is one request.
- **Too long**: if after cutting by the limit the platform still says a scene does not fit, it is not cut automatically again and not resent: that scene is recorded as failed (each scene that does not fit fails on its own and has its own `scene_too_long` notice, the other scenes are dubbed as usual, and it does not stop because several scenes do not fit), and the output says which scene it is; add a chapter marker (`# title`) in the middle of that scene to cut it into two scenes (for the two things to watch when adding a heading, see "A piece cannot hear the previous one" under "How long text is split" above), or use `--no-scene`.
- In an environment that does not declare it: it does not dub one request per scene, but one voice at a time; several lines of the same voice that continue are merged into one request if they fit, as in "How long text is split". With `--no-scene` given: one request and one file per line, and several lines of the same voice that continue are also separate (a long pause that does not fit in a line, and a line that does not fit in one request, are still cut there, see the `--no-scene` row of the table above). When the adapter declares `limits.minChars`, a line shorter than it is still merged into the next line, whether or not `--no-scene` was given and whether or not it crosses a chapter ("Ones shorter than the minimum are still merged" under "One request per passage" above).

**One audio file per line**: dub this way only when the user wants each line of a piece to have its own audio (a web page, a canvas or a video that plays line by line); at other times, merge into one request as above. Write each line of the script on its own line, with `[voice:<name>]` in front, cues written as usual, and a chapter heading `# <n>` (`n` starting at 1) in front of each line; dub with `--no-scene` and a separate `--out`. Line i is `units[i]`, and its audio is `units[i].file` (`<index>-<reference segment>.<extension>`): check that `units` has as many items as there are lines, that no item was cut (`cutBefore`), and that none was merged (`joined`; when the adapter declares `limits.minChars`, a line shorter than it is merged into the next line, so first, following step 2 of `scenes/one-line.md`, write the short lines into the lines before and after). For one that goes into a web page, put `--out` in the page's own directory, and the page refers to each file by a path relative to itself, so dub first and write the page after. Source: an existing practice on another platform, brought over; for the trade-off of one request per line see "One request per passage" above.

**Target duration** (a line that fits a picture: dubbing a line for a video, where the line has to match the picture's time): when an item of the script is given a target duration (`--target-duration-ms`, or `targetDurationMs` of that item in a `.json` script, a positive integer in milliseconds), `dub` changes the speed of this item's audio after synthesis (keeping pitch) so that its length matches the target. Key points:

- **One item becomes one audio.** The target duration is for one piece of audio. An item given a target duration is not merged with other items into one request; if it itself comes out as more than one piece (a pause in it that does not fit in a request, a chapter, a change of voice, a change of language or of opening cue between lines (the places that are always cut in "One request per passage"), or a request that does not fit and is cut ("How long text is split")), it reports `dub_input_invalid` before spending money (`--dry-run` reports it too): split it into several items, each with its own target duration, or remove what cuts it. An item that several people speak in turn that went into a scene ("One request per scene"): a scene is one audio, and the whole scene changes speed together.
- **Speed-change limits are the same as for stitching**: the factor is the original length divided by the target (greater than 1 means faster), the upper and lower limits are in `SPEED_LIMITS` in `lib/mix.mjs` (the source is there, and the speed change of `mix` uses the same place); if the factor wanted is outside, it changes to the nearest end and does not force it. Changing speed needs ffmpeg: if the environment has none, the audio is handed over at its original length, with no error.
- **Speed is set by the target duration**: for a segment given a target duration, neither the speed given by the caller nor the setup's is used, and its `speed` in the report is null (otherwise `mix` would change it again).
- **Report**: `units[i].targetDuration` in `dub.json`: `targetMs` (the target), `originalMs` (how long the synthesis came out), `speed` (the factor of the speed change, null without ffmpeg), `actualMs` (how long what is handed over is), `offByMs` (how much longer than the target, negative if shorter), all milliseconds rounded to integers; when outside the limits there is an extra `limit` (`max` upper limit, `min` lower limit). In `--dry-run` there is only `targetMs`. For those that cannot be changed to the target (outside the limits, or without ffmpeg), the output has a notice `target_duration_missed` listing for each segment the target, the actual and the difference: if the difference is large, change this line's words and dub again (delete words if too long, add words if too short). In the text output, the brackets under each line also give the target, the original length and the factor.
- A script given no target duration: the same as before.

**Comparing timbre** (timbre drift: the dubbed voice has drifted away from the reference): when the runtime environment has `speaker-verification`, `dub` measures, for each request that is not a scene (one unit, possibly with several lines merged), once after synthesis, the speaker similarity between it and the reference segment used. Key points:

- **What is measured.** The synthesized audio is compared with the recording of the reference segment used for this line (`pick.segmentId`). What is measured is the piece the model produced: for one that the pack's script changed, or whose speed was changed by speed or target duration, what is measured is the version before the change.
- **Similarity in the report.** `units[i].speakerSimilarity` in `dub.json`: `similarity` is the similarity, and `segmentId` is which reference segment it was compared with. When `--min-similarity` is given, a line below it has `drifted` as `true` (`false` if not below), and the output adds a separate notice ("Note:") listing these lines; if not given, there are only the numbers and no `drifted`. The default threshold has to wait until auditioning decides it, and is not given now. The range of the numbers is as the environment's `speaker-verification` says (written in the adapter's notes). The top-level `speakerSimilarity` writes whether this run measured (`measured`) and the threshold (`minSimilarity`, `null` if not given); when the environment does not have this capability, `measured` is `false`, `reason` is `capability_missing`, and no line has a similarity: the report says it was not measured, which is not the same as measured and fine. `--dry-run` also has this item.
- **A one-request scene cannot be measured.** There is no boundary for each speaker in one audio, so in `speakerSimilarity.speakers` of that scene each speaker has one item, `status` is `unmeasurable`, `label` is "unmeasurable", `reason` is `scene_in_request`, and no capability is called. To measure, use `--no-scene` for one request per line.
- **Could not be measured or heard.** If a voiceprint cannot be embedded from one side (too short, nearly silent), this line is "could not be measured" (`status` is `no_speech`, and `which` says whether it was the synthesized side or the reference side); a temporary service error is "not heard" (`not_heard`). Neither is retried, and this line is still done. Other errors during measuring (401 and the like) stop, the same as during synthesis.
- **What to do when it has drifted.** `dub` only measures and reports, does not spend money to redo on its own, and the agent does not redo by itself because of `drifted` or a low number either: the number is written truthfully into `dub.json`, and if the user asks whether the timbre is stable, tell him the number truthfully. If the user hears a drift, change the reference segment according to what he says (change to another reference tag) and dub again, using `--only` to redo only the lines he names (the flagged ones, or the ones he heard), and leave the other lines with their files and reference segments from the last run; if the setup in the pack wrote a default reference, that can be changed too. For lines carried over on a redo, they carry the similarity of the last run, and are re-flagged by this run's `--min-similarity`.
- **Cost of measuring.** Each line measured calls `speaker-verification` once, and the cost notice before spending money says the most times.

**Whether it was read in full**: when a model cannot finish reading one request it does not necessarily report an error; it stops halfway (for example `models/scene3.md`「Limits of one request」). So after each request is synthesized, `dub` measures how long the audio the model produced is, and compares it with an estimate by character count:

- **Estimating the length.** After removing cues, estimate toward the fast side by `SPEECH_RATE` in `lib/speech-length.mjs` (Chinese characters, kana and Hangul at one rate, other letters and digits at another, punctuation and whitespace not counted; the rate is written only there). This is faster than the measured speaking (reading: Chinese is 4.2 to 4.7 characters per second, `models/scene3.md`「Limits of one request」), so the estimate is on the short side.
- **Unfinished-speech note in the report.** If what came out is less than half of the estimate, `notes` records for this segment a `speech_maybe_unfinished` entry: `details` is `{ unit, expectedMs, actualMs }` (the number of the segment starting at 0, the estimate, and what came out, all in milliseconds), and in the text output it is a notice ("Note:"). This segment is still `ok` and is still handed over. It catches only one that was read less than halfway: if one or two sentences were left out (for example the last sentence of a line was not read) and what came out is still longer than half of the estimate, there is no such entry, and it depends on the user hearing it (below, "Only partial detection").
- **Costs nothing.** No retry, no error, no extra capability call. Measuring the length needs decoding the audio: WAV is decoded by itself, and other formats need ffmpeg; one that cannot be measured is not compared, and nothing is said.
- **Only partial detection.** It recognizes only those that stopped very early: for one that stopped around halfway, what came out is longer than half of the estimate, and there is no warning here. So the absence of this entry does not mean everything was read to the end: when handing back, ask the user to listen to the end of each block (the sub-skill for narration and long text, `scenes/narration.md` step 7「Read the report, then hand it back.」), and the agent does not transcribe it and compare on its own.
- **What to do when you see it.** This entry only reports which segment may have been truncated, and does not redo automatically: tell the user the number of that segment and its first few words, and the user decides. Source: requirement, said on 2026-11-08, no "check and re-draw" loop after generation (the original words: "Didn't I object from the start to logic like 'design twice, auto-check, re-draw if they don't match'? The process is painfully slow! Write the skill properly!"). For a segment the user wants redone, or one whose end the user heard was not read, redo it with `--only <index>` (where the environment accepts `seed`, this line gets a different `seed`, see "Failure and redo"; where it does not accept `seed`, each run is generally different, inference, not tested), or add a chapter heading in the middle to cut it shorter (for the two things to watch when adding a heading, see "A piece cannot hear the previous one" under "How long text is split"); if the `maxChars` the environment declares is too large, tell the adapter's owner.

**Stitching** (whoever joins the lines into one audio follows the details below: the command-line user, or an adapter that stitches by itself): for the details of `joined` segments (several lines merged into one request), speed changes and the silence at speaker changes, see `dub-details.md`「Stitching details」.

- **Silence at speaker changes** (done by `mix`): when two adjacent lines change speaker, the silence at the end of the earlier line and at the start of the later line are each trimmed to 50 milliseconds; for details see `dub-details.md`「Stitching details」.
- **`mix`**: (ffmpeg is needed to decode lines that are not WAV; if the environment has no ffmpeg, the dry run and cost notice of `dub` say so first) joins the lines into one WAV, following `dub-details.md`「Stitching details」: `node cli.mjs mix <dub output directory>... --out <file.wav>`; it computes only locally, calls no capability, and costs nothing. Several output directories can be given (one script split into several `dub` runs, for example changing the reference tag midway, or several roles that need different tags): they are joined into one file in the order given, and the join between directories is the same as between two adjacent lines in one directory (pauses are inserted as written, a different pack is a speaker change and is trimmed, speed is changed). No extra pause is added between directories: at a join where neither side's script wrote a pause, not one millisecond is inserted. Where the same pack keeps speaking (the pack that spoke last in the earlier directory is the same as the pack of the first line in the later directory), the text output names which two directories it is between; if you want a breath, write `[pause 0.5s]` at the start of the later script (or at the end of the earlier one), and for what has already been dubbed, after adding it run that `dub` again with the same `--out` and without `--only`: everything done is carried over and costs nothing, then `mix` (running it again with `--only`, the lines named are always dubbed again and billed again, see "Failure and redo" below; and if in that directory some lines were redone with `--only` under a different `--reference-tag`, without `--only` every line is compared with the reference in the command, and the lines that do not match must also be dubbed again). A join at a speaker change is trimmed per the previous bullet, the same as within one directory, and is not named. In this case the line numbers continue counting from the first directory, and `directories` in the report says which lines of the finished product each directory is (from which to which). With only one directory it is the same as before. Pauses before and after lines are inserted as silence, and the silence at speaker changes is trimmed per the previous bullet; `joined` segments follow the rules of that section; lines whose sample rate and channels differ from the first line's are unified to the first line's (resampling is pure JS and does not depend on ffmpeg). For a line whose `speed` is not null (one whose speed `dub` could not change, see "Opening cue and speed"; the `speed` of one `dub` changed is null, and it is not changed again): if the environment has ffmpeg it is changed with atempo (keeping pitch; the limits are the same as in "Target duration", and a value outside is changed to the nearest end, and `speedChanged` in the report also has `wanted` and `limit`), and if not, it is joined at its original speed, a `speed_not_applied` entry is recorded in the report, and there is no error. A line that is not WAV (mp3 and the like) needs ffmpeg to decode, and without it `runtime_missing` is reported. If some line was not made (it is not ok in `dub.json`), or `dub` stopped midway (`stoppedBy`), no finished product is produced (`mix_incomplete`): the error lists which lines (`details.failed`) and, according to why each line was not made, says what to do, sorted the same way as the output of `dub` (below, "Failure and redo"): for ones that need only a plain redo (a temporary service error, ones not done this time), the hint is to redo first with `dub --only`; for ones whose text was rejected, first change the words of those lines in the script, then give `--only` (for a line that is not in a scene and that the platform says does not fit, add that it should be shortened); for ones shorter than the minimum character count and scenes that do not fit, do not give `--only` and say first how to change the script (where it tells people to add a chapter marker to cut it, in the same sentence write the two things to watch when adding a heading, the same as the output of `dub`, see "A piece cannot hear the previous one" under "How long text is split"), and after changing it run that `dub` command again without `--only`; give only one redo command (the output of `dub` is the same): when ones whose text was rejected and ones that need only a plain redo both exist, first change the words, then redo both kinds together with one `--only`; and when there are ones shorter than the minimum character count or a scene that does not fit, give no `--only` at all, and everything else is redone together in the run without `--only` (if you run only half first, the rejected ones and the ones that do not fit, if not named, are recorded as not done this time, and the reason is lost; for details see `dub-details.md`「Failure and redo details」); for ones that need the script changed first, all point to the output of `dub` or the `error` of that line in `dub.json`; ones not retrieved are not told to be redone (see "Failure and redo"). For one where `dub` stopped midway, say according to the reason it stopped, quoting the notice from when `dub` stopped (`stoppedBy`): for one that did not finish running (`code` is `dub_unfinished`), the hint is to run the same `dub` command again; for one that stopped on consecutive rejections (`dub_text_rejected`, mostly because the reference or other input was blocked), say that redoing it as it is will still be rejected, first change to another reference segment (`--reference-tag`) or change the opening cue (`--emotion`, `--style`, `--energy`, what the setup wrote), and only if it is still rejected after the change, change the words of the rejected lines (name which lines, the numbering the same as `--only`); for one that stopped on another error, first handle the reason it stopped (401 and the like must first be handled by the user). None of them is given a new `--only` (lines that had not started after the stop are not in `dub.json`, so they cannot all be named), and say that after handling it, run the `dub` command that stopped again, and one that had `--only` keeps it as it was: if it is removed, a `--reference-tag` in that command that was meant only for those lines is applied to the whole script, and lines already done must also be dubbed again and billed again (only the reference is like this: emotion, style and energy change the opening cue of every line, and with `--only`, lines not named cannot be carried over either); for one that stopped on `dub_text_rejected`, for changing the reference only `--reference-tag` is changed and one with `--only` keeps it as it was, and for changing the opening cue there are two other routes: run again still with `--only`, in which case the lines not named are recorded as not done this time, so for changing only the lines that were not done well, use a `.json` script and write it in the `labels` of those items themselves and keep the command as it was (`dub-details.md`「Changing only the opening cue of a few lines」), and for changing the whole script, run again without `--only` (the `--reference-tag` in that command that was meant only for those lines is also applied to the whole script; if you want only those lines to use it, split into several `dub` runs and `mix`, the same as the `--reference-tag` row above); the hint says clearly that the command without `--only` changed the reference and the opening cue, and lines already done must also be dubbed again and billed again. `--only` always redoes the lines named, so for the lines that were done in this run before the stop, the hint names them and says to remove them from `--only` before running again (also for a stop at `dub_text_rejected`: for changing the reference, keeping them would redo them with the new reference, and for the `.json` route for changing the opening cue, they do not get the new writing, and keeping them would redo them as originally); for those that were not made even before the stop and that would still fail if run again as they are (rejected text, shorter than the minimum character count, a scene that does not fit), it also names them and says to change them before running again, listed in `details.failed`; when several directories were given, `details.directory` names which directory it is, and the numbers in `details.failed` are those in that directory. The report has the total duration, how many lines were joined, how many silences were inserted (count and milliseconds, counting only what was inserted, not the quiet at the head and tail that each line's audio carries itself), which lines had their speed changed, and how many silences at speaker changes were trimmed (count and milliseconds).

**Whether the pauses fit** (checked at the planning stage, and `--dry-run` also checks it, without synthesizing a single line or spending money): add up all the pauses in the script (`[pause …]` and those written in stage directions) in the order of stitching, and see whether one WAV can hold them. The format of the finished product does not exist yet at this point, so estimate it from the reference segments: take the highest sample rate among the reference segments and the most channels (an mp3 or the like whose channels cannot be read counts as mono); external reference segments, and ones that cannot be read or whose format cannot be recognized, do not count. Stitching uses the actual sample rate of the first line's audio, so the two sides may differ here: the reference segments have different sample rates, or the sample rate the synthesis capability returns differs from the reference segments'. What differs can only matter for a pause that is ten-odd hours or more, which is already a wrongly written script, and stitching checks as usual, and if it does not fit it still reports an error. When not even one reference segment's sample rate can be read, the check cannot be done in the plan: the plan and the output of `--dry-run` have a notice (`pause_length_unchecked`) saying that it was not checked this time and why. When it does not fit it reports `mix_too_long` (when several pauses added up exceed it, it names the place where it was exceeded); a single pause that exceeds what any sample rate can hold is reported as `pause_out_of_range` when the script is read; the errors all say clearly which place in the script it is.

**Failure and redo**: a line with a temporary service error is recorded as `failed`, the other lines are done as usual, the exit code is 1, and the output gives a redo command with `--only`. One shorter than the synthesis capability's minimum character count (the adapter's `limits.minChars`) and unable to merge with adjacent lines into a long enough passage is also recorded as `failed` (`error.code` is `text_too_short`, `details` is `{ chars, min }`, `chars` is the number of spoken characters, cues not counted), calls no capability, and can be seen already in `--dry-run`; the output lists it separately as "Not synthesized: N lines", and it is not in the redo command: redoing is no use, change the script so that it is long enough, or write it together with the adjacent line. Running the same command again with the same `--out`, what was done is not paid for again: a line that was done in the previous `dub.json`, whose file is still there, and whose request this time is exactly the same, is not synthesized again, and that file is carried over (`carriedOver` is `true`), and `carried_over` in `notes` and the text output say which lines were carried over. They are recognized by content, not by number: a chapter heading added in front that changed the numbers is still recognized, and the file is renamed by this run's number. Lines `--only` names are always synthesized again: to get another take of one line, use it. When the environment accepts `seed` (it declares `seed-in-request`), the same `seed` and the same request produce the same audio (checked in auditioning, sample for sample the same), so for a line `--only` names that was done in the same `--out` last time, this run's `seed` is last time's plus 1: `dub.json` records for this line `seed` and `seedChange` (`from` is last time's), and the text output writes under this line "(seed changed: …)". In this way, when a redo of one with `--only` did not succeed (for example a temporary service error), the failed record also records that run's `seed` and `seedChange`, and the next `--only` of it keeps adding, and does not go back to the fixed one (going back would produce exactly the take you wanted to replace). A line that has never been done (it failed the first time) still uses the fixed one on `--only`: what is wanted is to get it done, using the same `seed` as the other blocks it was cut with. For a carried-over line, `seed` and `seedChange` follow the file: what is recorded is what was used when that file was dubbed, and the next `--only` adds 1 to it. It is not an automatic retry: it changes only when you name it for a redo. Lines not named are not compared on the reference segment, and keep the last run's file and reference segment: when a few drifted lines are redone by changing `--reference-tag` and adding `--only`, the other lines are not dubbed again with it. Changing emotion, style, energy, speed and expressiveness is different: emotion, style and energy change the opening cue of each line, speed (given by `--speed` or written in the setup) changes each line's speed, and expressiveness (given by `--expressiveness`) changes the value passed to synthesis for each line (switching between given and not given also counts as a change), and it is the same when `--only` is added: lines not named do not match the last run and are recorded as not done this time (`skipped`); to change only a few lines, see `dub-details.md`「Changing only the opening cue of a few lines」 (write speed and expressiveness in the `speed` and `expressiveness` of those items themselves in the `.json` script). To start over completely, change to a different `--out`. Carrying over does not compare the adapter and the model: if the adapter or model changed and it has to be dubbed again, change to a different `--out`, or use `--only`. To know before running again which lines will be carried over, add `--dry-run` with the same `--out` and look at the plan. One that was interrupted midway (the process was killed, the command timed out): `dub.json` is an unfinished one (`ok` is `false`, `code` of `stoppedBy` is `dub_unfinished`) that lists only the lines already done, and `mix` produces no finished product; run the same command again and it continues, and what was done before the interruption is also carried over; the exception is the one with `--only`: the lines named are always dubbed again, and the lines done in this run before the interruption (`ok`, without `carriedOver`) must be removed from `--only` before running again to be carried over (the hint of `mix` names which lines). What counts as the same request is authoritatively in the file header "沿用" ("carrying over") of `cli/commands/dub.mjs`. A line that the service side has already finished and only whose result was not retrieved (the adapter marks `details.unretrieved`) is listed separately as "没取回" ("not retrieved") and is not in the redo command: running the same command again (or naming it with `--only`) will dub it again and bill again; if you do not want it dubbed again, retrieve it by hand in the way the output says. There is currently no way to hand a manually retrieved audio back into the output directory for `mix` to use, so for a finished product the only way is to dub it again. `unretrieved` at the top level of `dub.json` lists the numbers of these lines (the same numbering as `--only`, starting at 1), so one look tells how many lines were already generated and just not retrieved, and how to retrieve each line is in its `error.details.retrieve`; if there is none, there is no such item. After that, when the other lines are redone with the `--only` command in the output, these lines not named are still recorded as not retrieved (only if it is the same request, recognized the same way as carrying over), `unretrieved` and `retrieve` are still there, and that run also exits with 1. In that case, running that `--only` command again as it is will not dub them again, and will dub the lines named again and bill again: to dub them again, name them with `--only`, or run again without `--only` (the paragraph "not retrieved" in the output of that run says exactly this). For the remaining details (not retrieved, text rejected, conditions for stopping, 401), see `dub-details.md`「Failure and redo details」.

**Scripts inside the pack**: `{ entry, runtime, feature }` in the manifest's `scripts`, where `feature` is `dub` or `convert`. A feature runs only the scripts registered under its own name; one with no `feature` written is not run automatically (the dubbing guidance can teach you to use it by hand). The runtime environment trusts scripts completely: it runs them directly, does not have the user confirm, and does not isolate them. The runtime is taken by name: `node` is the Node that runs the command, `python` looks for `python3` or `python`, and other names are looked up on PATH. If the runtime is missing, only the feature that uses this script reports `runtime_missing`, before synthesis; `--dry-run` does not report it and only says in the output what is missing. A script reads one JSON from standard input and writes one JSON to standard output (writing nothing or `{}` means no change):

- Input: `{ protocol: 1, feature, hook, pack: { id, name, version }, unit: {…} }`. `hook` is `text` (before synthesis, `unit.text` is the words to be spoken) or `audio` (after synthesis, `unit.audio` is Base64 audio, and `unit.mimeType` is its type); the same script is called for both hooks, and outputs nothing if there is nothing to do. The `convert` feature has only the `audio` hook.
- Output: for the `text` hook `{ "text": "the rewritten words" }`; for the `audio` hook `{ "audio": "<Base64>", "mimeType": "audio/wav" }`. Other keys, or output that is not a JSON object, always report `script_output_invalid` and are not quietly ignored. When one feature has several scripts, they run one after another in the order in the manifest.

**Changing a voice and singing**: `node cli.mjs convert <pack directory> <audio file> --out <file>` (`--singing` is for singing); for a missing capability, an output file that already exists, the cost notice for changing a voice, and scripts, see `dub-details.md`「Changing a voice and singing」.

**Which capability each function needs**:

| Function | Required | Used if present |
|---|---|---|
| Dubbing (`dub`) | `voice-cloning` | `text-to-dialogue` plus `scene-in-request` (a passage that several people speak in turn is dubbed in one request), `speaker-verification` (each request is compared with the reference for timbre), `seed-in-request` (the same seed for each request, and `--only` redo changes it), `phoneme-markers` (the lexicon's phonemes are written as phoneme tags; for one that declares only `phoneme-in-text`, pinyin is written as SSML), the model that the enhancers correspond to |
| Changing a voice (`convert`) | for speech `voice-conversion`, for singing (`--singing`) `singing-voice-conversion` | the model that the enhancers correspond to |

Which capabilities the current runtime environment has is in the notes of the adapter that is connected; to write your own adapter, see `dub-details.md`「Your own adapter」.

# Making a voice pack

This file is the base part reference that `SKILL.md` section 7 points to. The flow (when to make a pack, how to use it afterwards) is in `SKILL.md`. Here is the general use of the command: how to write it, the options, the report, the material, tags, dubbing guidance and new versions. Fine details the main path does not need are in `references/make-pack-details.md`; the clean room and the duplicate check are in `references/clean-room.md`.

The author hands over a batch of original recordings, and they become the role part of a voice pack: `node cli.mjs make-pack [<material directory|material.json>] --output <new directory> --name <name> [--short-name <English short name>]`. `--short-name` is the English short name in the pack ID; without it `vp` is used. The material can be left out: hand over a long recording directly with `--recording <file|directory>` (see "Source material" below), and release a new version with `--previous` (see "Release a new version"). The authoritative description of inputs, options, report and errors is the file header of `lib/make-pack.mjs`. The `--output` directory must not exist yet; the command overwrites nothing. The protocol core must be sealed (`--protocol` points to the officially released one; in a development tree use `seal` to seal one for your own use).

**Source material** is clips that are already cut, each one an audio file plus what it says: every audio file in the directory is one segment, and a `.json` with the same name holds `{ id, text, annotatedText, language, tag, source, sentence, synthetic, trim, externalUrl }` (`id` is the segment name, and the file name is used if it is not written; for `annotatedText` see "Cue annotation" below, for `synthetic` see "Regenerated reference segments" below, for `trim` see the paragraph on using only a few seconds of a clip below) (`source` is `{ recording?, startSec?, endSec? }`: the source recording and the start and end seconds; it goes into the report only, not into the pack. `sentence` is a sibling of `source`, written on the segment, not inside `source` (written inside it, it raises no error and does not count): `{ bodySec, pauseSec }`, meaning this segment is one sentence, the length of the sentence in seconds and the pause that originally followed it, `null` when nothing follows. Segments with `sentence` are treated as sentences and, like the sentences cut from `--recording` below, are first merged into segments of 5 to 20 seconds. If every sentence in a merged segment has `text`, the text of the segment is the `text` of those sentences joined in order, and this segment is not transcribed; at a join where either side is a Chinese character, kana or their full-width punctuation, join directly, otherwise add one space (Korean is treated like English). If one sentence has no `text`, the whole segment is transcribed. If every sentence has `annotatedText`, the cue annotation of the segment is joined the same way, and the segment is marked `synthetic` only if every sentence is marked `synthetic`. Sentences in the same language may be merged into one segment, so `synthetic` and `annotatedText` must either all be written or all be left out; if they differ, before any money is spent it reports `make_pack_input_invalid`. When given together with `--recording`, the sentences cut from it count as having none of these written). When there is only text, a `.txt` with the same name also works. Or one `.json`: `{ "segments": [{ "audio": "audio/a.wav", "text": "…", "language": "zh", "tag": "愤怒" }], "notes": [{ "code": "…", "message": "…" }] }`. A long recording is handed over directly, without cutting first: `--recording <file|directory>` (every audio file in the directory is one long recording). If the environment has `audio-source-separation`, the vocals are separated first (`--no-separate` skips separation, for input that is already clean vocals), then the recording is cut into sentences: if the environment has `voice-activity-detection`, the speech intervals it gives are used; if not, pauses are found by energy (the file header of `lib/long-recording.mjs`, sentence mode). When the pack is made, sentences are first merged into segments of 5 to 20 seconds, then each segment is transcribed once (sentences are not transcribed one by one and not listened to one by one: a short sentence has no context, so transcription gets many characters wrong, and a small block with nobody speaking can make the transcription invent a sentence; measured, only on one adapter, 2026-11-05: of 25 sentences shorter than two seconds, in Chinese 18 of 38 characters were wrong, and both noise blocks were made into whole sentences). The number of transcriptions, the cost estimate and the plan of `--dry-run` are all counted in segments. Separation and VAD are paid calls, once per recording; before calling, this is stated on standard error, and `--dry-run` does not call them (it cuts by energy and reports the number of sentences and the number of merged segments). The segments cut out have no verbatim transcript, so if the environment has no transcription (`automatic-speech-recognition`) none of them can be used: when the material has no other segment with a verbatim transcript, the pack make reports `make_pack_no_material` before any money is spent and calls neither separation nor VAD (`--dry-run` reports it too); connect an adapter that has transcription. A note left by the cutting (for example "Separation was not done this time, so the input must be clean vocals") goes into the `notes` of the report; if you cut yourself, you can also write it into the `notes` of the material `.json`, and it goes into the report as written.

**Clips cut from a source**: recordings taken from video, animation or games are often files with a video track, often with background music and other people cutting in. Material (including segments with `trim`) is not separated; only `--recording` is separated, when the environment has the separation capability. Material and `--recording` both accept `.mp4`, `.m4v`, `.mov` and `.mkv`: the pack make takes only the first audio track and stores it as WAV, and the reference in the pack is still audio (the formats a pack can hold are still wav, mp3, flac, ogg and m4a; other formats such as `.webm` and `.aac` also get their audio track taken first); what `--recording` hands to separation and VAD is also this one audio track. Taking the audio track needs `ffmpeg` in the environment, the same as decoding other formats. If it is not there: that segment of the material cannot be used (`audio_unrecognized`; the text output says the environment does not have ffmpeg, so the audio track cannot be extracted; when no segment can be used, `make_pack_no_material` carries `details.missingRuntime`); for what `--recording` hands over, the whole command stops and reports `runtime_missing` (naming ffmpeg), and not one capability has been called on this recording. For a segment whose audio track was taken, `convertedFrom` in the report holds the original format. External resources (segments with `externalUrl`) do not get an audio track taken and do not accept `trim`: the pack records only the URL, the size and the hash, and if the file were taken or cut it would no longer match the file at the URL; to use one, first convert it to a format a pack can hold, cut it, and then put it at the URL.

To use only a few seconds of a segment, write `trim` on that segment: `{ startSec?, endSec? }`, in seconds, counted from the beginning of this file; write at least one, and cut at least 0.1 second; without `startSec` it starts at the beginning, without `endSec` it runs to the end, and a value past the end is cut at the end. The pack make cuts out these seconds first, then screens segments, transcribes and picks references; the `trim` of this segment in the report holds the seconds actually cut; the `--source-pack` duplicate check also compares only these seconds. If a file has several usable places, write them as several segments, with `audio` pointing to the same file and each with its own `trim` (the file is read once and decoded once); 5 to 20 seconds per segment is best (the suggested length of a reference; split longer ones). The `trim` ranges of the segments must not overlap: of overlapping ones in the same file, the later segment cannot be used and is recorded as `duplicate_audio` (a segment without `trim` counts as the whole file; adjacent ranges do not count as overlapping). The `.json` with the same name in a material directory can also hold `trim`. `trim` and `sentence` cannot be written together, and external resources do not accept it; a wrong value (not a number, negative, end not after start, shorter than 0.1 second) is reported as `make_pack_input_invalid` before any money is spent, naming which segment's `trim` it is; a segment whose start is past the end of the recording cannot be used (`trim_out_of_range`). `--recording` does not accept `trim`: hand over the recording to be cut as material, and a segment without `text` is transcribed when the pack is made:

```json
{ "segments": [
  { "id": "clip-a", "audio": "clip.mp4", "trim": { "startSec": 12, "endSec": 20 } },
  { "id": "clip-b", "audio": "clip.mp4", "trim": { "startSec": 41.5, "endSec": 50 } }
] }
```

**Segment tags**: each segment of material has two items, written as the segment's own `language` (language) and `tag` (reference tag), with the same names as the fields in the manifest; what the author gave and what the library gave are not told apart.

- Language: `--language` (when calling `makePack` in the library, the input's `language`) gives all segments a default, and the segment's own `language` overrides it. If none is given, it comes from the transcription or from the text itself (Latin script cannot tell English from French; a segment whose language cannot be recognized and was not given cannot be used, `language_unknown`; when the transcription does not report a language, every segment of Latin-script original voice cannot be used after the transcription fee is paid, so in that case add `--language`, and the command reminds you in one line before spending money).
- Reference tag: used only to switch between several reference segments of one character (segments for different emotions, different ages), one per segment, free text, Chinese or English, 1 to 64 characters (counted by code point). A given tag has whitespace removed at both ends and is not changed otherwise; only whitespace, or more than 64 characters, is reported as `make_pack_input_invalid` before any money is spent. There is no default tag. For a segment without one, the pack make names it itself: in the call that gives this segment its cue annotation (see "Cue annotation" below, in the same answer), the model is asked to also give a short name, in the skeleton language of the pack (`--text-language`, Chinese by default), saying the most prominent of the emotion, age or state of this segment, for example `平常` (normal), `愤怒` (angry), `少年` (young), without the character's name; no extra call is made for a name, and the cost estimate does not count more. The name has whitespace removed at both ends, and one over 64 characters is cut to 64. Where no name can be made, the segment name (`id`) is used: the environment has no `audio-text-to-text`; this segment is not annotated (voided, blocked, the service keeps failing); the name is missing or blank; the material gave `annotatedText` (this segment does not call the model). A name made by the model does not take part in the grouping used to pick held-out recordings and the cap on references. If two reference tags are the same within one language (compared character by character, differing case counts as two), the one later in the manifest gets a number (`愤怒 2`); there is only one exception: a tag someone gave takes priority, so when a name made by the model or a name that fell back to the segment name collides with a tag written in the material, one from the previous version, or one changed by `--retag`, no matter which comes first, it is the segment named by the model or by the fallback to the segment name that gets the number, so the `referenceTag` of a setup always points to the segment that was given that tag. Held-out recordings record only the language, without a tag. References carried from the previous version keep using the previous version's tags; to change them see "Change the tags" below.
- The `labels` of the old form (per segment, or in the input) is no longer recognized: it is reported as `make_pack_input_invalid` before any money is spent; rewrite it as `language` and `tag`.

In the report each reference segment has `{ language, languageSource, tag, tagSource, renamedFrom? }`: `languageSource` is one of `material` (given by the material or by `--language`), `transcription`, `text`, `previous`; `tagSource` is one of `material` (given by the material; one changed by `--retag` too), `model` (a name made by the model), `id`, `previous` (carried from the previous version); `renamedFrom` of a numbered one holds the original name (a tag given by the material or by renaming, or a name made by the model); a held-out recording has only `{ language, languageSource }`. For a segment without text, it can be transcribed only if the environment has `automatic-speech-recognition`; without it the segment cannot be used (`no_text`). When a capability is missing, only the step that uses it is skipped, and the report says so.

**Cue annotation**: besides the verbatim transcript `text`, a reference segment also stores a cue annotation `annotatedText`: the verbatim transcript with cues in square brackets added where the way of speaking changes, for example `[normal]啊，瞧瞧这是谁？[laughs]呵呵，[happy]太可爱了吧。`; the words outside the cues are the same as `text`. When dubbing, it is handed to the model together with the reference, so the model knows how this reference was spoken. The pack make annotates in more detail, point by point: in front of each clause it writes how the person in that clause sounds, where they pause, whether they speak fast or slow, and not one word is changed (the way of writing, the thresholds, examples and what was heard are in `models/scene3.md`「Reference text and cue annotation.」). Held-out recordings are not annotated; segments where the material gave `annotatedText`, and segments carried from the previous version, do not call the model. Every other reference segment, after the reference set is picked, is annotated this way if the environment has `audio-text-to-text`, three things per segment: listen, measure, combine (the authoritative description is in the file headers of `lib/segment-annotation.mjs` and `lib/make-pack-annotation.mjs`):

- **Listen once.** Let the model listen and annotate clause by clause. The verbatim transcript handed to it has the first few words removed, and it must write the beginning it hears (a check on what it heard: if what it wrote is empty, it heard nothing and this segment is voided; if it does not match the beginning of the verbatim transcript, the whole result is not voided: the beginning is no longer used to locate anything, the cues are placed only where the few words it gave are found as they are in the verbatim transcript, those not found are dropped, and `annotation.openingErrorRate` of this segment records the error rate; such a segment has no proof that "the model really heard it", so the report says so (`steps.annotation.openingMismatched`). The check on what it heard when picking the default segment and in blind listening stays as it was: a mismatch voids. Katakana versus hiragana, and in text with Chinese characters Arabic numerals versus Chinese numerals (94 and 九十四; Japanese follows Japanese writing, 100 and 百) are only different ways of writing and do not count as a mismatch; the folded and the as-is comparison take the smaller, so it is never more likely to be voided than an as-is comparison (numbers of 5 or more digits are read digit by digit, and writings such as 一万 that still do not match after folding are counted by the as-is comparison); `openingErrorRate` and `foldWritings` in `lib/fidelity.mjs`), then it gives the cue of each clause and the few words that follow the cue directly: the emotion is one or two words chosen from a fixed English vocabulary (cues are always written in English, whatever language the line is in), and a trailing drawn-out ending or rising ending can be added; a separate entry is written only for laughing, sighing, breathing in or choking that is really heard, and none is written where there is none. The cues are inserted into the verbatim transcript at the position of those words, and not one character of the verbatim transcript is changed.
- **Listening failed.** A temporary error or an empty answer is asked again under the retry rule (`lib/call-attempts.mjs`); if it still fails after the retries are used up, it is recorded as not listened to successfully; if it is blocked by the provider, the answer cannot be read, the beginning it wrote is empty (the check on what it heard did not pass), or it did not end normally, this segment is voided and is not asked again. The short name of the reference tag (above, "Segment tags") is in the same answer.
- **Measure pauses and speed.** This is done at the same time as listening (when listening fails, the transcription done for measuring has already been paid for, and the result is not used). It is measured if the environment has transcription (`automatic-speech-recognition`); measuring is only computation and transcription and does not judge good or bad: the recording is cut open where silence lasts 0.05 second or more (first this segment is brought to the loudness that is written into the pack (−20 LUFS) in memory and then cut; a peak below -30 dBFS in a 5 ms window counts as silence, and silence at the two ends is not a pause; with loudness adjustment turned off (`--no-loudness`) the original level is used); a block shorter than 0.05 second is not speech, is removed and not transcribed, and the silences on both sides of it count as one pause; at most 24 blocks, and if there are more, the shortest silences are merged back first; each block is transcribed once (only to match positions; the verbatim transcript `text` does not change by even one character), with the language of this segment, and matched to the words of the verbatim transcript by words and duration together (matching by duration alone would put words in the wrong place, and the transcription of short blocks is often wrong); a transcription clearly out of proportion to the duration does not count (the word count is greater than 2 plus the seconds of this block times 12, or it is empty); for such a block only the duration is used for matching words and it does not enter the error rate, and if the duration of the blocks with usable transcription is less than half of the total, that also counts as not matching; if the total edit error rate over the blocks with usable transcription is above 0.6, it counts as not matching, and this segment does not use the measured result. What is measured: how long each block was preceded by a pause, and how many words per second each clause speaks (by character for Chinese and Japanese, by word for others; a one-character clause is not counted for speed).
- **Combine the results.** Following the table in `models/scene3.md`「Reference text and cue annotation.」, merge the measured pauses and speed into the cues that were heard. With the square brackets removed, the combined text must be exactly the same as `text` and must not exceed the length the manifest allows; if not, it is voided, and this segment falls back to storing only the verbatim transcript.
- **A failed measurement does not block annotation.** No transcription, audio that cannot be decoded, transcription that still fails after the retries are used up, or no match with the verbatim transcript: this segment uses only the cues that were heard, no pause or speed is written, and the report says so.

The thresholds (how long a pause gets `[pause]`, the speed multiples, the volume and length of silence, 0.6) are all set from one segment of reference of a single voice; they are inference and have not been tried on other voices. The number that decides whether a transcription counts as invented (12 words per second) is inferred from four voices; for languages counted by words, such as English, it is much looser, only stops invention, and has not been measured. A segment that is not annotated (blocked by the provider, fewer than 2 usable answers, not one cue matches the original text, or the combined text does not match the verbatim transcript) stores only the verbatim transcript, and the report says which segments and why; the few cues that do not match the original text are dropped, and the report says how many were dropped; a segment where the model says there is no change in the way of speaking has no cue annotation and does not count as not annotated. If the environment does not have this capability, only the verbatim transcript is stored, and the report says so. For this step the report says how many times it actually asked, how many blocks it transcribed, how many segments were measured, how many were not and why (for a segment that did not match but did get its words matched, `measureErrorRate` also carries the word-matching error rate, so you can see how far off it was; segments with too few usable transcribed blocks have no word matching, and segments where no route could be cut have none either; neither carries it), and for each segment how many listening results were used. These calls are counted in the cost estimate before any money is spent: `audio-text-to-text` 3 times per reference segment; extra asks after temporary errors, and transcription (at most 24 blocks per segment, one call per block, plus retries) are counted in the margin for extra asks, not in the expected number of calls. The actual calls do not exceed the total the user agreed to.

**Change the tags**: when releasing a new version, `--retag <segment name>=<tag>` changes the reference tag of one reference segment of the previous version (when calling `makePack` in the library it is the input `retag: { segment name: tag }`); like `--drop`, it needs `--previous`. One segment per use; to change several, give it several times; it is split at the first `=`, not at commas, so a tag can contain commas. The rules for the tag are the same as for the `tag` given by the material: whitespace removed at both ends, only whitespace or more than 64 characters is not allowed. A segment name that is not a reference of the previous version (a held-out recording, one the previous version does not have, one removed by this `--drop`), or the same segment given twice, is not allowed either. All of these are reported before any money is spent as `make_pack_input_invalid`, with `field` set to `retag` and `details.segment` the segment; giving no `--previous` is a usage error. For a changed segment `tagSource` in the report is `material`. Name collisions: all the `--retag` values are counted first and then compared, so two segments swapping names is not a collision; if a changed name collides with an unchanged segment of the previous version, the segment being renamed gets the number; if it collides with a segment newly added this time, the new one gets the number; if two segments are changed to the same name, the one later in the reference set gets the number. If the `referenceTag` of a setup refers to a changed tag, change it together (write the new name in `--setups`; the same when the setups of the previous version are carried over), otherwise it is reported as `make_pack_input_invalid` before any money is spent, with `field` set to `setups[<index>].referenceTag`. Giving only `--retag` and changing nothing else can also release a new version: `retagged` in `version.changes` of the report holds the names of the segments whose tag changed (the library's `describeChanges` receives this item among the changes as well), and a changelog generated when `--changelog` is not given names those segments; changing to the original name changes nothing (`make_pack_nothing_changed`).

**Change annotated cues**: if the material `.json` has `annotatedText`, it is used as given, and the model no longer annotates this segment (what the author gave and what the library gave are not told apart). The words outside the cues must be the same as `text`; if they do not match, it reports an error before any money is spent; if only `annotatedText` is written and `text` is not, the verbatim transcript is that sentence with the cues removed, and this segment is not transcribed (the rule is in the file header of `lib/make-pack.mjs`, "Input"). For a segment carried from the previous version, this version offers no separate way to change it: to change it, `--drop` that segment and give it again as material with the new `annotatedText`; the segment name must not repeat one from the previous version (a removed one counts too), so use another segment name, for example change `calm` to `calm-2`. A segment carried from the previous version is not annotated again and follows the previous version.

**Loudness**: the rules, the limiter, and how to use `--no-loudness` and `--no-limiter` are described in detail in `references/make-pack-details.md`「Loudness」.

**Look at the plan first**: `--dry-run` does only the steps that cost nothing (recognizing the format, the duplicate check, the audio quality check), says how many times at most each capability would be called, and makes no pack and calls no capability. When a connected adapter gives a cost notice, it is stated once more on standard error before the real run; the cost is booked to the user's own account. `--no-evaluate` does not do the trial synthesis and does not measure fidelity.

**Reference set and held-out recording**: how many held-out recordings are kept is described in detail in `references/make-pack-details.md`「Reference set and held-out recording」; how the default segment is decided is in "Default segment and audition line" below. For a designed voice, make the pack twice, both times with `--default-segment <that segment> --no-holdout`; see "Making a pack from a designed voice" below for how to write it; for recordings given by the user (recordings of this character himself in the library count too) see "Recordings supplied by the user".

**Default segment and audition line**: the default segment is the way this voice speaks normally. A character can speak several languages, and in the reference set each language has its own default segment: when neither the caller nor the setup names a reference, dubbing uses the segment of the language of the line (`references/dub.md`「How a line becomes synthesis」step 3). The main language is the language with the most segments in the reference set (for a new version it stays the main language of the previous version); its default segment is written into `reference.defaultSegment` of the manifest, and those of the other languages into `reference.languageDefaults` (`protocol/FORMAT.md` 4.4). The audition on the card: if the pack has an audition line (see "How to give the audition line" below), that is played; if not, the recording of the default segment of the main language is played, not synthesized, only as a fallback. When making the pack, give the same line this way for designed voices and for voices made from recordings alike. The default segment of each language is decided this way (the authoritative rules are rule 5 of `lib/pack-material.mjs` and the file header of `lib/make-pack-pick.mjs`):

- If the author names one, follow the name. On the command line use `--default-segment <segment name>`; it can be given once per language, each time naming one segment, and that segment is the default segment of its own language, for example `--default-segment e3 --default-segment z2`; when calling `makePack` in the library it is the input `defaultSegment`: the name of one segment, or an array of the names of several segments (the file header of `lib/make-pack.mjs`). One language can have only one named segment: two segments of the same language report `make_pack_input_invalid` (`details.field` is `defaultSegment`), and where the material states the language it is reported before any money is spent. Naming does not decide the main language: if only a Chinese segment is named, the main language is still decided by the number of segments (or by the previous version). When releasing a new version, a language that is not named carries over the previous version's (for conditions see rule 5).
- For a language that is neither named nor carried over, and has more than one candidate: if the environment has a model that can listen to audio (`audio-text-to-text`), ask it to pick, among the candidates of this language, the one that is most natural, sounds like talking to a person and carries acting, not one that reads a script flatly. The candidates are all the references of this language in the reference set, the first 8 segments by priority, one call per language, and each call hands over only the segments of this language; it must write the first few words of the segment it picked, and if they do not match the known text the pick is voided (a check on what it heard, the same as for the cue annotation). The reason for the pick is written into the report: for the main language in `defaultSegment.why`, for other languages in the `why` of that language's entry in `languageDefaults`, and the text summary has it too. These calls (one per language, plus the margin for retries) are counted in the cost estimate before any money is spent; for a language that was named or carried over from the previous version, it is not asked to pick and this is not counted.
- If the environment lacks this capability, or it did not manage to pick (`unpicked` of that language's entry in the report says why): if there is speaker similarity, pick the segment most similar to the average of the other references; if there is not, go by priority.
- A regenerated segment (marked `synthetic: true`) is a candidate just like an original recording, and if it is picked it is the default segment; when the pack has no audition line, the fallback played on the card is this recording.

**How to give the audition line**: `--card-line <file.txt>` (when calling `makePack` in the library, the input `cardLine`) hands over one line; how to write it is in `references/character-voice.md`「Audition line」. The file is plain UTF-8 text, and after whitespace at both ends is removed the whole is the line; it can carry a cue (`[happy, bright voice]`). After the pack is made, this new pack is used to dub it, following the rules of `dub` when no setup and no reference are named (for how the reference is picked see `references/dub.md`「How a line becomes synthesis」; a setup with `default` is filled in following the dubbing rules), one request; the audio is put into the pack, the manifest gets `cardLine` (`protocol/FORMAT.md` 4.4), and the card of the share file plays it. This one synthesis and the margin for its retries are counted in the plan of `--dry-run` and in the cost estimate before any money is spent. The authoritative rules are the file header of `lib/make-pack-card-line.mjs`; for `cardLine` in the report see the file header of `lib/make-pack.mjs`.

- Give this line an expressiveness of its own: `--card-line-expressiveness <integer from 0 to 100>` (when calling `makePack` in the library, the input `cardLineExpressiveness`; for the scale see `vocab/capability-signatures.md`). Only this one line, dubbed this one time, uses this value; the other expressiveness stays as it was, from the default setup. Give it together with `--card-line`; without `--card-line` it reports `make_pack_input_invalid` (`details.field` is `cardLineExpressiveness`, `--dry-run` reports it too). The value given is recorded in `cardLine.expressiveness` of the manifest (`protocol/FORMAT.md` 4.4). If the voice has no fixed value (the pack gave no global value and the default setup does not write one), do not fix a starting point: choose by this character and the situation of this line (`models/scene3.md`「Expressiveness」›「How to choose the value」); if one is fixed, do not give it. Source: requirement (author, 2026-11-10: "Dramatic intensity must not be hard-coded. It still has to be tuned per character, presets included, and a preset that fits the character has to be tuned first.").
- If dubbing would turn it into more than one request (a long pause in it, a chapter marker, more characters than one synthesis allows, see `references/dub.md`「One request per passage」): it reports `make_pack_input_invalid` before any money is spent, `details.field` is `cardLine`, and `--dry-run` reports it too. A line shorter than the lower limit of one synthesis declared by the environment (`minChars`) reports the same error. If it is empty after whitespace at both ends is removed: `manifest_invalid` (`details.keyword` is `minLength`). If it has only invisible characters (for example a zero-width space): `manifest_invalid` (`details.reason` is `text_blank`).
- Dubbed but failed: the pack is still made, and the manifest does not have this line; `cardLine.status` in the report is `failed`, and `hints` has `card_line_failed`. To add it, release a new version: `--previous <the directory of this version's pack> --card-line <file.txt>`, nothing else needs to be given. Give it together with `--card-line`.

When there are `reasons`, `hints` has `card_line_stale`: it was carried over, but it differs from how it would be dubbed now. A changed default segment mostly means the voice was changed ("switch to another"): if the voice was changed, give `--card-line` to dub again; for the others (changed pronunciation, speed, expressiveness) it has to be dubbed the current way, again by giving `--card-line`. The rule is in `carriedCardLine` of `lib/make-pack-card-line.mjs` (the text hook, the enhancer and the seed of the dubbing script in the pack are not compared; see there).

When this request is exactly the same as that line of the previous version (the reference, the text of the request, the speed and the expressiveness all match, compared as in the previous item), the seed is changed to that of that line of the previous version plus 1 (`cardLine.seed` in the manifest; if the previous version did not record it, the fixed one plus 1), `cardLine` in the report carries `seed` and `seedChange` (`{ from }`), and the text output says the seed was changed. A request that is different still uses the fixed one. The seed used is recorded in `cardLine.seed` of the manifest (`protocol/FORMAT.md` 4.4), a carried version still carries it, and the next dub-again continues adding. It is not an automatic retry: it changes only when this line is given. The rule is in `voiceCardLine` of `lib/make-pack-card-line.mjs`.

**Regenerated reference segments**: references regenerated in the library (for example a few segments regenerated from one clean reference), and the segment dubbed across languages with this pack when adding another language to the pack (`references/character-voice.md`「Add a reference segment in this language」), are accepted as material, the same as original recordings: they count as references the same way and can be the default segment. In the material mark it `"synthetic": true`; this marker is used only for measuring fidelity: it is not a held-out recording, does not enter the real-person baseline, and the count of real recording segments in the report does not count it. `make-pack` itself does not clone or regenerate material.

**Fidelity**: how it is measured, how to read the report, and the entries for completing and voiding are described in detail in `references/make-pack-details.md`「Fidelity」.

**Where the report is**: the report is printed only on standard output: without `--json` it is a text summary, with `--json` the complete JSON (the `report` field). The command does not write the report to a file; to keep it, redirect standard output.

**What material is still missing**: `hints` in the report, one reason per entry, for example no held-out recording (`no_holdout`), a language with only one segment (`language_single_reference`), no dubbing guidance (`guidance_missing`), items in the guidance that are written `缺` (missing) or not written (`guidance_gaps`). A pack with a design source, or with `--no-holdout`, does not get the two entries about held-out recordings (`no_holdout`, `holdouts_few`). What can only be made up by cloning from this pack itself is not hinted to be made up: a pack with a design source also does not get the three entries about reference segments (`few_references`, `short_reference_total`, `language_single_reference`), because the reference of a designed voice is only the one segment dubbed from the audition, and there is no recording to add. A pack made from the default voice or from a blended voice also writes a design source, and the manifest cannot tell it from a designed voice, so these three entries are not given for it either; its references are cut from the audition of `--audition`, and where there are few segments, they are short in total, or a language has only one segment (the thresholds are `THRESHOLDS` in `lib/material-hints.mjs`), look at the references in the report yourself (the segments with `role` equal to `reference` in `report.segments`, with the duration in `quality.metrics.durationSec`) and add: generate a few more auditions with the default voice or the blend, and release a new version with `--previous` to hand them in; if all the references of a language are synthetic (marked `synthetic`, for example the segment dubbed across languages with this pack when adding another language), `language_single_reference` is not given for this language. Languages are compared in normalized form (`zh-CN` and `zh-cn` are one). After adding material, release a new version.

**Dubbing guidance and voice tags**: `--guidance <file.md>` writes the dubbing guidance (for how to write its five sections see "The five sections of the dubbing guidance" below); it is placed in the last section of `SKILL.md`; write only the effect wanted; the instruction syntax of a model is decided by the adapter, and writing it into the dubbing guidance would tie it to one model. `--direction <file.json>`: `{ description, tags }`; voice tags can only be taken from the design vocabulary (`vocab/design.json`), Chinese names are also recognized, and what is written into the manifest is the canonical form; one that is not in the vocabulary, or any other field, is reported as `make_pack_input_invalid` before any money is spent. `--lexicon <file.pls>` supplies the pronunciation lexicon: it is read only if the `files` of the manifest lists it, so editing the `lexicon.pls` in an installed pack directly has no effect. To change a pronunciation, release a new version (`--previous <previous version> --lexicon <new file.pls>`, see "Release a new version"), which writes the lexicon and its hash into the manifest. `--design-source <file.json>` records the design source, written when a pack is made from a designed voice, a default voice or a blended voice: `{ description, model, modelVersion, date, auditionLines }`, where `auditionLines` is the design audition text (an array of strings, the original text read out at design time). `model` takes the `model` field returned by the capability call (the `voice-design` return has it, and only if the adapter gave it; how to get it is in the notes of the connected adapter); if the return does not have it, do not write it; `modelVersion` is not in the return, do not write it. `--audition <file>` takes the audition of a default voice or a blended voice: it is not separated (synthesized audio is clean vocals to begin with), and it is cut and transcribed the same way, with part as references and part as held-out recordings (the pack make picks following the rules), and the design source is written into the manifest; without `--design-source`, the report reminds you with `design_source_missing`. The audition of a designed voice is not handed in with it: it is only raw material and does not go into the pack that is handed out (see "Making a pack from a designed voice"). `--sample-lines <file.json>` records the sample lines: a JSON array, one line per item, written into `sampleLines` of the manifest as it is; at most 50, each 1 to 500 characters, and not whitespace only (`text_blank`); a line can carry a stage cue, for example `（耳语）` (whispering), and the format stores only this string and does not parse it. If a new version is released without `--sample-lines`, the previous version's is carried over; an empty array removes it.

**Pronunciation lexicon**: the two ways of writing `--lexicon` (`<alias>`, `<phoneme>`) and the conditions for phonemes are in `make-pack-details.md`「Pronunciation lexicon」. Phonemes are written in pinyin for Chinese (`x-pinyin`), Arpabet for English (`x-arpabet`) or romaji for Japanese (`x-romaji`); a phoneme is sent out as a tag, and the characters of the tag are charged just the same; an entry is a whole word, and for one that has only one character the `notes` of the report has an entry `lexicon_single_character`. How to rewrite as phonemes a pronunciation that was changed with an alias using a homophone is in that section too.

**Several setups (writing fixed values into the voice)**: `--setups <file.json>`: a JSON array, each item one setup `{ name, labels?, referenceTag?, speed?, instructions?, expressiveness?, default? }` (`labels` is a fixed `{ language?, emotion?, style?, energy? }`: `language` is a language tag, the names of `emotion` and `style` come from the tag vocabulary (`vocab/cues.json`), and `energy` is one of `low`, `medium`, `high`; they are not the same thing as the reference tag of a reference segment; `referenceTag` is the default reference of this setup, written as the reference tag of one reference segment in the pack, and can be left out; `speed` is a positive number, 1 unchanged, 0.85 slower, 1.15 faster; `expressiveness` is the expressiveness fixed by this setup, and when dubbing, if the caller did not give one and this line uses this setup, it is used (it overrides the global value of the pack, for the global value see "Expressiveness of the whole voice (global value)" below) (for the scale see `vocab/capability-signatures.md`), and how to decide the value is in `models/scene3.md`「Expressiveness」; when making setups, do not declare it by default, and declare it only when this setup really has to differ from the global value (for example furious), and when declaring, move about 10 from the global value; if the pack has no global value, follow `models/scene3.md`「How to choose the value」; the exception is the default preset when a pack is made from a designed voice: it carries a value that fits this character (step 3 of "Making a pack from a designed voice" below), and other presets still do not declare it (source: requirement); `instructions` is a note for the person writing the script, writing the concrete features of an accent or manner of speaking, and `dub` does not send it to the model; names must not repeat, at most one setup has `default: true`, and the authoritative description of the format is `protocol/FORMAT.md` 4.4), written into `setups` of the manifest as it is. When dubbing, the `setup` option of the `dub` command picks one setup, and without it the one with `default` is used; a setup fills in the item that the caller did not give: the language is used to pick the reference (`references/dub.md` step 3); emotion, style and energy are combined into one cue, written at the start of each request, and where the script writes a cue at the start of a passage itself, the script is followed; the speed is changed after synthesis; expressiveness is passed to every synthesis request as it is (all in `references/dub.md`「Opening cue and speed」). **The note (`instructions`) is not sent to the model.** A general label such as "with a bit of a Sichuan accent" or "the manner of a news broadcast" does not tell the model concretely how to read (these two phrases are bad examples). The note is for the person writing the script, and it writes the concrete features of this accent or manner: for an accent, record the words and modal particles of this dialect itself, and which common characters are written as which other characters; it can also record tones, whether the end of a sentence rises or falls, and fast or slow rhythm; where you do not know, look it up or ask the user, and do not make it up from impression (the way to write it and the reason are in `models/scene3.md`「Cross-language and accent」「What to write」). When a setup with a note is used, the `notes` of the `dub` plan has an entry `setup_instructions`, which lists the note as written and which lines use this setup, telling the person writing the script to write the concrete things into the script following the note (`references/dub.md`「Opening cue and speed」). The note has no length limit, and the pack make does not check its length; the manifest format only requires 1 to 4000 characters (`protocol/FORMAT.md` 4.4). For emotion and style use the names in the tag vocabulary (`vocab/cues.json`) or their near-synonyms; a one-shot sound (sighing, laughing, `oneShot` in `vocab/cues.json`) written in style or in emotion is the same, and does not go into the opening cue when dubbing: to sigh or laugh, write it in the script where it happens. **The opening cue combined from emotion, style and energy must be short.** The dubbing model takes only text, and it will be written at the start of every request. Counted the way `dub` synthesizes (one-shot sounds not counted), the whole must not exceed 10 words (`MAX_OPENING_CUE_WORDS` in `lib/cue-length.mjs`; two Chinese characters or kana count as one word, alphabetic scripts count by spaces, digits and punctuation are not counted). If one of the setups given by `--setups` is over, it reports `make_pack_input_invalid` before any money is spent (`--dry-run` reports it too), `details.field` is `setups[<index>]`, and `details.words` is the number of words counted; when a new version is released without `--setups` and the previous version's setups are carried over, one that is over does not raise an error and is written into the new version as it is, the `notes` of the report has an entry `setup_opening_cue_too_long` (`details` is `{ setup, words, limit, from: 'previous' }`), and dubbing reports `dub_input_invalid` when it uses this setup; to change it, give a different file with `--setups`. If the `expressiveness` of one of the setups given by `--setups` is not an integer from 0 to 100 (a decimal, a 0 to 1 style, out of range, not a number), it also reports `make_pack_input_invalid` before any money is spent (`--dry-run` reports it too), and `details.field` is `setups[<index>].expressiveness`. `cueWords` and the two limits (`MAX_CUE_WORDS`, `MAX_OPENING_CUE_WORDS`) are a stable interface for callers: a caller can import `lib/cue-length.mjs` directly and check for itself before handing over to `make-pack` or `dub`. `referenceTag` is checked before any money is spent (`--dry-run` checks it too): it must be a tag given by the material (a segment that was not screened out before any money was spent), or a tag of a reference of the previous version (one removed by this `--drop` does not count, and one changed by `--retag` is recognized as the changed one); a name made by the model or a tag that fell back to the segment name does not count; a mismatch reports `make_pack_input_invalid`, `details.field` is `setups[<index>].referenceTag`, and the setups that were given and the ones carried from the previous version are both checked. When the tag it points to has only one segment left in that language, this segment is not made a held-out recording, and the reference cap does not trim it; if after payment this segment still did not enter the reference set (for example the transcription did not succeed), the command stops with the same error. The trial synthesis of the pack make (measuring fidelity) does not use setups and does not use `referenceTag`: each held-out recording uses the default segment of its own language. There are two ways to change setups. **Only saving a preset or deleting a preset, without a new version**: change in place with the `setups` command, `node cli.mjs setups save <pack directory> --setup <one setup.json>` (the file is one JSON object, with the same fields as each item of `--setups`; one with the same name is overwritten, and if there is none it is added) and `node cli.mjs setups delete <pack directory> --name <name>`, and in the library `saveSetup` and `deleteSetup` of `lib/pack-setups.mjs`. Both accept `--json` and output `{ status, name, setups }`: `status` is one of `added`, `replaced`, `deleted`, and `setups` is the whole list after the change (an empty array if none are left); without `--json` it prints a line or two of explanation. They change only the `manifest.json` of this current version (the setups are in the manifest), and the `SKILL.md` whose size and hash the manifest records (the skeleton has one sentence that depends on whether any setup writes `referenceTag`; after the change it is regenerated from the current manifest, and not written if the bytes did not change); `version`, `changelog`, the verification record and other files are not touched. Before acting, it checks that the pack itself is intact (the files match the manifest, the manifest is valid), and if not it refuses and reports the original error; after the change it validates the whole manifest again (duplicate names, two defaults, `referenceTag` not in the reference set, `speed`, `expressiveness` out of range), and the opening cue combined from the setup saved this time must also not exceed 10 words; one that does not qualify reports `pack_setup_invalid` (`details.problems` is the list of problems), and not one byte is written. When saving `default: true`, the `default` of the other setups is removed (a pack has at most one); overwriting a setup with the same name replaces the whole setup, and the fields of the old setup (including `default`) are not inherited; when all are deleted, the manifest has no `setups` field; deleting the default setup leaves the pack with no default setup, and no other is designated automatically; deleting a name that does not exist reports `setup_not_found` (`details.name`, `details.names`); a new value exactly the same as the old one succeeds as usual and writes nothing to disk. **Only the one pack directory given to the command is changed**: copies of the same pack installed elsewhere and share files already exported do not change, and each has to be changed on its own; do not have two processes change the same directory at the same time (there is no lock, and the later write overwrites the earlier). **Anything that changes the voice, such as changing the reference, changing the guidance or adding material, still needs a new version**: `make-pack --previous`; a new version released without `--setups` carries over the previous version's, giving it replaces them, and giving an empty array removes them.

**Expressiveness of the whole voice (global value)**: `--expressiveness <integer from 0 to 100>` (when calling `makePack` in the library, the input `expressiveness`; for the scale see `vocab/capability-signatures.md`): written into the optional top-level field `expressiveness` of the role part manifest (`protocol/FORMAT.md` 4.4); it is the value of the whole voice, not a setup. When dubbing it comes after the `expressiveness` of the setup: if the setup used for this line has one it is used, otherwise this is used, and what the caller gave overrides both (for the order see the row for `--expressiveness` in the options table of `references/dub.md`). When dubbing without a setup, it only means the setup's value is not taken; the global value is still used. A new version released without it carries over the previous version's value; `--expressiveness none` (in the library `expressiveness: null`) removes it; changing to a different value needs a new version. If it is not an integer from 0 to 100 (a decimal, a 0 to 1 style, out of range, not a number), it reports `make_pack_input_invalid` before any money is spent (`--dry-run` reports it too), and `details.field` is `expressiveness`. How to decide the value is in `models/scene3.md`「Expressiveness」›「How to choose the value」.

When the material is a designed voice, write the sample lines for this character: the basis is the `### 这个人是谁` (who this person is) section of the dubbing guidance (identity, character, toward different people, when emotions rise), the audition line and the user's words; use his way of referring to himself, his catchphrases and his wording, and speak of things he will meet and things he will say to people; if the user has said nothing about this character (every item written in the `### 这个人是谁` section is `缺`), write by the description of the voice, and likewise do not make up an identity. The tone is everyday talk said to a person face to face (the same as `references/character-voice.md`「Default segment: a passage the character says naturally, with acting」: the tone of speaking, like talking face to face; do not write it as the "who the script is addressed to" of the same file, because sample lines are example sentences for the pack and not a script spoken to a listener), one emotion per line, and at least two lines are a question, an answer or an interjection. The group in `vocab/design-sample-lines.json` in the same language as the voice (zh and en, 7 lines each, the `feel` of each line different, and `kind` says which kind this line is: `greeting`, `question`, `reply`, `aside` (interjection), `request`, `apology`) is only a model for tone and length and is not to be copied in as it is: those lines have nothing to do with any character, and if copied in, what the next agent that uses this pack learns is generic pleasantries. `--sample-lines` wants an array of strings; giving the objects of the vocabulary directly reports `make_pack_input_invalid` before any money is spent (`details.field` is `sampleLines[0]`, naming which item). Sample lines are written only into `sampleLines` and are not cloned into material.

**The five sections of the dubbing guidance**: the dubbing guidance writes who this person is, how this voice speaks, how it is read, what is said, and how it speaks after a change of language; it has five sections, and the section names are not translated, following the rule for the `## 配音指引` (dubbing guidance) heading. The sections `### 这个人是谁` (who this person is) and `### 换语言时怎么说` (what to say when the language changes) must be written when the pack is made: if `--guidance` is given but lacks these two sections, or one of them has not one line, it reports `make_pack_input_invalid` before any money is spent (`details.field` is `guidance`, and `details.missing` is the names of the missing sections); a section where every item is written `缺` (missing) also counts as written. After writing, before making the pack, look at the items of these two sections that are written `缺`: if the user is present, ask, and fill in as answered (for a new pack made from an existing pack, hand the answer to the session that writes the guidance to fill in; an agent that has read the source pack does not change it itself, see `references/clean-room.md` step 2); if the user is not present or cannot be asked, leave `缺`, do not make anything up, and when handing over the pack tell the user which items are still missing. The "What material is still missing" of the pack make report also lists these items (`guidance_gaps`), and once they are filled in, release a new version with `--previous`. The other three sections are optional. All five sections are for the person writing the script, and `dub` does not hand them to the model:

- `### 这个人是谁`: five items, one line each, item names written as they are: `- 身份：` (identity: what he does, where, how old; an identity the user has stated is written in as it is, without losing one place), `- 性格：` (character), `- 在意什么：` (what he cares about), `- 对不同的人：` (toward different people: the attitude toward acquaintances, strangers and children, and at least acquaintances and strangers are written), `- 情绪上来时：` (when emotions rise: which way the voice changes when angry, sad or happy). The basis is the user's words, the character's materials and the original work, and each entry is followed by its source; an item with no basis is written `缺` (`- 在意什么：缺`), not made up and not inferred from the type of person. When writing the script, follow it to decide how this person would speak at this moment and what attitude to take toward whom.

- `### 音色` (the voice): how this voice sounds (gender, age, pitch, characteristics and so on, the same kind of thing the design description says). Huskiness and a low voice go in the characteristics, and huskiness is also written into the delivery section; throat position, tightness, breathiness and speed are written in the delivery section (both sections are for the person writing the script: the delivery section is followed to write cues, and the voice section is followed to choose the way of writing). The design description also writes only the voice; how the character speaks, such as speed, pauses and laughing, is written into the delivery section, not into the design description (`references/character-voice.md`「A designed voice: the description」).
- `### 演法` (delivery): how it is read, seven items: throat position, tightness, breathiness, huskiness, speed, pauses, laughing and sighing. `dub` does not hand the guidance to the model: the dubbing agent follows the delivery section to write cues into the script, at the places where the way of speaking or the voice has to change, one place with one cue of two or three words (`references/dub.md`「How a line becomes synthesis」step 5, and the sub-skill of each scene; for fine delivery see the item on fine delivery in `models/scene3.md`「What to write」); which ways of writing the model recognizes and how the readings are, look at the model notes of the base part (`models/scene3.md`「Cues」). The seven items are the range that can be written, not a form to fill item by item: an item the materials do not have is left out as a whole line, with no placeholder (placeholders such as "the materials do not say, not written" would be taken as something to act and written into the cue). If there is not one item, this section is not written.
- `### 台词` (lines): what is said and how it is worded, five items: how he refers to himself, sentence endings, catchphrases, word choice, dialect. The person writing the script looks at it, and it is not handed to the model. For a character with an accent, the dialect item records the concrete features of this accent (`references/character-voice.md`「Features of an accent」).
- `### 换语言时怎么说` (what to say when the language changes): three items, item names written as they are, with the language tag in front: `- 名字：` (name: the name in each language, `en Harry Potter；zh 哈利·波特`), `- 自称：` (self-reference: how he refers to himself in each language), `- 口头禅：` (catchphrase: how it is said in another language, or a note that the original is kept untranslated). One with no basis is written `缺`, as above. The name pair for cross-language dubbing (`[name in the reference language|name in the line's language]`, `references/dub.md` step 3) is taken from the `- 名字：` item; if it is `缺`, the person writing the script makes one up on the spot and tells the user it was made up on the spot.
- Age tiers: where the guidance is written by age tier ("the 16-18 version", "adult"), the tier name and the setup (`name` and `referenceTag` of `--setups`) are written as the same; whether the sayings of the several tiers can be used for each other (whether the adult tier can use the catchphrases of the teenage years) is stated.

After each feature of the voice and the lines, follow its source: the original sentence or a passage of narration in the materials, written as in the original. If it is drawn from narration only, copy the original text of the line. One that the materials do not have and was inferred from the type of person is written "inference" and is not taken as a fact of the character. Each item of the delivery section writes only the content, without a source and without "inference": it is used to write cues, and a source or "inference" written in would be taken as something to act. When analyzing the materials a source is still looked for as usual, and an entry whose source cannot be found is not written into the delivery section. The authoritative description of the format is `protocol/FORMAT.md` section 5 (read it when changing the format, not needed for making a pack). For how to fill in and how to decide the default segment, see `references/character-voice.md`.

**Language of the skeleton**: when an English author makes an English pack, add `--text-language en`; the way of writing and the rules are in `make-pack-details.md`「Language of the skeleton」.

**Release a new version**: `--previous <the previous version's pack directory>`. The pack ID does not change and the version number goes up (`--version` states it explicitly and must be greater than the previous version, otherwise `make_pack_version_invalid`; or `--bump patch|minor|major`, minor by default), and if `--changelog` is not given one is generated from the changes. The previous version must be a pack of protocol 3.x. Packs of 1.x and 2.x (the `protocol` of the manifest is `1.x` or `2.x`; those made by base part 2.7.0 and earlier are all this) are reported as `make_pack_previous_invalid` before any money is spent (`--dry-run` the same): `details.reason` is `protocol_old`, and `details.protocol` is the protocol version it wrote. This version does not migrate old packs; make a new pack from new material, and the pack ID is new. To change the tag of a reference of the previous version use `--retag` ("Change the tags" above). To switch to another, use `--drop` to remove all the segment names of the previous version, see "Making a pack from a designed voice" below. When the design source (`--design-source`) is not given, it is carried over if at least one segment of the previous version is still kept in this version (adding an audition line, changing setups, changing pronunciation, adding material); if not one segment is kept (`--drop` removed all segments, for example making the voice of a voice library out of a designed voice) it is not carried over, this version has no design source, and the notes of the report (`report.notes`) have `design_source_dropped`: the manifest cannot tell which segments came from design, so it counts by segments, and if not one is kept, it counts as dropped; if the voice of this version was still designed, hand over its `--design-source` (the rule is in the file header of `lib/pack-version.mjs`, "design source"). The remaining details are in `references/make-pack-details.md`「Details of releasing a new version」.

**Making a pack from a designed voice**: first use `design` to design an audition, then make the pack twice, going through `make-pack` and `dub`. The designed audition is only raw material: it is unprocessed dry audio and mostly read flat, and if it is used as the reference, every line after that will mostly be acted flat too (inference: all that was listened to was one character in the first page of auditions, listened to by one person, `models/scene3.md`「Reference segments」). So first use the audition to make a temporary pack, use it to dub a passage with acting following the character's materials, and then make the formal pack from that dubbed passage; what is handed out is the formal pack. Write the material as a `.json`, with the `audio` path relative to the directory it is in.

Step 0, design: `node cli.mjs design --description <description> --text <audition text> --out <candidate directory> --adapter <adapter directory>` (how to write the description and the audition text is in `SKILL.md` section 2「Voice design」). It calls `voice-design` once (a temporary error is retried per `lib/call-attempts.mjs`), writes into the candidate directory the audition `intro.<extension>`, the material for step 1 `material.json` and the design source for step 3 `design-source.json`, and then prints the complete commands for the later steps. One candidate at a time; to get another, run again with another output directory (`references/character-voice.md`「Finishing a round without asking, and switching to another」). First add `--dry-run` to see the plan, which calls no capability.

Step 1, the temporary pack, only raw material and not handed out: not installed, not put in the library, no share file made, and it can be deleted after the formal pack is made. The material has only one segment `intro`, which is the locked audition, and `text` is the original audition text (the `material.json` written by `design` is exactly this, the path as written, no need to copy again). It has text, so the pack make does not transcribe the whole segment (when the cue annotation measures pauses it transcribes by blocks, only to match positions and not changing the text); with only one segment, the model is also not asked to pick a default segment (the plan of `--dry-run` shows this); the cue annotation is done as usual (1 listen). The design source, voice, guidance, sample lines and `--card-line` are all not given. The "What material is still missing" of the report will have `few_references`, `short_reference_total`, `language_single_reference`, `guidance_missing`, `direction_tags_missing`, `card_line_missing`, none of which need attention: the temporary pack is only raw material, so no material is added and no new version is released. The material is written like this:

```json
{
  "segments": [
    { "id": "intro", "audio": "audio/intro.mp3", "text": "<audition text>" }
  ]
}
```

```sh
node cli.mjs make-pack <audition-material.json> --output <temporary directory> --name <name> --language zh --default-segment intro --no-holdout --adapter <adapter directory>
```

Step 2, the passage with acting. Write it following the character's materials (where there are no other materials, follow the description and the name); for how to write it see `references/character-voice.md`「Default segment: a passage the character says naturally, with acting」; fit this character, and act the most characteristic part of him fully; save it as a script file and dub it with the temporary pack. Expressiveness is chosen by this character (`--expressiveness <the value of this character>`, an integer from 0 to 100, no fixed number hard-coded, `models/scene3.md`「How to choose the value」; requirement, author 2026-11-10: "Dramatic intensity must not be hard-coded. It still has to be tuned per character, presets included, and a preset that fits the character has to be tuned first."): it only governs dubbing this passage and is not written into the global value of the formal pack, step 3 writes it into the default preset; the text output of the dry run (`--dry-run`) has an expressiveness line saying what value is used and from which level it comes. First add `--dry-run` to see the plan: it must be one request (the text output says "Total 1 line", and in `--json` `units` has only one item); if it has a long pause or a chapter heading it is split into several requests, so remove them and dub again:

```sh
node cli.mjs dub <temporary directory> <that-passage.txt> --out <output directory> --expressiveness <the value of this character> --adapter <adapter directory>
```

After dubbing, look at `dub.json`:

- This passage carries `modelChange` (the adapter changed the model, `adapters/README.md`「When the model changes」): this passage is not used, because the reference must be dubbed by the dubbing model (`models/scene3.md`). Wait until the original model is usable again and dub again as below. A round that does not ask anyone stops here, does not make the formal pack, and writes it into the report as it is.
- Not read in full: if `notes` has `speech_maybe_unfinished`, only report that this passage may have been cut off, and do not dub again automatically: this passage is used all the same, and written into the report as it is (say which passage and its first few characters), and whether to dub again is decided by the user (the command for dubbing again is below; for the source see `references/dub.md`「Whether it was read in full」). One or two sentences left unread (for example the last sentence is missing) has no such entry, and no separate transcription is done to check: step 3 transcribes this passage when the pack is made, and the verbatim transcript in the formal pack is what was actually read, following the voice.
- Longer than 20 seconds: the model side will cut it short, and the text given is no longer used either (`references/character-voice.md`「Default segment: a passage the character says naturally, with acting」). Do not dub again: step 3 cuts it at a sentence end when the pack is made, keeping a length enough for a default segment (no shorter than 10 seconds and no longer than 20 seconds; the rule and numbers are in `lib/cut-at-sentence-end.mjs`, using the pauses in the recording to align sentence ends), and the verbatim transcript in the pack is what was heard in the cut passage, and the sentences after it are not in the pack; the `notes` of the report has an entry `reference_cut_at_sentence_end` (`details` is `{ id, fromSec, keptSec }`), and `cutAtSentenceEnd` of this passage records how long it was and how long was kept. If no pause can be found between 10 and 20 seconds, if there is only one sentence, or if the environment has no ffmpeg and it is not WAV (it cannot be decoded, so the length cannot be measured), it is not cut and is used as it is, and in `quality.reasons` of this passage `duration_long` still reminds you.

If the user decides to dub again: `node cli.mjs dub <temporary directory> <that-passage.txt> --out <output directory> --only 1 --expressiveness <the value of this character> --adapter <adapter directory>`. If the environment accepts `seed`, dubbing again changes the `seed` (`references/dub.md`「Failure and redo」). Do not dub again yourself: one not read in full is written into the report as it is, and one that is too long is cut when the pack is made. The formal pack uses the passage that was dubbed (the verbatim transcript is transcribed by the pack make and matches the recording).

Step 3, the formal pack. The material has only one segment, with a segment name such as `acted`: copy the `001-intro.<extension>` dubbed in the output directory to `audio/acted.<the same extension>` beside the material (or let `audio` be written directly as its path relative to the material .json). Do not write `text`; write `scriptText`: the original script text of the passage from step 2 (with cues and names is fine, and the pack make removes them). The pack make still transcribes this passage, and the picking of the default segment and the cue annotation are both done from what the transcription heard (what the check on what was heard compares is also what was heard); after the annotation, the pieces of the verbatim transcript that sound the same as the script are written in the script's way of writing (transcription often mishears homophones, `百伦` is written back to `摆轮`), and the cue annotation changes to the same characters along with it. If one piece has one character with a different pronunciation (`摸爬` against `莫慌`), or has one extra character that the script does not have, the whole piece is kept as heard: it cannot be told whether the dubbing read it as something else or the transcription misheard it, and the characters of the reference must match what this audio says. What the script has but was not read is not written in. Pronunciation is compared by the first Mandarin reading of each character, tones not counted, and this is done only for Chinese segments; other languages follow what was heard. The authoritative rule is the file header of `lib/script-writing.mjs`. In the report `writtenFromScript` of this passage lists the pieces that were changed; if not one piece was changed (including a segment not in Chinese) it carries `scriptTextUnused`. A segment where `text` is written is not transcribed and is not changed following the script. Do not write `annotatedText` either: the pack make asks a model that can listen to audio to annotate it according to how this audio actually sounds ("Cue annotation" above). Do not fill it with the cues of the script: the cues of the script are the way of speaking that was wanted, not what was read out in this audio, and filling them in would make the annotation wrong. If the environment has no model that can listen to audio, do not fill it either, and only the verbatim transcript is stored. For an environment without transcription (`automatic-speech-recognition`), making a pack without writing `text` reports `make_pack_no_material` (`--dry-run` reports it too): in that case write `text`, which is the original script text with the cues removed; one or two sentences that were left unread cannot be found out either, and this is written into the report as it is. For the reference tag, do not write it and the model names it; to name it yourself, write `tag` ("Segment tags" above). It is the only reference and also the default segment; the audition passage does not go into the formal pack. So in the "What material is still missing" of the report there are no entries for too few references, too short, or a language with only one segment (a pack with a design source does not get them, "What material is still missing" above), and there is no need to clone a few more segments following the hints. The design source (`auditionLines` is the original design audition text), voice, guidance, sample lines and audition line are handed in as usual; for how to write them see "Dubbing guidance and voice tags" and "How to give the audition line" above:

```json
{
  "segments": [
    { "id": "acted", "audio": "audio/acted.mp3", "scriptText": "<script of the passage in step 2>" }
  ]
}
```

```sh
node cli.mjs make-pack <final-material.json> --output <new directory> --name <name> --short-name <English short name> --language zh --design-source <design-source.json> --direction <direction.json> --guidance <guidance.md> --sample-lines <sample-lines.json> --card-line <audition-line.txt> --setups <setups.json> --default-segment acted --no-holdout --adapter <adapter directory>
```

`<setups.json>` is an array with only one default preset, carrying the same value used in step 2: `[ { "name": "default", "default": true, "expressiveness": <the value of this character> } ]`. After the pack is made, it is used when a dub does not give an expressiveness, and the audition line uses it too (no separate `--card-line-expressiveness` is given); the text output of the dry run has an expressiveness line saying what the value is and from which level it comes. Other presets still do not declare expressiveness.

After it is made, the directory name must be the same as the pack ID: if the notes of the report have `directory_name_differs`, change it as it says. The audition line is dubbed with the formal pack, and the reference is this passage. After that, when this pack is used for dubbing, the reference is also this; when the platform temporarily changes the dubbing model, what is cloned is also this, not the audition.

Neither of the two makes uses `--audition`: it cuts the audio into segments of 5 to 20 seconds and then transcribes them, the segment names are made by the command from the file name, a named segment name cannot point to them, and the default segment has to be picked from the cut segments following the rules. `--default-segment <segment name> --no-holdout` fixes this segment as the default segment and leaves out no held-out recording: a designed voice has no recordings of a real person, and holding out a few only costs one more round of trial synthesis. The audition is no longer used to clone emotional lines: cloning mostly copies the acting in the reference, and the "happy" and "angry" cloned from a flat-read audition are mostly still read flat (inference: one person listened on the first page, one character, with no dedicated comparison, `models/scene3.md`「Reference segments」).

The second version (switching to another, for how see `references/character-voice.md`「Finishing a round without asking, and switching to another」): steps 1 and 2 are followed as they are (a new audition, a new temporary pack, a newly dubbed passage), and step 3 becomes releasing a new version of the previous version. If the previous version was made by base part 2.x or earlier (the `protocol` of the manifest is `1.x` or `2.x`; for such packs the segment name of the designed one is `intro`, and some also have `happy`, `angry`, `calm`), a new version cannot be released ("Release a new version" above): for such a pack, to switch to another, make a new pack following steps 1 to 3, with a new pack ID, keep the old pack, and write in the report that the old pack is of the old protocol and no version was continued from it. A pack of protocol 3.x is done as below. The segment name must not repeat one from the previous version, a removed one counts too, so the newly dubbed passage is called `acted-2` (switching once more, `acted-3`, and so on); `--drop` removes all the segment names of the previous version (taken from the references and held-out recordings of the manifest.json of the previous version: a pack made this way has `acted`, and switched ones have `acted-2`, `acted-3` and so on), and the default segment points to the new `acted-2`. When the description is changed, the design source, the voice (the `description` of `--direction`) and the `### 音色` (the voice) section of the dubbing guidance are all rewritten following the new description; a voice and guidance that are not given are carried over from the previous version, and what is written in the pack would still be the old voice; when the design source is not given, all segments of the previous version were removed, the old one is not carried over, and this version has no design source (the notes of the report have `design_source_dropped`). Hand over the audition line again (`--card-line`): if it is not handed over, the line of the previous version was dubbed with the old voice and is carried over all the same, and the report hints `card_line_stale`:

```sh
node cli.mjs make-pack <new-material.json> --previous <the previous version's pack directory> --drop acted --default-segment acted-2 --no-holdout --design-source <new-design-source.json> --direction <new-direction.json> --guidance <new-guidance.md> --card-line <audition-line.txt> --language zh --changelog "<what changed>" --output <new directory> --adapter <adapter directory>
```

A voice from a voice library is also made in these three steps, passing through the acted passage (requirement, raised by the author on 2026-11-10 in `models/scene3.md`「Good examples」; nobody has listened to one made this way): the material for step 1 is this voice from the library (one segment, 5 to 20 seconds, with `trim` written for a long one to take only a few seconds; where the library has text, write `text`, and where it does not, do not write it, and the pack make transcribes it); step 2 dubs the same way, and the expressiveness is also chosen by this character; step 3 does not hand over `--design-source` (it is not designed), and the "What material is still missing" of the report will have `few_references`, `short_reference_total`, `language_single_reference`, which need no attention, and no more segments are cloned following the hints. A recording given by the user does not go through the acted passage, and is made as one pack as below.

**Recordings supplied by the user**: `--recording <recording>` (a directory means several recordings; files with a video track are also accepted, see "Clips cut from a source" above), no need to cut first. At the moment the recording is received, ask one question first: "Is she the only one speaking in this? Is there background music or other people cutting in? If there is, tell me which seconds she speaks alone" (replace "she" with how the character is referred to). If it is only her and there is no background, make it as usual with `--recording`, and there is no need to say more. If seconds were given, write them as material following "Clips cut from a source", one segment per place, with `trim` written, and do not use `--recording`. Material is not separated, and the report will not have a `separation_skipped` reminder for you: if there is still background music in the seconds she speaks, tell the user that the music will be carried into this voice together; if the connected adapter has `audio-source-separation` and the music is to be removed, use `--recording` instead (it does not accept `trim`, and the voices of other people cutting in will be carried in together). If there is background and the times cannot be obtained, make it with `--recording` as it is, and tell the user that the voices of other people cutting in will be carried into this voice; the music has to be judged from the report after it is made. After it is made, look at the report: if `report.notes` of `--json` has `separation_skipped` (the text output is "Note: Separation was not done this time, so the input must be clean vocals"; the environment has no separation capability, or `--no-separate` was given), and the recording also has background music, tell the user the music was also carried into the voice, and if they want it removed, hand over a clean recording and make it again. **Say the noise of the recording on the spot.** The noise and muffledness of a recording are cloned into every line as they are. When `--dry-run` text output shows `recording_noisy` (in `--json` it is in `report.notes`; in a real run the text output also has it on standard error before any money is spent, and `--json` writes nothing to standard error) ("this recording has speech only N dB above the noise ..." or "... the sample rate is N Hz, ... will sound muffled"; either condition triggers it: the median signal-to-noise ratio measured by the quality check is under 25 dB, or the sample rate is 16 kHz or less; a designed voice and `synthetic` segments are not reported), tell the user the facts before the real run: say whichever the note says: every line will carry the same noise (hiss, room sound), or a recording at 16 kHz or less has nothing above 8 kHz and the voice will sound muffled; this is how the recording is, not something the pack making did; give the two better routes, a cleaner recording or a designed voice ("Making a pack from a designed voice"), and ask which; if the user wants to keep using this recording, make it as usual and do not urge again. The basis of the lines is in the header of `lib/recording-noise.mjs`. How long a recording must be to leave enough held-out recordings for fidelity: reading fidelity needs at least 5 valid held-out recordings (`lib/fidelity.mjs`, "how to read this report", point 1); the number held out is 20% of the real recording segments (rounded, rule 2 of `lib/pack-material.mjs`), so 23 segments of real recording (5 to 20 seconds each, a few minutes of recording in all) are needed to leave 5. Make the pack once and it is done:

`node cli.mjs make-pack --recording <recording> --output <new directory> --name <name> --guidance <guidance.md> --direction <direction.json> --sample-lines <sample-lines.json> --card-line <audition-line.txt> --adapter <adapter directory>`, for how to write it see "Dubbing guidance and voice tags", and for `--card-line` see "How to give the audition line". The delivery, the lines and the sample lines are written from the character's materials; if there are no materials, none of them is written, and the guidance has only the `### 音色` (the voice) section. If the recording and the audition line (or the lines to be dubbed later) are not in the same language, do not ask, add `--allow-cross-language`, and at the start of this line write a name pair `[name in the reference language|name in the line's language]` (`references/character-voice.md`「Language and accent」); if it was missed, the report of the pack make will have `card_line_cross_language` ("How to give the audition line" above). Write the audition line following `references/character-voice.md`「Audition line」 (where there are no other materials, follow the description and the name). The command cuts the recording into sentences, merges sentences of the same sampling rate in their original order into segments of 5 to 20 seconds, and then transcribes each segment once (in the plan of `--dry-run`, the transcriptions are counted in segments), and sentences are not transcribed one by one and not listened to one by one; one segment may contain several ways of speaking. Merging does not separate by language: if `--language` was given, the language of the segment is it; if not, the language reported by the transcription of the whole segment is used, and if none is reported, it is recognized from the text of the whole segment. So when one recording mixes several languages and `--language` is not given, one segment may contain several languages, and the language of the segment is decided as above; to separate by language, cut it yourself first and hand it over as material with `language` written on each segment. The reference tag of each segment is named by the call that annotates the cues, and where that cannot make one, it is the segment name ("Segment tags" above). Between two adjacent sentences the original pause is kept, and between sentences that have other sentences between them it is 0.3 second of silence (the rule is in the file header of `lib/make-pack-sentences.mjs`). The default segment is picked following "Default segment and audition line", and `--default-segment` can name any sentence or segment; held-out recordings and fidelity are as usual, without `--no-holdout`. The number of held-out recordings and the cost estimate are both counted by the merged segments.

For all the kinds of pack making above: do not ask the user about `--short-name`; if it is not given, `vp` is used.
